## The Convergence No One Expected

Five years ago, the frontend landscape was fragmented into incompatible reactivity models: React's immutable state + reconciliation, Vue's Proxy-based reactivity, Svelte's compiler-driven invalidation, Angular's Zone.js dirty checking, and Solid's fine-grained signals. Each had its own mental model, its own performance characteristics, and its own set of footguns.

In 2026, something remarkable has happened: **every major framework has converged on signals**.

- **Solid** pioneered fine-grained signals and still has the purest implementation
- **Preact** shipped `@preact/signals` and it became their standard recommendation
- **Vue** introduced `VueSignal` in Vue 3.5, extending their existing ref system
- **Angular** landed signal-based change detection in v17 and made Zone.js optional
- **Svelte** introduced runes (`$state`) in Svelte 5 — syntactic sugar over signals
- **React** released the `useSignal` hook (experimental) built on the same primitives

And perhaps most significantly: the **TC39 committee** (the standards body behind JavaScript) is working on a [Signals proposal](https://github.com/tc39/proposal-signals) to make signals a native JavaScript feature. Once that lands, every framework will interoperate on the same reactive graph.

## What Are Signals, Actually?

A signal is a **reactive value container with automatic dependency tracking**. When you read a signal inside a computed value or effect, the system records that dependency. When you write to the signal, only the things that depend on it re-evaluate.

```javascript
import { signal, computed, effect } from './signals';

const count = signal(0);
const doubled = computed(() => count.value * 2);

effect(() => {
  console.log(`Count: ${count.value}, Doubled: ${doubled.value}`);
  // Logs: "Count: 0, Doubled: 0"
});

count.value = 5;
// Automatically logs: "Count: 5, Doubled: 10"
// Only this effect runs — nothing else in the tree is touched.
```

Contrast this with React's traditional model:

```javascript
function Counter() {
  const [count, setCount] = useState(0);
  const doubled = count * 2;

  useEffect(() => {
    console.log(`Count: ${count}, Doubled: ${doubled}`);
  }, [count, doubled]);

  return <button onClick={() => setCount(5)}>Increment</button>;
}
```

The mental overhead is higher: you declare explicit dependency arrays, you worry about stale closures, you deal with the effect running twice in strict mode, and every state change re-renders the entire component tree unless you manually memoize.

With signals, the dependency graph is automatic. You write code that looks synchronous, and the framework handles the rest.

## The Three Primitives

Every signals implementation boils down to three primitives:

### 1. Signal — A Reactive Value

A writable container. Reading it registers a dependency in the current tracking scope. Writing it invalidates dependents.

```javascript
const name = signal('Alice');
const age = signal(30);
```

### 2. Computed (Derived) — A Derived Value

A read-only value that automatically recomputes when its dependencies change. Computed values are lazy — they only recompute when something reads them after a dependency changed.

```javascript
const greeting = computed(() => `Hello, ${name.value}. You are ${age.value}.`);
const isAdult = computed(() => age.value >= 18);
```

### 3. Effect — A Side Effect

Runs a function whenever its dependencies change. This is where you touch the DOM, make network requests, or update external state.

```javascript
effect(() => {
  document.title = `${name.value} — Profile`;
});
```

## The Dependency Graph: Push-Pull Hybrid

The magic of signals lies in their evaluation strategy — a **push-pull hybrid**.

When you write `count.value = 5`, the signal **pushes** a notification to all its direct dependents (computed values and effects), marking them as dirty. But it does NOT eagerly recompute them. Instead, a dirty dependent **pulls** its value when it's next read or when its effect needs to fire.

This is the key insight that makes signals performant: you only compute what's actually consumed.

```
count = 5        (write: mark dirty)
  ↓ push
doubled = dirty  (not recomputed yet)
  ↓ push  
effect = dirty   (scheduled to run)
  ↓ pull (when effect fires)
doubled = 10     (only now computed)
```

Compare to React's model where the entire component function body re-runs on every state change, regardless of what changed. Signals are fundamentally more efficient because they operate at the property level, not the component level.

### Graph Disconnection

Smart signals implementations disconnect inactive branches:

```javascript
const showDetail = signal(false);
const detail = computed(() => {
  if (!showDetail.value) return null;
  return expensiveNameTransform(name.value); // Only tracks name when showDetail is true
});

// When showDetail is false, changing name.value does nothing to detail.
// The dependency was never registered.
```

This is impossible with manual dependency arrays. With signals, you write normal conditional logic and the graph reflects it exactly.

## Signals Are Not Just for UIs

The TC39 proposal explicitly targets non-UI use cases:

- **State management**: replace Redux, Zustand, MobX with native reactive atoms
- **Server state synchronization**: signals wrapping React Query / TanStack Query results
- **Game engines**: per-entity property reactivity without polling or manual invalidation
- **Web Workers**: signals that transparently sync across threads
- **IoT and edge devices**: lightweight reactive state with minimal overhead

Here's a signal that syncs to localStorage — 100% synchronous feeling, zero explicit subscriptions:

```javascript
function persistedSignal(key, initialValue) {
  const raw = JSON.parse(localStorage.getItem(key)) ?? initialValue;
  const s = signal(raw);

  effect(() => {
    localStorage.setItem(key, JSON.stringify(s.value));
  });

  return s;
}

const theme = persistedSignal('theme', 'dark');
theme.value = 'light'; // Automatically persisted
```

## Common Pitfalls

### Reading Inside an Effect Without Intending to Track

```javascript
effect(() => {
  const current = count.value; // tracked
  const snapshot = untracked(() => count.value); // NOT tracked
  fetch(`/api/count/${snapshot}`);
});
```

If you don't wrap the second read in `untracked()`, changing `count` will re-fetch even though you only wanted a snapshot.

### Forgetting .value

```javascript
const name = signal('Alice');
console.log(name); // Signal object, not 'Alice'
console.log(name.value); // 'Alice' ✓
```

This trips up everyone at first. Once TC39 standardizes signals, JavaScript may get syntax-level support that eliminates `.value` — possibly through the [Signal Extensions](https://github.com/tc39/proposal-signals) proposal.

### Creating Signals Inside Effects

```javascript
effect(() => {
  const local = signal(0); // Created every time dependencies change
  local.value = count.value;
});
```

Always create signals at the top level of a component or module. Creating them inside effects or computed values creates a new signal on every re-evaluation, leaking memory.

## Where This Is Heading

The TC39 Signals proposal is the most significant JavaScript language change since async/await. Once signals are a native feature, here's what changes:

1. **Zero-cost interop**: Solid, React, Vue, Angular components all share the same signal graph. Pass a signal from a Solid component to a React component and both frameworks react to the same state changes.

2. **Tools become universal**: DevTools, debuggers, and profilers work on the native signal graph, regardless of which framework generated it.

3. **No more .value**: Native syntax support lets you read and write signals like regular variables. The compiler or engine handles the reactive wiring.

4. **Web Workers become trivial**: Signals natively synchronize across thread boundaries, making off-main-thread state management a first-class language feature.

## Should You Adopt Signals Today?

**Yes** — they're already stable in every major framework. The mental model is simpler than explicit dependency arrays, the performance is better, and the TC39 proposal means signals are the future of JavaScript reactivity.

If you're starting a new project: Solid or Svelte 5 for the cleanest signal experience.

If you're on React: Preact Signals (`@preact/signals-react`) is production-ready and works with existing React components.

If you're on Vue: `ref()` and `computed()` are signals — you're already using them.

If you're on Angular: the signal-based change detection in v17+ is the recommended path forward.

The convergence is real. In two years, "reactive state" will just mean "signals," and the framework wars on this particular front will be over.
