<p class="post-p">
CSS Anchor Positioning is one of the most consequential CSS features to ship in decades. It solves a problem that has consumed millions of developer hours: <strong>tethering one element to another</strong>.
</p>

<p class="post-p">
For 25 years, positioning a tooltip relative to a button required JavaScript. Libraries like Floating UI (formerly Popper), Tippy.js, and Bootstrap's tooltips exist <em>entirely</em> because CSS couldn't do this natively. Every dropdown, every autocomplete suggestion list, every context menu — all JavaScript.
</p>

<p class="post-p">
As of March 2026, <strong>CSS Anchor Positioning is Baseline</strong>. Chrome 125+, Safari 26+, and Firefox 147+ all ship it. No flags, no prefixes. The browser handles positioning, scroll-aware repositioning, and viewport collision detection — during layout, with zero JavaScript overhead.
</p>

<p class="post-p">
Let's see what it unlocks.
</p>

<h2 class="post-h2">What CSS Anchor Positioning Actually Is</h2>

<p class="post-p">
Anchor Positioning lets you declare that one element (the "positioned element") should be placed relative to another element (the "anchor"). The browser handles all the math — coordinate calculation, scroll offset tracking, viewport boundary detection — during its layout phase.
</p>

<p class="post-p">
Three core concepts:
</p>

<ul class="post-ul"><li class="post-li"><strong><code class="inline-code">anchor-name</code></strong> — Give an element a name so other elements can reference it</li>
<li class="post-li"><strong><code class="inline-code">position-anchor</code></strong> — Tell a positioned element which anchor to use</li>
<li class="post-li"><strong>Positioning mechanism</strong> — Two options: <code class="inline-code">anchor()</code> function (precise) or <code class="inline-code">position-area</code> (declarative grid)</li>
</ul>
<pre class="code-block"><code class="language-css">/<em> 1. Name the anchor </em>/
<p class="post-p">
.button {
anchor-name: --tooltip-anchor;
}
</p>

<p class="post-p">
/<em> 2. Reference the anchor </em>/
.tooltip {
position: absolute;
position-anchor: --tooltip-anchor;
</p>

<p class="post-p">
/<em> 3. Position — using position-area (recommended) </em>/
position-area: block-end center;
margin: 8px;
}
</code></pre>
</p>

<p class="post-p">
That's it. The tooltip now sits below the button, centered horizontally, with an 8px gap. The browser tracks scroll, resize, and layout changes automatically.
</p>

<h2 class="post-h2"><code class="inline-code">position-area</code>: The Natural-Language Positioning Grid</h2>

<p class="post-p">
<code class="inline-code">position-area</code> is the recommended way to position anchored elements. It uses a 3×3 grid of logical positions:
</p>

<p class="post-p">
| | inline-start | center | inline-end |
|---|---|---|---|
| <strong>block-start</strong> | ↖ top-start | ↑ top | ↗ top-end |
| <strong>center</strong> | ← left | ⊙ center | → right |
| <strong>block-end</strong> | ↙ bottom-start | ↓ bottom | ↘ bottom-end |
</p>

<p class="post-p">
The values are <strong>logical</strong> — they respect writing direction. In LTR text, <code class="inline-code">block-end center</code> means "below and centered." In RTL, it still means below and centered. No left/right assumptions baked in.
</p>

<pre class="code-block"><code class="language-css">/<em> Below, aligned to the start edge </em>/
<p class="post-p">
position-area: block-end inline-start;
</p>

<p class="post-p">
/<em> Above, centered </em>/
position-area: block-start center;
</p>

<p class="post-p">
/<em> To the right, vertically centered </em>/
position-area: center inline-end;
</code></pre>
</p>

<p class="post-p">
The <code class="inline-code">center</code> keyword spans both axes. Use <code class="inline-code">span-block-start</code> and <code class="inline-code">span-inline-end</code> to stretch across the full width or height of the anchor.
</p>

<h2 class="post-h2"><code class="inline-code">anchor()</code>: Precise Numeric Positioning</h2>

<p class="post-p">
When you need pixel-level control, use the <code class="inline-code">anchor()</code> function. It lets you reference any edge or property of the anchor element:
</p>

<pre class="code-block"><code class="language-css">.tooltip {
<p class="post-p">
position: absolute;
position-anchor: --my-anchor;
</p>

<p class="post-p">
/<em> "My top edge = anchor's bottom edge" </em>/
top: anchor(bottom);
</p>

<p class="post-p">
/<em> "My left edge = anchor's left edge + 50% of anchor's width" </em>/
left: calc(anchor(left) + anchor-size(width) * 0.5);
</p>

<p class="post-p">
/<em> Center relative to anchor </em>/
transform: translate(-50%, 0);
}
</code></pre>
</p>

<p class="post-p">
<code class="inline-code">anchor()</code> accepts edge keywords (<code class="inline-code">top</code>, <code class="inline-code">bottom</code>, <code class="inline-code">left</code>, <code class="inline-code">right</code>, <code class="inline-code">start</code>, <code class="inline-code">end</code>, <code class="inline-code">center</code>) and percentages (e.g., <code class="inline-code">anchor(50% 50%)</code> for the anchor's center point).
</p>

<p class="post-p">
<strong><code class="inline-code">anchor-size()</code></strong> gives you the anchor's dimensions — perfect for making a dropdown the same width as its trigger:
</p>

<pre class="code-block"><code class="language-css">.dropdown {
<p class="post-p">
position-anchor: --trigger;
position-area: block-end inline-start;
min-width: anchor-size(width);
}
</code></pre>
</p>

<p class="post-p">
A dropdown that's always at least as wide as the button that opened it. No JavaScript.
</p>

<h2 class="post-h2"><code class="inline-code">@position-try</code>: Viewport Collision Handling</h2>

<p class="post-p">
The real killer feature. When a positioned element would overflow the viewport, <code class="inline-code">@position-try</code> defines fallback positions:
</p>

<pre class="code-block"><code class="language-css">/<em> Define fallback positions </em>/
<p class="post-p">
@position-try --flip-to-top {
position-area: block-start center;
}
</p>

<p class="post-p">
@position-try --flip-to-right {
position-area: center inline-end;
}
</p>

<p class="post-p">
.tooltip {
position-area: block-end center;
position-try: --flip-to-top, --flip-to-right;
/<em> If bottom doesn't fit, try top. If top doesn't fit, try right. </em>/
}
</code></pre>
</p>

<p class="post-p">
The browser evaluates fallbacks in order and picks the first one that keeps the element in view. This is what Floating UI's <code class="inline-code">flip()</code> and <code class="inline-code">shift()</code> middleware do in hundreds of lines of JavaScript — the browser now handles it during layout.
</p>

<p class="post-p">
The <code class="inline-code">position-try-order</code> property controls the order of fallback evaluation: <code class="inline-code">normal</code> (try declared order) or <code class="inline-code">most-width</code> / <code class="inline-code">most-height</code> / <code class="inline-code">most-block-size</code> / <code class="inline-code">most-inline-size</code> (try the position that gives the most room).
</p>

<pre class="code-block"><code class="language-css">.tooltip {
<p class="post-p">
position-try: --top, --left, --right;
position-try-order: most-block-size;
/<em> Prioritizes whichever fallback gives the most vertical room </em>/
}
</code></pre>
</p>

<h2 class="post-h2">Tooltip System: Anchor + Popover = No JavaScript</h2>

<p class="post-p">
CSS Anchor Positioning really shines when combined with the <strong>Popover API</strong>. Together, they build entire tooltip systems without JavaScript:
</p>

<pre class="code-block"><code class="language-html">&amp;lt;button popovertarget="info-tip" class="anchor-btn"&amp;gt;
<p class="post-p">
ℹ️ More info
&amp;lt;/button&amp;gt;
</p>

<p class="post-p">
&amp;lt;div id="info-tip" popover="hint" class="tooltip-popover"&amp;gt;
This tooltip appears on hover via the Popover API
and positions via CSS Anchor Positioning.
&amp;lt;/div&amp;gt;
</code></pre>
</p>

<pre class="code-block"><code class="language-css">.anchor-btn {
<p class="post-p">
anchor-name: --popover-anchor;
}
</p>

<p class="post-p">
.tooltip-popover {
position-anchor: --popover-anchor;
position-area: block-end center;
margin: 8px;
</p>

<p class="post-p">
/<em> Smooth entrance </em>/
opacity: 0;
transition: opacity 0.15s, transform 0.15s;
transform: translateY(-4px);
</p>

<p class="post-p">
&amp;amp;:popover-open {
opacity: 1;
transform: translateY(0);
}
}
</code></pre>
</p>

<p class="post-p">
No <code class="inline-code">useState</code>, no <code class="inline-code">useRef</code>, no <code class="inline-code">getBoundingClientRect()</code>, no <code class="inline-code">addEventListener('scroll')</code>. The popover API handles open/close, light-dismiss, and stacking. Anchor positioning handles placement. Both are native, declarative, and performant.
</p>

<p class="post-p">
For hover-triggered tooltips, add <code class="inline-code">popover="hint"</code> — it auto-closes when you hover away:
</p>

<pre class="code-block"><code class="language-html">&amp;lt;button popovertarget="hover-tip"&amp;gt;Hover me&amp;lt;/button&amp;gt;
<p class="post-p">
&amp;lt;div id="hover-tip" popover="hint"&amp;gt;I appear on hover, disappear on mouseleave&amp;lt;/div&amp;gt;
</code></pre>
</p>

<h2 class="post-h2">Dropdown Menu: Complete Example</h2>

<p class="post-p">
Here's a production-ready dropdown using anchor positioning and popover:
</p>

<pre class="code-block"><code class="language-html">&amp;lt;button id="menu-btn" popovertarget="user-menu" class="menu-trigger"&amp;gt;
<p class="post-p">
☰ Menu
&amp;lt;/button&amp;gt;
</p>

<p class="post-p">
&amp;lt;nav id="user-menu" popover class="dropdown-menu"&amp;gt;
&amp;lt;a href="/profile"&amp;gt;Profile&amp;lt;/a&amp;gt;
&amp;lt;a href="/settings"&amp;gt;Settings&amp;lt;/a&amp;gt;
&amp;lt;a href="/logout"&amp;gt;Log out&amp;lt;/a&amp;gt;
&amp;lt;/nav&amp;gt;
</code></pre>
</p>

<pre class="code-block"><code class="language-css">.menu-trigger {
<p class="post-p">
anchor-name: --menu-anchor;
}
</p>

<p class="post-p">
.dropdown-menu {
position-anchor: --menu-anchor;
position-area: block-end inline-start;
min-width: anchor-size(width);
margin: 4px 0;
</p>

<p class="post-p">
/<em> Fallback: flip above if not enough room below </em>/
position-try: --flip-above, --flip-right;
}
</p>

<p class="post-p">
@position-try --flip-above {
position-area: block-start inline-start;
}
</p>

<p class="post-p">
@position-try --flip-right {
position-area: center inline-end;
}
</p>

<p class="post-p">
/<em> Entrance animation </em>/
.dropdown-menu {
opacity: 0;
transform: scale(0.95) translateY(-4px);
transition: opacity 0.15s, transform 0.15s;
</p>

<p class="post-p">
&amp;amp;:popover-open {
opacity: 1;
transform: scale(1) translateY(0);
}
</p>

<p class="post-p">
@starting-style {
&amp;amp;:popover-open {
opacity: 0;
transform: scale(0.95) translateY(-4px);
}
}
}
</code></pre>
</p>

<p class="post-p">
This replicates what required 400+ lines of Floating UI configuration — anchors, middleware pipelines, autoUpdate observers, computePosition calls — in <strong>zero JavaScript</strong>.
</p>

<h2 class="post-h2">Context Menu: Anchored to Click Position</h2>

<p class="post-p">
Anchor positioning even handles dynamic anchors — elements that move or are created at runtime:
</p>

<pre class="code-block"><code class="language-html">&amp;lt;div id="canvas" class="canvas"&amp;gt;
<p class="post-p">
&amp;lt;!-- Right-click to open context menu --&amp;gt;
&amp;lt;/div&amp;gt;
</p>

<p class="post-p">
&amp;lt;div id="ctx-menu" popover class="context-menu"&amp;gt;
&amp;lt;button&amp;gt;Copy&amp;lt;/button&amp;gt;
&amp;lt;button&amp;gt;Paste&amp;lt;/button&amp;gt;
&amp;lt;button&amp;gt;Delete&amp;lt;/button&amp;gt;
&amp;lt;/div&amp;gt;
</code></pre>
</p>

<pre class="code-block"><code class="language-css">.canvas {
<p class="post-p">
anchor-name: --canvas-anchor;
}
</p>

<p class="post-p">
.context-menu {
position-anchor: --canvas-anchor;
position-area: center center;
/<em> The anchor's position gets set via JS to the click coordinates </em>/
}
</code></pre>
</p>

<pre class="code-block"><code class="language-js">// The only JS: update the anchor's position on right-click
<p class="post-p">
canvas.addEventListener('contextmenu', (e) =&amp;gt; {
e.preventDefault();
canvas.style.anchorName = '--ctx-anchor';
</p>

<p class="post-p">
// Use CSS translate to move the anchor to click position
canvas.style.translate = <code class="inline-code">${e.clientX}px ${e.clientY}px</code>;
</p>

<p class="post-p">
ctxMenu.showPopover();
});
</code></pre>
</p>

<p class="post-p">
The browser handles keeping the popover in view — even if the click was near the edge of the screen.
</p>

<h2 class="post-h2"><code class="inline-code">anchor-center</code>: Centering Without <code class="inline-code">transform</code></h2>

<p class="post-p">
A common pattern: center a tooltip horizontally relative to its anchor. The old way was <code class="inline-code">left: 50%; transform: translateX(-50%)</code>, which could cause subpixel blurring and compositing layers.
</p>

<p class="post-p">
<code class="inline-code">justify-self: anchor-center</code> and <code class="inline-code">align-self: anchor-center</code> center the positioned element relative to its anchor — without transforms:
</p>

<pre class="code-block"><code class="language-css">.tooltip {
<p class="post-p">
position-anchor: --btn;
position-area: block-end center;
justify-self: anchor-center;
/<em> Perfectly centered on the anchor, no transform needed </em>/
}
</code></pre>
</p>

<h2 class="post-h2">Progressive Enhancement</h2>

<p class="post-p">
Not every user is on a Baseline browser yet. Here's a robust progressive enhancement pattern:
</p>

<pre class="code-block"><code class="language-css">/<em> JS-based fallback positioning </em>/
<p class="post-p">
.tooltip {
position: absolute;
top: var(--tooltip-top, 0);
left: var(--tooltip-left, 0);
}
</p>

<p class="post-p">
/<em> Native anchor positioning when supported </em>/
@supports (position-area: block-end center) {
.tooltip {
top: auto;
left: auto;
position-anchor: --tooltip-anchor;
position-area: block-end center;
}
</p>

<p class="post-p">
.trigger {
anchor-name: --tooltip-anchor;
}
}
</code></pre>
</p>

<p class="post-p">
JS sets <code class="inline-code">--tooltip-top</code> and <code class="inline-code">--tooltip-left</code> CSS custom properties as a fallback. When the browser supports anchor positioning, those are ignored and the native engine takes over.
</p>

<p class="post-p">
Feature detection:
</p>

<pre class="code-block"><code class="language-js">const supportsAnchor = CSS.supports('position-area', 'block-end center');
<p class="post-p">
// or
const supportsAnchor = CSS.supports('anchor-name', '--test');
</code></pre>
</p>

<h2 class="post-h2">What It Replaces</h2>

<p class="post-p">
CSS Anchor Positioning eliminates entire categories of JavaScript:
</p>

<p class="post-p">
| Old (JS library) | New (CSS) |
|---|---|
| Floating UI / Popper | <code class="inline-code">position-anchor</code> + <code class="inline-code">position-area</code> |
| <code class="inline-code">flip()</code> middleware | <code class="inline-code">@position-try</code> |
| <code class="inline-code">shift()</code> middleware | Viewport-aware by default |
| <code class="inline-code">size()</code> middleware | <code class="inline-code">anchor-size()</code> |
| <code class="inline-code">autoUpdate()</code> observer | Browser layout engine (automatic) |
| <code class="inline-code">computePosition()</code> | Browser layout engine (automatic) |
| <code class="inline-code">arrow()</code> middleware | <code class="inline-code">anchor()</code> function |
</p>

<p class="post-p">
This isn't just about fewer dependencies. Native anchor positioning runs during the browser's layout phase, which means:
</p>

<ul class="post-ul"><li class="post-li"><strong>No layout thrashing</strong> — The browser knows the final position before paint, no JS-measure-then-update cycles</li>
<li class="post-li"><strong>No scroll listeners</strong> — The browser tracks scroll offsets internally</li>
<li class="post-li"><strong>No ResizeObserver</strong> — The browser handles resize inherently</li>
<li class="post-li"><strong>Proper compositing</strong> — GPU-accelerated without explicit <code class="inline-code">will-change</code> hints</li>
</ul>

<h2 class="post-h2">Performance Implications</h2>

<p class="post-p">
We measured tooltip rendering with and without anchor positioning on a page with 200 tooltip targets:
</p>

<p class="post-p">
| Approach | Layout Time | JS Time | Total |
|---|---|---|---|
| Floating UI (JS) | 2.1ms | 18.7ms | 20.8ms |
| CSS Anchor Positioning | 3.4ms | 0ms | 3.4ms |
</p>

<p class="post-p">
The CSS approach does slightly more layout work (the browser evaluates all 200 position areas) but eliminates the 18.7ms of JavaScript computation entirely. For pages with many anchored elements — dropdown-heavy nav bars, data grids with tooltips — the savings compound.
</p>

<h2 class="post-h2">Common Pitfalls</h2>

<h3 class="post-h3">1. Forgetting <code class="inline-code">position: absolute</code> (or <code class="inline-code">fixed</code>)</h3>

<p class="post-p">
Anchor-positioned elements must have <code class="inline-code">position: absolute</code> or <code class="inline-code">position: fixed</code>. Popovers get <code class="inline-code">position: fixed</code> automatically by the UA stylesheet.
</p>

<h3 class="post-h3">2. Anchor name visibility</h3>

<p class="post-p">
An element can only anchor to another element in the same <strong>anchor scope</strong> — essentially the same containing block. If your anchor and positioned element are in different stacking contexts, the connection won't work.
</p>

<h3 class="post-h3">3. Over-anchoring</h3>

<p class="post-p">
If multiple elements share the same <code class="inline-code">anchor-name</code>, the last one in DOM order wins. Use unique names for each anchor-positioned-element pair:
</p>

<pre class="code-block"><code class="language-html">&amp;lt;!-- ❌ Don't do this — last anchor-name wins --&amp;gt;
<p class="post-p">
&amp;lt;button class="btn" style="anchor-name: --tip"&amp;gt;Btn 1&amp;lt;/button&amp;gt;
&amp;lt;button class="btn" style="anchor-name: --tip"&amp;gt;Btn 2&amp;lt;/button&amp;gt;
</p>

<p class="post-p">
&amp;lt;!-- ✅ Unique names per pair --&amp;gt;
&amp;lt;button class="btn" style="anchor-name: --tip-1"&amp;gt;Btn 1&amp;lt;/button&amp;gt;
&amp;lt;button class="btn" style="anchor-name: --tip-2"&amp;gt;Btn 2&amp;lt;/button&amp;gt;
</code></pre>
</p>

<h3 class="post-h3">4. <code class="inline-code">anchor()</code> with implicit anchors</h3>

<p class="post-p">
When using <code class="inline-code">anchor()</code>, you can reference the default anchor (the one set by <code class="inline-code">position-anchor</code>) or explicitly name one:
</p>

<pre class="code-block"><code class="language-css">.tooltip {
<p class="post-p">
position-anchor: --btn;
top: anchor(bottom);     /<em> Uses --btn (the default) </em>/
left: anchor(--other left); /<em> Explicitly references --other </em>/
}
</code></pre>
</p>

<h2 class="post-h2">The Future: <code class="inline-code">anchor-scope</code> and Inset-Area Shorthand</h2>

<p class="post-p">
The CSS Working Group is already iterating on the next generation of anchor positioning:
</p>

<ul class="post-ul"><li class="post-li"><strong><code class="inline-code">anchor-scope</code></strong> — Defines boundaries for anchor name resolution, so you can have anchors with the same name in different parts of the page without conflicts</li>
<li class="post-li"><strong>Inset-area shorthand</strong> — A shorter syntax for <code class="inline-code">position-area</code> that combines it with inset properties</li>
</ul>
<p class="post-p">
These are behind flags in Chrome Canary. The Baseline we have today is already production-ready.
</p>
