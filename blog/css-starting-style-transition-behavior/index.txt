<h2 class="post-h2">The Two Impossible CSS Animations</h2>

<p class="post-p">
Ask any frontend developer what CSS animation they've always wanted but couldn't have, and you'll get the same two answers:
</p>

<ul class="post-ul"><li class="post-li"><strong>Animating from <code class="inline-code">display: none</code></strong> — you want a dialog to fade in when it opens, but <code class="inline-code">display</code> can't animate and <code class="inline-code">visibility: hidden</code> still takes up space</li>
<li class="post-li"><strong>Animating to <code class="inline-code">height: auto</code></strong> — you want an accordion to smoothly expand, but you can only animate to explicit pixel values</li>
</ul>
<p class="post-p">
Until 2024, the answer was always "use JavaScript." You'd measure heights with <code class="inline-code">getBoundingClientRect()</code>, toggle classes after <code class="inline-code">requestAnimationFrame()</code>, or reach for a library. In 2026, the browser handles both natively. Here's how.
</p>

<h2 class="post-h2">The Three Primitives</h2>

<p class="post-p">
Three new CSS features work together to make this possible:
</p>

<p class="post-p">
| Feature | What It Solves | Baseline Since |
|---------|---------------|----------------|
| <code class="inline-code">@starting-style</code> | Defines initial state for entry transitions | Chrome 117, Safari 18, Firefox 129 |
| <code class="inline-code">transition-behavior: allow-discrete</code> | Enables transitions on discrete properties (like <code class="inline-code">display</code>) | Chrome 117, Safari 18, Firefox 129 |
| <code class="inline-code">interpolate-size: allow-keywords</code> | Enables interpolation to/from <code class="inline-code">auto</code> and intrinsic sizes | Chrome 129, Safari 18, Firefox 133 |
</p>

<p class="post-p">
All three are now cross-browser Baseline. Let's take them one at a time.
</p>

<h2 class="post-h2">@starting-style: Entry Animations From Nothing</h2>

<p class="post-p">
The problem: CSS transitions need a <em>before</em> state and an <em>after</em> state. When an element goes from <code class="inline-code">display: none</code> to <code class="inline-code">display: block</code>, the browser has no "before" state to transition from — it just appears.
</p>

<p class="post-p">
<code class="inline-code">@starting-style</code> gives you that before state:
</p>

<pre class="code-block"><code class="language-css">.popover {
<p class="post-p">
opacity: 1;
transform: scale(1);
transition: opacity 0.2s, transform 0.2s;
}
</p>

<p class="post-p">
/<em> This runs only during the FIRST frame the element exists </em>/
@starting-style {
.popover {
opacity: 0;
transform: scale(0.95);
}
}
</code></pre>
</p>

<p class="post-p">
That's it. When the <code class="inline-code">.popover</code> appears (via changing <code class="inline-code">display</code> or inserting into the DOM), it starts at <code class="inline-code">opacity: 0; transform: scale(0.95)</code> and transitions to <code class="inline-code">opacity: 1; transform: scale(1)</code>. This works for <strong>exit animations</strong> too with regular transitions in reverse.
</p>

<h3 class="post-h3">Real Pattern: Dialog Entry</h3>

<pre class="code-block"><code class="language-css">dialog[open] {
<p class="post-p">
opacity: 1;
transform: translateY(0) scale(1);
transition:
opacity 0.2s ease-out,
transform 0.2s ease-out,
overlay 0.2s ease-out allow-discrete,
display 0.2s ease-out allow-discrete;
}
</p>

<p class="post-p">
@starting-style {
dialog[open] {
opacity: 0;
transform: translateY(10px) scale(0.97);
}
}
</code></pre>
</p>

<p class="post-p">
<strong>Wait — what's <code class="inline-code">allow-discrete</code> doing there?</strong> Let's get to that.
</p>

<h2 class="post-h2">transition-behavior: Making display Animatable</h2>

<p class="post-p">
Normally, <code class="inline-code">display</code> and <code class="inline-code">content-visibility</code> are <strong>discrete</strong> properties — they have no intermediate states. You can't be "halfway between block and none." So CSS transitions skip them entirely — the property changes at the <em>end</em> of the transition duration.
</p>

<p class="post-p">
<code class="inline-code">transition-behavior: allow-discrete</code> tells the browser: "Transition this discrete property at the boundary of the animation — apply it at the <strong>start</strong> (for entry) or <strong>end</strong> (for exit) of the transition instead."
</p>

<pre class="code-block"><code class="language-css">.tooltip {
<p class="post-p">
opacity: 1;
transform: translateY(0);
transition:
opacity 0.15s ease-out,
transform 0.15s ease-out,
/<em> display animates at the START — element becomes 'block' first, then fades in </em>/
display 0.15s ease-out allow-discrete;
}
</p>

<p class="post-p">
.tooltip[hidden],
.tooltip:not(.visible) {
opacity: 0;
transform: translateY(4px);
/<em> display becomes 'none' at the END — fades out first, then disappears </em>/
display: none;
}
</p>

<p class="post-p">
@starting-style {
.tooltip:not([hidden]),
.tooltip.visible {
opacity: 0;
transform: translateY(4px);
}
}
</code></pre>
</p>

<p class="post-p">
The <code class="inline-code">0.15s</code> duration on <code class="inline-code">display</code> sets the timing boundary. For entry: <code class="inline-code">display: block</code> at frame 0, then the visual properties animate over 0.15s. For exit: visual properties animate over 0.15s, then <code class="inline-code">display: none</code> at the very end.
</p>

<h3 class="post-h3">The overlay Property</h3>

<p class="post-p">
<code class="inline-code">dialog</code> and <code class="inline-code">popover</code> elements have an additional discrete property: <code class="inline-code">overlay</code>. Without <code class="inline-code">allow-discrete</code> on <code class="inline-code">overlay</code>, a closing dialog sits in the top layer until the very last frame, blocking clicks.
</p>

<pre class="code-block"><code class="language-css">dialog {
<p class="post-p">
transition:
opacity 0.3s,
transform 0.3s,
overlay 0.3s allow-discrete,
display 0.3s allow-discrete;
}
</code></pre>
</p>

<p class="post-p">
Always pair <code class="inline-code">overlay</code> with <code class="inline-code">display</code> when animating dialogs and popovers.
</p>

<h2 class="post-h2">interpolate-size: The Height:auto Holy Grail</h2>

<p class="post-p">
This is the one developers have wanted for 20 years:
</p>

<pre class="code-block"><code class="language-css">details::details-content {
<p class="post-p">
height: 0;
overflow: hidden;
transition: height 0.3s ease;
interpolate-size: allow-keywords;  /<em> ← THE MAGIC LINE </em>/
}
</p>

<p class="post-p">
details[open]::details-content {
height: auto;  /<em> ← YES, AUTO. It actually works. </em>/
}
</code></pre>
</p>

<p class="post-p">
That <code class="inline-code">interpolate-size: allow-keywords</code> one-liner tells the browser: "When interpolating sizing properties, treat <code class="inline-code">auto</code>, <code class="inline-code">min-content</code>, <code class="inline-code">max-content</code>, and <code class="inline-code">fit-content</code> as numeric values." The browser calculates the actual pixel value of <code class="inline-code">auto</code> and animates to it.
</p>

<h3 class="post-h3">Complete Accordion Pattern</h3>

<pre class="code-block"><code class="language-html">&amp;lt;details name="faq"&amp;gt;
<p class="post-p">
&amp;lt;summary&amp;gt;What is DevBench?&amp;lt;/summary&amp;gt;
&amp;lt;div class="accordion-content"&amp;gt;
DevBench is a collection of free developer tools — no sign-up, no ads.
&amp;lt;/div&amp;gt;
&amp;lt;/details&amp;gt;
</code></pre>
</p>

<pre class="code-block"><code class="language-css">/<em> Progressive enhancement — only animate if supported </em>/
<p class="post-p">
@supports (interpolate-size: allow-keywords) {
details .accordion-content {
height: 0;
overflow: hidden;
transition: height 0.35s ease;
interpolate-size: allow-keywords;
}
</p>

<p class="post-p">
details[open] .accordion-content {
height: auto;
}
}
</code></pre>
</p>

<p class="post-p">
The <code class="inline-code">@supports</code> guard means unsupported browsers get the instant toggle — which is fine, they've been fine with it for 20 years.
</p>

<h3 class="post-h3">The Exclusive Accordion</h3>

<p class="post-p">
With the <code class="inline-code">name</code> attribute on <code class="inline-code">&lt;details&gt;</code>, browsers now support exclusive accordions natively (open one, others close). Combined with <code class="inline-code">interpolate-size</code>:
</p>

<pre class="code-block"><code class="language-html">&amp;lt;details name="faq-section"&amp;gt;
<p class="post-p">
&amp;lt;summary&amp;gt;Question 1&amp;lt;/summary&amp;gt;
&amp;lt;p&amp;gt;Answer 1&amp;lt;/p&amp;gt;
&amp;lt;/details&amp;gt;
&amp;lt;details name="faq-section"&amp;gt;
&amp;lt;summary&amp;gt;Question 2&amp;lt;/summary&amp;gt;
&amp;lt;p&amp;gt;Answer 2&amp;lt;/p&amp;gt;
&amp;lt;/details&amp;gt;
</code></pre>
</p>

<p class="post-p">
No JavaScript. The <code class="inline-code">name</code> attribute groups them and the CSS handles the animation. This is production-ready in all modern browsers.
</p>

<h2 class="post-h2">calc-size(): When You Need Math In Your Animation</h2>

<p class="post-p">
<code class="inline-code">interpolate-size</code> handles <code class="inline-code">auto</code> ↔ numeric, but what if you need calculations during the animation? Enter <code class="inline-code">calc-size()</code>:
</p>

<pre class="code-block"><code class="language-css">.slide-panel {
<p class="post-p">
width: 0;
overflow: hidden;
transition: width 0.3s ease;
interpolate-size: allow-keywords;
}
</p>

<p class="post-p">
.slide-panel.open {
/<em> 100% of the auto width, minus 2rem </em>/
width: calc-size(auto, size - 2rem);
}
</code></pre>
</p>

<p class="post-p">
The <code class="inline-code">size</code> keyword inside <code class="inline-code">calc-size()</code> represents the <code class="inline-code">auto</code> value. You can do: <code class="inline-code">calc-size(fit-content, size * 0.8)</code>, <code class="inline-code">calc-size(auto, size + 20px)</code>, etc.
</p>

<h2 class="post-h2">Putting It All Together: A Notification Toast</h2>

<p class="post-p">
Here's a complete pattern combining all three primitives:
</p>

<pre class="code-block"><code class="language-css">.notification {
<p class="post-p">
position: fixed;
bottom: 1rem;
right: 1rem;
</p>

<p class="post-p">
/<em> Visible state </em>/
opacity: 1;
transform: translateY(0);
max-height: 200px;
</p>

<p class="post-p">
transition:
opacity 0.3s ease,
transform 0.3s ease,
max-height 0.3s ease;
interpolate-size: allow-keywords;
}
</p>

<p class="post-p">
/<em> Hidden state — remove from layout </em>/
.notification.dismissed {
opacity: 0;
transform: translateY(100%);
max-height: 0;
margin: 0;
padding-top: 0;
padding-bottom: 0;
/<em> display animates at the end so it fades out first </em>/
transition:
opacity 0.25s ease,
transform 0.25s ease,
max-height 0.25s ease,
margin 0.25s ease,
padding 0.25s ease,
display 0.25s ease allow-discrete;
display: none;
}
</p>

<p class="post-p">
@starting-style {
.notification:not(.dismissed) {
opacity: 0;
transform: translateY(100%);
max-height: 0;
}
}
</code></pre>
</p>

<h2 class="post-h2">Performance Considerations</h2>

<p class="post-p">
These features are implemented at the compositor level — they don't trigger layout during animation frames (unlike the JavaScript <code class="inline-code">getBoundingClientRect()</code> approach). However:
</p>

<ul class="post-ul"><li class="post-li"><strong><code class="inline-code">height</code> animations still trigger layout</strong> on every frame. Prefer <code class="inline-code">transform: scaleY()</code> + a wrapper with <code class="inline-code">overflow: hidden</code> for pure-compositor performance in complex layouts.</li>
<li class="post-li"><strong><code class="inline-code">interpolate-size</code> calculates the <code class="inline-code">auto</code> value once</strong> at transition start. If content changes mid-transition, the target size won't update until the next transition.</li>
<li class="post-li"><strong>Nested accordions work fine</strong> — each <code class="inline-code">details</code> element gets its own <code class="inline-code">interpolate-size</code> context.</li>
<li class="post-li"><strong><code class="inline-code">display: none</code> transitions with <code class="inline-code">allow-discrete</code> are instant</strong> — the transition duration only controls <em>when</em> in the sequence the discrete change happens, not a gradual change in <code class="inline-code">display</code> itself (which is impossible).</li>
</ul>

<h2 class="post-h2">Migration: Drop the JavaScript</h2>

<p class="post-p">
Here's what you can delete:
</p>

<p class="post-p">
<strong>Before (JavaScript accordion):</strong>
</p>
<pre class="code-block"><code class="language-javascript">accordion.addEventListener('click', () =&amp;gt; {
<p class="post-p">
const content = accordion.nextElementSibling;
content.style.height = content.scrollHeight + 'px';
// ... RAF, transitionend cleanup, resize observer ...
});
</code></pre>
</p>

<p class="post-p">
<strong>After (CSS only):</strong>
</p>
<pre class="code-block"><code class="language-css">details::details-content {
<p class="post-p">
height: 0;
overflow: hidden;
transition: height 0.3s;
interpolate-size: allow-keywords;
}
details[open]::details-content {
height: auto;
}
</code></pre>
</p>

<p class="post-p">
Two CSS rules replace ~30 lines of JavaScript. No resize observer, no RAF orchestration, no cleanup.
</p>
