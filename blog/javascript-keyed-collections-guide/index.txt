<h2 class="post-h2">The Object-as-Dictionary Problem</h2>

<p class="post-p">
Ask any JavaScript developer how to store key-value pairs, and 95% will reach for a plain object:
</p>

<pre class="code-block"><code class="language-js">const cache = {};
<p class="post-p">
cache['user:1234'] = { name: 'Ada' };
cache['user:5678'] = { name: 'Grace' };
</code></pre>
</p>

<p class="post-p">
This works — until it doesn't. Plain objects come with a long list of footguns:
</p>

<ul class="post-ul"><li class="post-li"><strong>String-only keys.</strong> <code class="inline-code">cache[obj]</code> coerces the object to <code class="inline-code">"[object Object]"</code> — every key becomes identical.</li>
<li class="post-li"><strong>Prototype pollution.</strong> <code class="inline-code">cache['toString']</code> doesn't behave like a normal key.</li>
<li class="post-li"><strong>No size tracking.</strong> You need <code class="inline-code">Object.keys(cache).length</code> — O(n) every time.</li>
<li class="post-li"><strong>No iteration order guarantee.</strong> (Technically there is one now, but it's complex and fragile.)</li>
<li class="post-li"><strong>No built-in clear().</strong> You have to reassign or delete every key individually.</li>
<li class="post-li"><strong>Keys collide with inherited properties.</strong> <code class="inline-code">__proto__</code>, <code class="inline-code">constructor</code>, and <code class="inline-code">toString</code> all have special behavior.</li>
</ul>
<p class="post-p">
JavaScript has had first-class solutions for all of these problems since ES6 (2015). In 2026, every browser and runtime supports them natively, yet most developers still reach for <code class="inline-code">{}</code> by default.
</p>

<p class="post-p">
Here's the definitive guide to all four keyed collections — with real-world patterns you can use today.
</p>

<hr class="post-hr" />

<h2 class="post-h2">Map: The Real Hash Map</h2>

<p class="post-p">
<code class="inline-code">Map</code> is the direct replacement for using objects as dictionaries. It supports <strong>any type as keys</strong>, preserves insertion order, and has a proper API.
</p>

<h3 class="post-h3">Creating Maps</h3>

<pre class="code-block"><code class="language-js">// Empty map
<p class="post-p">
const map = new Map();
</p>

<p class="post-p">
// From iterable of [key, value] pairs
const map = new Map([
['name', 'Ada'],
['role', 'engineer'],
[42, 'the answer'],
[{ id: 1 }, 'object key'],
]);
</p>

<p class="post-p">
// From Object.entries()
const config = { theme: 'dark', fontSize: 14 };
const configMap = new Map(Object.entries(config));
</code></pre>
</p>

<h3 class="post-h3">Core API</h3>

<pre class="code-block"><code class="language-js">const users = new Map();

<p class="post-p">
// Set — returns the Map (chainable)
users.set('u1', { name: 'Ada', role: 'admin' });
users.set('u2', { name: 'Grace', role: 'editor' });
</p>

<p class="post-p">
// Get
users.get('u1'); // { name: 'Ada', role: 'admin' }
users.get('u3'); // undefined
</p>

<p class="post-p">
// Has (faster than checking undefined — keys CAN be undefined)
users.set('u3', undefined);
users.has('u3'); // true
users.get('u3'); // undefined — has() is the only reliable check
</p>

<p class="post-p">
// Size — O(1)
users.size; // 3
</p>

<p class="post-p">
// Delete
users.delete('u3'); // true
users.delete('u99'); // false (key doesn't exist)
</p>

<p class="post-p">
// Clear
users.clear();
users.size; // 0
</code></pre>
</p>

<h3 class="post-h3">Iteration</h3>

<p class="post-p">
Maps preserve insertion order and are directly iterable:
</p>

<pre class="code-block"><code class="language-js">const scores = new Map([
<p class="post-p">
['Alice', 95],
['Bob', 82],
['Charlie', 88],
]);
</p>

<p class="post-p">
// forEach
scores.forEach((value, key) =&amp;gt; {
console.log(<code class="inline-code">${key}: ${value}</code>);
});
</p>

<p class="post-p">
// for...of — iterates [key, value] pairs by default
for (const [name, score] of scores) {
console.log(<code class="inline-code">${name} scored ${score}</code>);
}
</p>

<p class="post-p">
// keys(), values(), entries()
[...scores.keys()];     // ['Alice', 'Bob', 'Charlie']
[...scores.values()];   // [95, 82, 88]
[...scores.entries()];  // [['Alice', 95], ['Bob', 82], ['Charlie', 88]]
</code></pre>
</p>

<h3 class="post-h3">Any-Type Keys</h3>

<p class="post-p">
This is the killer feature — keys can be anything, not just strings:
</p>

<pre class="code-block"><code class="language-js">const metadata = new Map();
<p class="post-p">
const user = { id: 1 };
const role = Symbol('admin');
</p>

<p class="post-p">
metadata.set(user, { lastLogin: Date.now() });
metadata.set(role, ['write', 'delete']);
metadata.set(NaN, 'NaN key');   // NaN === NaN is false, but Map uses SameValueZero
metadata.set(0, 'zero');
metadata.set(-0, 'negative zero'); // 0 and -0 ARE the same key in Map (SameValueZero)
</p>

<p class="post-p">
metadata.get(user); // { lastLogin: ... }
metadata.get(NaN);  // 'NaN key'
metadata.get(0);    // 'negative zero' — overwritten
metadata.get(-0);   // 'negative zero'
</code></pre>
</p>

<h3 class="post-h3">Real-World Use Case: LRU Cache</h3>

<pre class="code-block"><code class="language-js">class LRUCache {
<p class="post-p">
#capacity;
#map = new Map();
</p>

<p class="post-p">
constructor(capacity) {
this.#capacity = capacity;
}
</p>

<p class="post-p">
get(key) {
if (!this.#map.has(key)) return -1;
const value = this.#map.get(key);
// Move to end (most recently used) by re-inserting
this.#map.delete(key);
this.#map.set(key, value);
return value;
}
</p>

<p class="post-p">
put(key, value) {
if (this.#map.has(key)) {
this.#map.delete(key);
} else if (this.#map.size &amp;gt;= this.#capacity) {
// Map.keys() returns in insertion order — first key is LRU
const lru = this.#map.keys().next().value;
this.#map.delete(lru);
}
this.#map.set(key, value);
}
}
</code></pre>
</p>

<p class="post-p">
This is cleaner and faster than any object-based LRU implementation. <code class="inline-code">Map.keys().next()</code> gives us O(1) access to the least recently used key.
</p>

<h3 class="post-h3">Real-World Use Case: Event Delegation Metadata</h3>

<pre class="code-block"><code class="language-js">const listeners = new Map();

<p class="post-p">
function addDelegateListener(container, selector, event, handler) {
const wrapper = (e) =&amp;gt; {
const target = e.target.closest(selector);
if (target &amp;amp;&amp;amp; container.contains(target)) {
handler.call(target, e);
}
};
container.addEventListener(event, wrapper);
</p>

<p class="post-p">
// Store handler→wrapper mapping for cleanup
if (!listeners.has(handler)) {
listeners.set(handler, new Map());
}
listeners.get(handler).set(container, { event, wrapper });
}
</p>

<p class="post-p">
function removeDelegateListener(handler) {
const containers = listeners.get(handler);
if (!containers) return;
for (const [container, { event, wrapper }] of containers) {
container.removeEventListener(event, wrapper);
}
listeners.delete(handler);
}
</code></pre>
</p>

<h3 class="post-h3">Map vs Object: When to Use Which</h3>

<p class="post-p">
| Feature | Map | Object |
|---------|-----|--------|
| Key types | Any value | String or Symbol only |
| Size | <code class="inline-code">.size</code> — O(1) | <code class="inline-code">Object.keys().length</code> — O(n) |
| Iteration | Directly iterable | <code class="inline-code">Object.entries()</code> |
| Insertion order | Guaranteed | Mostly guaranteed (complex) |
| Default keys | None | Prototype chain |
| JSON serializable | No | Yes |
| Performance (frequent adds/deletes) | Better | Worse |
| Performance (static, string-keyed lookup) | Comparable | Slightly faster in some engines |
</p>

<p class="post-p">
<strong>Rule of thumb:</strong> Use <code class="inline-code">Map</code> when keys are dynamic, unknown, or non-string. Use plain objects for static, known, string-keyed data that needs JSON serialization (e.g., config objects, API payloads, React state).
</p>

<h2 class="post-h2">Set: The Deduped Collection</h2>

<p class="post-p">
<code class="inline-code">Set</code> stores unique values of any type. Think of it as an array that automatically deduplicates.
</p>

<h3 class="post-h3">Core API</h3>

<pre class="code-block"><code class="language-js">const tags = new Set();

<p class="post-p">
tags.add('javascript');
tags.add('typescript');
tags.add('javascript'); // No-op — already exists
tags.add('css');
</p>

<p class="post-p">
tags.has('javascript'); // true
tags.size;              // 3
tags.delete('css');     // true
tags.clear();
</code></pre>
</p>

<h3 class="post-h3">Iteration</h3>

<pre class="code-block"><code class="language-js">const ids = new Set(['a', 'b', 'c']);

<p class="post-p">
for (const id of ids) {
console.log(id);
}
</p>

<p class="post-p">
ids.forEach(id =&amp;gt; console.log(id));
</p>

<p class="post-p">
// values() and keys() are identical for Set
[...ids.values()]; // ['a', 'b', 'c']
[...ids.keys()];   // ['a', 'b', 'c']
[...ids.entries()]; // [['a', 'a'], ['b', 'b'], ['c', 'c']] — [value, value] pairs
</code></pre>
</p>

<h3 class="post-h3">Creating Sets from Arrays</h3>

<pre class="code-block"><code class="language-js">// Deduplicate an array
<p class="post-p">
const arr = [1, 2, 2, 3, 3, 3, 4];
const unique = [...new Set(arr)]; // [1, 2, 3, 4]
</code></pre>
</p>

<h3 class="post-h3">Set Operations (Union, Intersection, Difference)</h3>

<p class="post-p">
ES2025 added native set operations — but there's a zero-dependency approach that works everywhere:
</p>

<pre class="code-block"><code class="language-js">const a = new Set([1, 2, 3, 4]);
<p class="post-p">
const b = new Set([3, 4, 5, 6]);
</p>

<p class="post-p">
// Union: all unique elements from both
const union = new Set([...a, ...b]);        // {1, 2, 3, 4, 5, 6}
</p>

<p class="post-p">
// Intersection: elements in both
const intersection = new Set([...a].filter(x =&amp;gt; b.has(x))); // {3, 4}
</p>

<p class="post-p">
// Difference: elements in a but not in b
const difference = new Set([...a].filter(x =&amp;gt; !b.has(x)));  // {1, 2}
</p>

<p class="post-p">
// Symmetric difference: elements in either but not both
const symDiff = new Set(
[...a].filter(x =&amp;gt; !b.has(x)).concat([...b].filter(x =&amp;gt; !a.has(x)))
); // {1, 2, 5, 6}
</p>

<p class="post-p">
// Subset: is a a subset of b?
const isSubset = [...a].every(x =&amp;gt; b.has(x)); // false
</p>

<p class="post-p">
// Superset: is a a superset of b?
const isSuperset = [...b].every(x =&amp;gt; a.has(x)); // false
</code></pre>
</p>

<h3 class="post-h3">Real-World Use Case: Tracking Active Connections</h3>

<pre class="code-block"><code class="language-js">class ConnectionPool {
<p class="post-p">
#connections = new Set();
</p>

<p class="post-p">
connect(socket) {
this.#connections.add(socket);
console.log(<code class="inline-code">Active connections: ${this.#connections.size}</code>);
}
</p>

<p class="post-p">
disconnect(socket) {
this.#connections.delete(socket);
console.log(<code class="inline-code">Active connections: ${this.#connections.size}</code>);
}
</p>

<p class="post-p">
broadcast(data) {
for (const socket of this.#connections) {
socket.send(data);
}
}
</p>

<p class="post-p">
get activeCount() {
return this.#connections.size;
}
}
</code></pre>
</p>

<h3 class="post-h3">Real-World Use Case: Visited State Tracker</h3>

<pre class="code-block"><code class="language-js">const visitedNodes = new Set();

<p class="post-p">
function traverse(node) {
if (visitedNodes.has(node)) return;
visitedNodes.add(node);
</p>

<p class="post-p">
// Process node...
for (const child of node.children) {
traverse(child);
}
}
</code></pre>
</p>

<p class="post-p">
For graph traversal (DFS/BFS), <code class="inline-code">Set</code> is dramatically clearer than array-based visited tracking and avoids the O(n) <code class="inline-code">includes()</code> check.
</p>

<h2 class="post-h2">WeakMap: Garbage-Collectable Key-Value Store</h2>

<p class="post-p">
<code class="inline-code">WeakMap</code> is like <code class="inline-code">Map</code> but with one crucial difference: <strong>keys are weakly referenced</strong>. If nothing else references a key object, it can be garbage collected, and its entry is automatically removed from the WeakMap.
</p>

<h3 class="post-h3">Constraints</h3>

<ul class="post-ul"><li class="post-li">Keys MUST be objects (not primitives)</li>
<li class="post-li">WeakMaps are NOT iterable (no <code class="inline-code">forEach</code>, no <code class="inline-code">keys()</code>, no <code class="inline-code">size</code>)</li>
<li class="post-li">No <code class="inline-code">clear()</code> method (entries clear automatically via GC)</li>
</ul>
<h3 class="post-h3">Why Would You Want That?</h3>

<p class="post-p">
The canonical use case is <strong>private data associated with DOM nodes</strong>:
</p>

<pre class="code-block"><code class="language-js">const elementData = new WeakMap();

<p class="post-p">
function setupTooltip(el, content) {
elementData.set(el, { content, shown: false });
</p>

<p class="post-p">
el.addEventListener('mouseenter', () =&amp;gt; {
const data = elementData.get(el);
if (!data.shown) {
showTooltip(el, data.content);
data.shown = true;
}
});
}
</p>

<p class="post-p">
// When the element is removed from the DOM and no longer referenced,
// both the element and its associated data are garbage collected.
// No cleanup code needed. No memory leak.
</code></pre>
</p>

<p class="post-p">
With a <code class="inline-code">Map</code>, you'd have to manually delete entries when elements are removed — or leak memory. With <code class="inline-code">WeakMap</code>, the garbage collector handles it automatically.
</p>

<h3 class="post-h3">Real-World Use Case: True Private Instance Data</h3>

<p class="post-p">
Before private class fields (<code class="inline-code">#field</code>), WeakMap was the standard way to achieve truly private instance data:
</p>

<pre class="code-block"><code class="language-js">const _private = new WeakMap();

<p class="post-p">
class BankAccount {
constructor(owner, balance) {
_private.set(this, { owner, balance });
}
</p>

<p class="post-p">
get balance() {
return _private.get(this).balance;
}
</p>

<p class="post-p">
deposit(amount) {
const data = _private.get(this);
data.balance += amount;
return data.balance;
}
</p>

<p class="post-p">
withdraw(amount) {
const data = _private.get(this);
if (amount &amp;gt; data.balance) throw new Error('Insufficient funds');
data.balance -= amount;
return data.balance;
}
</p>

<p class="post-p">
// owner is truly inaccessible from outside
}
</code></pre>
</p>

<p class="post-p">
In 2026, <code class="inline-code">#privateFields</code> are preferred for this (they're syntactic sugar and slightly faster), but WeakMap-based privacy is still valuable when you need to share private state across multiple classes or between a class and its mixins.
</p>

<h3 class="post-h3">Real-World Use Case: Caching Computed Values</h3>

<pre class="code-block"><code class="language-js">const computedCache = new WeakMap();

<p class="post-p">
function getExpensiveComputation(obj) {
if (computedCache.has(obj)) {
return computedCache.get(obj);
}
const result = /<em> expensive computation using obj </em>/;
computedCache.set(obj, result);
return result;
}
</p>

<p class="post-p">
// When obj is garbage collected, its cached result is automatically freed.
// No manual cache eviction needed.
</code></pre>
</p>

<p class="post-p">
This pattern is used by libraries like Zod, Valibot, and React's internal hooks system. It's the most memory-efficient caching pattern in JavaScript.
</p>

<h3 class="post-h3">WeakMap vs Private Fields: 2026 Guidance</h3>

<p class="post-p">
| Feature | WeakMap | <code class="inline-code">#private</code> |
|---------|---------|------------|
| Syntax | Verbose setup | <code class="inline-code">this.#field</code> |
| Performance | Slightly slower | Faster (engine-optimized) |
| Cross-class sharing | ✅ Easy | ❌ Per-class |
| Dynamic key objects | ✅ Any object | Only <code class="inline-code">this</code> |
| Debugging | Harder to inspect | Visible in DevTools |
| Garbage collection | Automatic | Tied to instance lifecycle |
</p>

<p class="post-p">
<strong>Use <code class="inline-code">#private</code></strong> for class-specific private state. <strong>Use WeakMap</strong> when you need shared, cross-cutting private state, caching, or DOM metadata.
</p>

<h2 class="post-h2">WeakSet: Garbage-Collectable Membership Tracker</h2>

<p class="post-p">
<code class="inline-code">WeakSet</code> stores objects and, like WeakMap, holds them weakly. If nothing else references an object in a WeakSet, it gets garbage collected.
</p>

<h3 class="post-h3">Constraints</h3>

<ul class="post-ul"><li class="post-li">Values MUST be objects</li>
<li class="post-li">Not iterable (no <code class="inline-code">forEach</code>, no <code class="inline-code">size</code>)</li>
<li class="post-li">No <code class="inline-code">clear()</code></li>
</ul>
<h3 class="post-h3">Real-World Use Case: Branding / Tagging Objects</h3>

<pre class="code-block"><code class="language-js">const processedItems = new WeakSet();

<p class="post-p">
function processItem(item) {
if (processedItems.has(item)) {
console.log('Already processed, skipping');
return;
}
processedItems.add(item);
// ... expensive processing ...
}
</code></pre>
</p>

<h3 class="post-h3">Real-World Use Case: Circular Reference Detection</h3>

<pre class="code-block"><code class="language-js">const visiting = new WeakSet();

<p class="post-p">
function deepClone(obj) {
if (typeof obj !== 'object' || obj === null) return obj;
if (visiting.has(obj)) throw new Error('Circular reference detected');
</p>

<p class="post-p">
visiting.add(obj);
const clone = Array.isArray(obj) ? [] : {};
</p>

<p class="post-p">
for (const [key, value] of Object.entries(obj)) {
clone[key] = deepClone(value);
}
</p>

<p class="post-p">
visiting.delete(obj); // Allow object to appear multiple times in different branches
return clone;
}
</code></pre>
</p>

<h3 class="post-h3">Real-World Use Case: Preventing Double-Invocation of Callbacks</h3>

<pre class="code-block"><code class="language-js">const invoked = new WeakSet();

<p class="post-p">
function once(fn) {
return function (...args) {
if (invoked.has(fn)) return;
invoked.add(fn);
return fn.apply(this, args);
};
}
</p>

<p class="post-p">
const init = once(() =&amp;gt; console.log('Initialized'));
init(); // 'Initialized'
init(); // (silent no-op)
</code></pre>
</p>

<h2 class="post-h2">Performance: The Numbers</h2>

<p class="post-p">
Here's a rough performance comparison of common operations (relative, not absolute — exact numbers depend on the engine):
</p>

<p class="post-p">
| Operation | Performance |
|-----------|-------------|
| Map.set() vs Object assignment | Map is ~20% faster for frequent adds/deletes |
| Map.get() vs Object access | Comparable for string keys; Map wins for non-string keys |
| Set.has() vs Array.includes() | O(1) vs O(n) — Set wins massively for large collections |
| Set iteration | Comparable to array iteration |
| WeakMap memory | Zero leak-by-design; Map requires manual cleanup |
</p>

<p class="post-p">
<strong>The 100-element rule:</strong> For collections under ~100 elements, the difference is negligible. For anything larger, or any code that runs in a hot loop, <code class="inline-code">Map</code> and <code class="inline-code">Set</code> should be your defaults.
</p>

<h2 class="post-h2">Decision Flowchart</h2>

<pre class="code-block"><code class="language-text">Do you need key-value pairs?
<p class="post-p">
├── Keys are strings AND data needs JSON serialization?
│   └── Use Object
├── Keys are objects AND entries should auto-cleanup when keys are GC'd?
│   └── Use WeakMap
└── Otherwise?
└── Use Map
</p>

<p class="post-p">
Do you need a collection of unique values?
├── Values are objects AND membership should auto-cleanup when values are GC'd?
│   └── Use WeakSet
└── Otherwise?
└── Use Set
</code></pre>
</p>

<h2 class="post-h2">Common Mistakes</h2>

<h3 class="post-h3">1. Using <code class="inline-code">map.get(key)</code> to check existence</h3>

<pre class="code-block"><code class="language-js">// ❌ Wrong — breaks when value is undefined, 0, '', null, or false
<p class="post-p">
if (map.get(key)) { ... }
</p>

<p class="post-p">
// ✅ Correct
if (map.has(key)) { ... }
</code></pre>
</p>

<h3 class="post-h3">2. Expecting JSON.stringify to work</h3>

<pre class="code-block"><code class="language-js">const map = new Map([['a', 1]]);
<p class="post-p">
JSON.stringify(map); // '{}' — Map is not JSON-serializable
</p>

<p class="post-p">
// ✅ Convert first
JSON.stringify([...map]); // '[["a",1]]'
// Or
JSON.stringify(Object.fromEntries(map)); // '{"a":1}'
</code></pre>
</p>

<h3 class="post-h3">3. Using WeakMap with primitive keys</h3>

<pre class="code-block"><code class="language-js">const wm = new WeakMap();
<p class="post-p">
wm.set('hello', 'world'); // TypeError: Invalid value used as weak map key
</code></pre>
</p>

<h3 class="post-h3">4. Forgetting that Set only checks reference equality for objects</h3>

<pre class="code-block"><code class="language-js">const set = new Set();
<p class="post-p">
set.add({ id: 1 });
set.add({ id: 1 });
set.size; // 2 — different object references!
</code></pre>
</p>

<h3 class="post-h3">5. Overusing WeakMap for everything</h3>

<p class="post-p">
WeakMap is not a silver bullet. If you need iteration, size, or primitive keys, use Map. WeakMap is specifically for the "associate data with objects and auto-clean when they're GC'd" use case.
</p>

<hr class="post-hr" />

<h2 class="post-h2">The Bottom Line</h2>

<p class="post-p">
JavaScript's keyed collections aren't niche features — they're fundamental data structures that solve real problems:
</p>

<ul class="post-ul"><li class="post-li"><strong>Map</strong> replaces object-as-dictionary with better API, non-string keys, and O(1) size</li>
<li class="post-li"><strong>Set</strong> replaces array-for-uniqueness with O(1) has() and automatic deduplication</li>
<li class="post-li"><strong>WeakMap</strong> enables zero-leak private data and DOM metadata patterns</li>
<li class="post-li"><strong>WeakSet</strong> enables zero-leak membership tracking and branding</li>
</ul>
<p class="post-p">
In 2026, every JavaScript developer should reach for these before reaching for <code class="inline-code">{}</code> or <code class="inline-code">[]</code> for collection use cases. The APIs are ergonomic, the performance is better, and the intent is clearer.
</p>

<p class="post-p">
Stop using objects for everything. Your future self (and your garbage collector) will thank you.
</p>
