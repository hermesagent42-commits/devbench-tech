<p class="post-p">
For two decades, CSS developers asked for a <strong>parent selector</strong> — a way to style an element based on what it <em>contains</em>. In 2023, we got it. And by late 2025, <code class="inline-code">:has()</code> reached Baseline — supported in every major browser, covering ~94% of global users.
</p>

<p class="post-p">
But <code class="inline-code">:has()</code> is much more than a parent selector. It's a <strong>relational selector</strong> that lets you style any element based on any of its descendants, siblings, or state. It unlocks patterns that used to require JavaScript — or were simply impossible in CSS.
</p>

<p class="post-p">
Let's dive deep.
</p>

<h2 class="post-h2">What <code class="inline-code">:has()</code> Actually Does</h2>

<p class="post-p">
<code class="inline-code">:has()</code> is a functional pseudo-class that takes a <strong>selector list</strong> as its argument. It matches an element if any of the relative selectors in that list match at least one element.
</p>

<pre class="code-block"><code class="language-css">/<em> "Select any .card that contains an img" </em>/
<p class="post-p">
.card:has(img) {
grid-column: span 2;
}
</p>

<p class="post-p">
/<em> "Select any li that contains a ul (a sublist)" </em>/
li:has(&amp;gt; ul) {
list-style: none;
}
</p>

<p class="post-p">
/<em> "Select a form that contains an invalid input" </em>/
form:has(:invalid) {
border-left: 4px solid #ef4444;
}
</code></pre>
</p>

<p class="post-p">
The argument is a <strong>relative selector</strong> — it's scoped to the element you're checking. The <code class="inline-code">:has()</code> itself doesn't change which element gets styled; it changes <em>whether</em> it gets styled.
</p>

<h2 class="post-h2">The Classic: Parent Selector</h2>

<p class="post-p">
The most requested use case — style a parent based on its child:
</p>

<pre class="code-block"><code class="language-css">/<em> A card that contains an image gets a two-column layout </em>/
<p class="post-p">
.card:has(img) {
display: grid;
grid-template-columns: 200px 1fr;
gap: 1.5rem;
}
</p>

<p class="post-p">
/<em> A nav item that has a dropdown gets a chevron </em>/
.nav-item:has(&amp;gt; .dropdown)::after {
content: ' ▾';
font-size: 0.7rem;
}
</code></pre>
</p>

<p class="post-p">
Without <code class="inline-code">:has()</code>, you'd need JavaScript to toggle a class on the parent. Now it's a single CSS rule.
</p>

<h2 class="post-h2">Previous Sibling Selector</h2>

<p class="post-p">
This is the one that blows people's minds. CSS has always had <code class="inline-code">+</code> (next sibling) but never "previous sibling." With <code class="inline-code">:has()</code>, you can:
</p>

<pre class="code-block"><code class="language-css">/<em> When a checkbox is checked, style the label BEFORE it </em>/
<p class="post-p">
label:has(+ input:checked) {
color: #6366f1;
font-weight: 600;
}
</p>

<p class="post-p">
/<em> Style all items BEFORE the active one differently </em>/
.item:has(+ .item.active) {
opacity: 0.6;
}
</code></pre>
</p>

<p class="post-p">
This is a game-changer for custom form controls, navigation, and any UI where "the thing before the active thing" matters.
</p>

<h2 class="post-h2">Real-World Patterns</h2>

<h3 class="post-h3">Pattern 1: Form Validation States</h3>

<p class="post-p">
This is where <code class="inline-code">:has()</code> shines brightest. Style the entire form — or individual field groups — based on the validity of their inputs:
</p>

<pre class="code-block"><code class="language-css">/<em> Highlight the entire form when any field is invalid </em>/
<p class="post-p">
form:has(:user-invalid) {
--form-border: #ef4444;
}
</p>

<p class="post-p">
/<em> Show a submit button only when all required fields are filled </em>/
form:has(:required:valid) button[type="submit"] {
opacity: 1;
pointer-events: auto;
}
</p>

<p class="post-p">
/<em> Style a field group with an error state </em>/
.field-group:has(:user-invalid) {
border-left: 3px solid #ef4444;
padding-left: 1rem;
background: rgba(239, 68, 68, 0.05);
}
</p>

<p class="post-p">
/<em> Show error message only when the associated input is invalid </em>/
.field-group:has(:user-invalid) .error-message {
display: block;
}
</p>

<p class="post-p">
/<em> Style the password field differently when it passes validation </em>/
.field-group:has(input[type="password"]:valid) .strength-indicator {
background: #22c55e;
}
</code></pre>
</p>

<p class="post-p">
No JavaScript. No class toggling. Pure CSS form validation feedback.
</p>

<h3 class="post-h3">Pattern 2: Card Layout Adaptation</h3>

<p class="post-p">
Make your card layouts responsive to their <em>content</em>, not just the viewport:
</p>

<pre class="code-block"><code class="language-css">/<em> Cards with images get a horizontal layout </em>/
<p class="post-p">
.product-card:has(img) {
display: grid;
grid-template-columns: 180px 1fr;
gap: 1rem;
}
</p>

<p class="post-p">
/<em> Cards without images stay vertical </em>/
.product-card:not(:has(img)) {
display: flex;
flex-direction: column;
}
</p>

<p class="post-p">
/<em> A featured card with a badge gets extra prominence </em>/
.product-card:has(.badge--featured) {
box-shadow: 0 0 0 2px #6366f1, 0 4px 20px rgba(99, 102, 241, 0.3);
}
</p>

<p class="post-p">
/<em> Card with multiple tags gets a scrollable tag area </em>/
.product-card:has(.tag:nth-child(4)) .tags-container {
overflow-x: auto;
mask-image: linear-gradient(to right, black 80%, transparent);
}
</code></pre>
</p>

<p class="post-p">
Content-aware layouts. No media queries. No container queries. Just the structure of the content deciding the layout.
</p>

<h3 class="post-h3">Pattern 3: Navigation States</h3>

<pre class="code-block"><code class="language-css">/<em> Highlight the current nav section </em>/
<p class="post-p">

/<em> We know we're on a page with active nav </em>/

</p>

<p class="post-p">
.nav-item:has([aria-current="page"]) {

}
</p>

<p class="post-p">
/<em> Breadcrumb with more than 3 items gets truncated </em>/
.breadcrumb:has(&amp;gt; li:nth-child(4)) {
/<em> Enable truncation mode </em>/
--truncate-breadcrumbs: 1;

</code></pre>
</p>

<h3 class="post-h3">Pattern 4: Interactive Components</h3>

<h3 class="post-h3">Pattern 5: Empty States and Edge Cases</h3>

<pre class="code-block"><code class="language-css">/<em> A list with no items gets an empty state </em>/
<p class="post-p">
.list-container:has(&amp;gt; :not(.empty-state)) {
/<em> The list has items — hide the empty state </em>/

<p class="post-p">

<h2 class="post-h2">Combining <code class="inline-code">:has()</code> with Other Selectors</h2>

<p class="post-p">
<code class="inline-code">:has()</code> composes beautifully with other modern CSS:
</p>

<pre class="code-block"><code class="language-css">/<em> :has() + :not() — cards WITHOUT images </em>/
<p class="post-p">
.product-grid:has(.card:not(:has(img))) {
grid-template-columns: repeat(auto-fill, minmax(250px, 1fr));
}
</p>

<p class="post-p">
/<em> :has() + :is() — any input that has an error state </em>/
.form:has(:is(input, select, textarea):user-invalid) {
--form-state: 'error';
}
</p>

<p class="post-p">
/<em> :has() + :where() — low-specificity structural checks </em>/
.sidebar:where(:has(nav)) {
background: var(--surface);
}
</p>

<p class="post-p">
/<em> :has() + :nth-child() — a grid with an odd number of items </em>/
.grid:has(&amp;gt; :nth-child(odd):last-child) {
/<em> The last item will span full width </em>/
justify-items: center;
}
</code></pre>
</p>

<h2 class="post-h2">Performance Considerations</h2>

<p class="post-p">
The browser needs to evaluate <code class="inline-code">:has()</code> selectors carefully because they look <em>downward</em> in the DOM tree — opposite to the normal top-down selector matching. Here's what to know:
</p>

<h3 class="post-h3">Good: Low specificity, shallow checks</h3>

<pre class="code-block"><code class="language-css">/<em> Fast — checks only immediate children </em>/
<p class="post-p">
.card:has(&amp;gt; img) { }
</p>

<p class="post-p">
/<em> Fast — checks only one level deep </em>/
form:has(input:invalid) { }
</p>

<p class="post-p">
/<em> Fast — simple structural check </em>/
section:has(&amp;gt; h2) { }
</code></pre>
</p>

<h3 class="post-h3">Watch out: Deep or complex selectors</h3>

<pre class="code-block"><code class="language-css">/<em> Slower — checks all descendants at any depth </em>/
<p class="post-p">
.container:has(img) { }
</p>

<p class="post-p">
/<em> Slower — complex combinator chain </em>/
body:has(.modal .dialog button:focus) { }
</code></pre>
</p>

<h3 class="post-h3">The browser is smart about it</h3>

<p class="post-p">
Browsers use a technique called "selector invalidation" — they only re-evaluate <code class="inline-code">:has()</code> when something changes that could affect the result. Changing the color of a child won't trigger a re-evaluation for <code class="inline-code">:has(img)</code>, but adding or removing an <code class="inline-code">&lt;img&gt;</code> will.
</p>

<p class="post-p">
In practice, for typical UI patterns, the performance impact of <code class="inline-code">:has()</code> is negligible. Don't avoid it out of premature optimization fear.
</p>

<h3 class="post-h3">The "specificity gotcha"</h3>

<p class="post-p">
<code class="inline-code">:has()</code> itself <strong>does not add specificity</strong>. Only the selectors <em>inside</em> <code class="inline-code">:has()</code> contribute:
</p>

<pre class="code-block"><code class="language-css">/<em> Specificity: 0,1,0 (one class) </em>/
<p class="post-p">
.card { }
</p>

<p class="post-p">
/<em> Specificity: 0,1,0 (still one class — :has() adds nothing) </em>/
.card:has(img) { }
</p>

<p class="post-p">
/<em> Specificity: 0,2,0 (.card + img inside :has()) </em>/
.card:has(img.hero) { }
</code></pre>
</p>

<p class="post-p">
This is different from <code class="inline-code">:not()</code> and <code class="inline-code">:is()</code> which take the specificity of their <em>most specific</em> argument. <code class="inline-code">:has()</code> is refreshingly simple.
</p>

<h2 class="post-h2">Common Pitfalls</h2>

<h3 class="post-h3">1. <code class="inline-code">:has()</code> cannot be nested inside another <code class="inline-code">:has()</code></h3>

<pre class="code-block"><code class="language-css">/<em> ❌ Not allowed — nested :has() </em>/
<p class="post-p">
.card:has(.body:has(img)) { }
</p>

<p class="post-p">
/<em> ✅ Restructure instead </em>/
.card:has(.body img) { }
</code></pre>
</p>

<p class="post-p">
The CSSWG restricted this to keep selector matching performant.
</p>

<h3 class="post-h3">2. Pseudo-elements don't work inside <code class="inline-code">:has()</code></h3>

<pre class="code-block"><code class="language-css">/<em> ❌ Won't work </em>/
<p class="post-p">
.card:has(::before) { }
</code></pre>
</p>

<p class="post-p">
<code class="inline-code">::before</code> and <code class="inline-code">::after</code> are not real DOM elements — <code class="inline-code">:has()</code> only sees the real tree.
</p>

<h3 class="post-h3">3. <code class="inline-code">:has()</code> only works with supported selectors</h3>

<pre class="code-block"><code class="language-css">/<em> ❌ Pseudo-classes that represent element state may not work </em>/
<p class="post-p">
/<em> (browser-dependent — check support) </em>/
.element:has(:focus-within) { } /<em> ✅ Works </em>/
.element:has(:hover) { }        /<em> ✅ Works </em>/
.element:has(:playing) { }      /<em> ⚠️ Check support </em>/
</code></pre>
</p>

<h3 class="post-h3">4. Overusing <code class="inline-code">:has()</code> for everything</h3>

<p class="post-p">
Just because you <em>can</em> doesn't mean you <em>should</em>. Simple structural selectors are often clearer:
</p>

<pre class="code-block"><code class="language-css">/<em> Over-engineered </em>/
<p class="post-p">
.wrapper:has(&amp;gt; .sidebar) { }
</p>

<p class="post-p">
/<em> Clearer and does the same thing </em>/
.wrapper &amp;gt; .sidebar { grid-column: 1; }
</code></pre>
</p>

<p class="post-p">
Use <code class="inline-code">:has()</code> when you need to style the <strong>ancestor</strong> or <strong>previous sibling</strong> — not when you can just target the element directly.
</p>

<h2 class="post-h2">Debugging <code class="inline-code">:has()</code> Selectors</h2>

<h3 class="post-h3">Chrome DevTools</h3>

<ul class="post-ul"><li class="post-li">Open DevTools → <strong>Elements</strong> panel</li>
<li class="post-li">Find an element with a <code class="inline-code">:has()</code> rule</li>
<li class="post-li">In the <strong>Styles</strong> pane, hover over the selector — Chrome highlights matching elements</li>
<li class="post-li">If the selector isn't matching, check the <strong>Computed</strong> tab to see which rule is being overridden</li>
</ul>
<h3 class="post-h3">Checking support dynamically</h3>

<pre class="code-block"><code class="language-css">@supports selector(:has(*)) {
<p class="post-p">
/<em> :has() is supported </em>/
.card:has(img) {
display: grid;
grid-template-columns: 200px 1fr;
}
}
</p>

<p class="post-p">
@supports not selector(:has(*)) {
/<em> Fallback </em>/
.card {
display: flex;
flex-direction: column;
}
}
</code></pre>
</p>

<h3 class="post-h3">Common debugging checklist</h3>

<ul class="post-ul"><li class="post-li">Is the element inside <code class="inline-code">:has()</code> actually a descendant? Use <code class="inline-code">&gt; </code> for direct children, space for any descendant.</li>
<li class="post-li">Are you using a valid selector inside <code class="inline-code">:has()</code>? No pseudo-elements, no nested <code class="inline-code">:has()</code>.</li>
<li class="post-li">Does the element exist in the DOM? <code class="inline-code">:has()</code> only sees real elements — not <code class="inline-code">::before</code>/<code class="inline-code">::after</code>.</li>
<li class="post-li">Is your specificity right? <code class="inline-code">:has()</code> doesn't add specificity — you might be getting overridden.</li>
</ul>
<h2 class="post-h2">The Bigger Picture: Why <code class="inline-code">:has()</code> Matters</h2>

<p class="post-p">
<code class="inline-code">:has()</code> represents a fundamental shift in CSS. For the first time, selectors can look <em>back up</em> the tree. This changes how we think about component architecture:
</p>

<ul class="post-ul"><li class="post-li"><strong>Before <code class="inline-code">:has()</code>:</strong> You styled elements from the top down. Components needed JavaScript to communicate state upward.</li>
<li class="post-li"><strong>After <code class="inline-code">:has()</code>:</strong> Components can react to their <em>contents</em>. A card knows if it has an image. A form knows if it has errors. A list knows if it's empty.</li>
</ul>
<p class="post-p">
This is <strong>declarative component logic</strong> — the CSS equivalent of React's component state, but built into the browser itself.
</p>

<h3 class="post-h3">What you can remove</h3>

<p class="post-p">
With <code class="inline-code">:has()</code>, you can often eliminate:
</p>

<p class="post-p">
| JavaScript Pattern | CSS Replacement |
|---|---|
| <code class="inline-code">parent.classList.toggle('has-image')</code> | <code class="inline-code">.card:has(img)</code> |
| <code class="inline-code">form.classList.add('has-errors')</code> | <code class="inline-code">form:has(:invalid)</code> |
| <code class="inline-code">menu.classList.toggle('open')</code> | <code class="inline-code">.dropdown:has([aria-expanded="true"])</code> |
| <code class="inline-code">items.length === 0 &amp;&amp; showEmptyState()</code> | <code class="inline-code">.list:not(:has(&gt; *)) .empty-state</code> |
| <code class="inline-code">previousSibling.classList.add('before-active')</code> | <code class="inline-code">.item:has(+ .item.active)</code> |
</p>

<p class="post-p">
Less JavaScript. Fewer state-management bugs. Faster initial render.
</p>
