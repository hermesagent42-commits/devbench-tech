CSS @starting-style: Entry Animations Without JavaScript — The Complete Guide

@starting-style lets you animate elements when they first appear — popovers, dialogs, lazy-loaded content, and display:none→block transitions. Pair it with transition-behavior:allow-discrete to animate discrete properties like display. This complete guide covers every use case with real production patterns.

The Missing Piece: Animating First Render

For decades, CSS animations had a fundamental limitation: you could animate an element while it existed, but you couldn't animate its first appearance. Opening a dialog? Instant. Showing a tooltip? Instant. Toggling display? Instant. Developers resorted to JavaScript, requestAnimationFrame hacks, and fragile setTimeout tricks just to fade in a modal.

@starting-style fixes this. It's a CSS at-rule that defines the "before" state for a transitioning element. When the browser renders an element for the first time (or after display:none), it uses the @starting-style values as the initial state, then transitions to the regular values. No JavaScript. No timeouts. Just CSS.

In 2026, @starting-style is Baseline Widely Available — supported in Chrome 117+, Edge 117+, Safari 17.2+, Firefox 134+, and Samsung Internet 24+. Combined with transition-behavior: allow-discrete (also Baseline 2026), you can now animate every CSS property, including display.

The Basic Syntax

@starting-style wraps a ruleset that the browser uses as the "entry" state. It's always scoped inside an existing rule: 

.tooltip {
  opacity: 1;
  transform: translateY(0);
  transition: opacity 0.2s, transform 0.2s;

  @starting-style {
    opacity: 0;
    transform: translateY(8px);
  }
}

When .tooltip first renders (or re-renders after display:none), the browser snaps it to opacity: 0; transform: translateY(8px), then immediately transitions to opacity: 1; transform: translateY(0). The result: a smooth fade-in + slide-up, every time.

How it works under the hood: @starting-style doesn't create a separate animation. It just tells the browser "when you first paint this element, pretend these were its previous styles." The existing transition property does the rest — transitioning from the @starting-style values to the current computed values.

Animating Display: The display + opacity Trick

The most common real-world use case: showing and hiding elements with display: none while keeping animation. Before @starting-style, this required opacity+visibility hacks or JavaScript to toggle display after animation ended. Now it's one ruleset: 

.panel {
  display: none;
  opacity: 1;
  transition: opacity 0.3s, display 0.3s;
  transition-behavior: allow-discrete;

  &.open {
    display: block;

    @starting-style {
      opacity: 0;
    }
  }
}

When .panel.open is applied, the element gets display: block but starts at opacity: 0, then transitions. transition-behavior: allow-discrete is needed because display is a discrete property — it has no intermediate values. The browser waits until the end of the transition duration to flip display from none to block (for entry) or vice versa (for exit).

The Exit Side: Why You Still Need @starting-style

Exiting (hiding) works with standard transitions — animate opacity: 1 → 0, then the browser sets display: none at the end. But for entry, you need @starting-style because the element has no "before" styles when it transitions from display: none.

Key rule: @starting-style defines the entry state. For exit animations, use normal transitions (opacity 1→0, etc.) and rely on transition-behavior: allow-discrete to delay the display: none until the transition completes.

Popover Entry Animations

The Popover API (popover attribute) is a natural match for @starting-style. Popovers transition from hidden to shown via the :popover-open pseudo-class: 

[popover] {
  opacity: 1;
  transform: scale(1);
  transition:
    opacity 0.2s,
    transform 0.2s,
    overlay 0.2s,
    display 0.2s;
  transition-behavior: allow-discrete;

  &:popover-open {
    @starting-style {
      opacity: 0;
      transform: scale(0.95);
    }
  }
}

Note the overlay property in the transition list. Popovers render in the top layer, and overlay is another discrete property that needs allow-discrete to transition. Include it in the transition shorthand so the popover stays in the top layer during the exit transition.

Directional Popover Entry

Make popovers enter from the direction they point. Use custom properties for reusable direction-aware animations: 

[popover] {
  --enter-from: translateY(4px);
  opacity: 1;
  transform: translate(0, 0);
  transition: opacity 0.2s, transform 0.25s cubic-bezier(0.34, 1.56, 0.64, 1);

  &:popover-open {
    @starting-style {
      opacity: 0;
      transform: var(--enter-from);
    }
  }
}

.tooltip-top { --enter-from: translateY(8px); }
.tooltip-bottom { --enter-from: translateY(-8px); }
.tooltip-left { --enter-from: translateX(8px); }
.tooltip-right { --enter-from: translateX(-8px); }

One @starting-style rule, infinite directions — all driven by custom properties. Swap the --enter-from value and the popover enters from any direction.

Dialog & Modal Entry

The <dialog> element's showModal() method also benefits from @starting-style. Unlike popovers, dialogs use the [open] attribute and ::backdrop for the overlay: 

dialog {
  opacity: 1;
  transform: translateY(0) scale(1);
  transition:
    opacity 0.3s,
    transform 0.3s,
    overlay 0.3s,
    display 0.3s;
  transition-behavior: allow-discrete;

  &[open] {
    @starting-style {
      opacity: 0;
      transform: translateY(16px) scale(0.97);
    }
  }
}

dialog::backdrop {
  background: rgb(0 0 0 / 50%);
  transition: background 0.3s, overlay 0.3s, display 0.3s;
  transition-behavior: allow-discrete;

  dialog[open] & {
    @starting-style {
      background: rgb(0 0 0 / 0%);
    }
  }
}

Result: modal slides up with a gentle scale, backdrop fades in. No JS animation libraries. The ::backdrop pseudo-element gets its own @starting-style for a simultaneous overlay fade.

Staggered List Entries

@starting-style really shines with list entries. Add items to a list and each one animates in, staggered via animation-delay or transition-delay: 

.list-item {
  opacity: 1;
  transform: translateX(0);
  transition: opacity 0.3s, transform 0.3s;
  transition-delay: calc(var(--i, 0) * 50ms);

  @starting-style {
    opacity: 0;
    transform: translateX(20px);
  }
}

Set --i: 0, --i: 1, --i: 2 inline on each item, and they cascade in with a 50ms stagger. This pattern works with any framework — React, Vue, Svelte, or plain HTML generated server-side.

Lazy-Loaded Content & Skeleton Screens

Skeleton screens typically flash from skeleton → content. With @starting-style, the content can crossfade from the skeleton state: 

.card-content {
  opacity: 1;
  filter: blur(0);
  transition: opacity 0.4s, filter 0.4s;

  @starting-style {
    opacity: 0;
    filter: blur(4px);
  }
}

When the skeleton screen hides and the real content mounts, it blurs in smoothly. The filter: blur() transition masks any layout shift during the swap.

View Transitions + @starting-style

The View Transitions API and @starting-style are complementary, not competitive. View Transitions handle cross-document and cross-state morphing. @starting-style handles first-render entry. They can work together: 

::view-transition-new(root) {
  animation: none; /* Disable crossfade */
}

/* Use @starting-style for the entry instead */
.page {
  opacity: 1;
  transform: translateY(0);
  transition: opacity 0.3s, transform 0.3s;

  @starting-style {
    opacity: 0;
    transform: translateY(20px);
  }
}

This gives you slide-up page transitions on SPA navigation without the full View Transitions ceremony. Disable the VT crossfade, let @starting-style handle the entry animation.

Performance: What to Animate

@starting-style triggers a style recalculation and paint on entry. For smooth 60fps, stick to compositor-only properties:

Safe (compositor)Avoid (layout triggers)
opacitywidth, height
transform (translate, scale, rotate)top, left, margin, padding
filter (blur, brightness)border-width
clip-path (simple shapes)font-size, line-height

Every transform animation is GPU-accelerated and doesn't trigger layout. A width transition triggers layout on every frame. When in doubt: opacity + transform is always safe.

Progressive Enhancement

@starting-style is safe to use without fallbacks. Browsers that don't support it simply render the element in its final state instantly — no broken layouts, no invisible content. The @starting-style block is ignored: 

.banner {
  opacity: 1;
  transform: translateY(0);
  transition: opacity 0.4s, transform 0.4s;

  @starting-style {
    opacity: 0;
    transform: translateY(12px);
  }
}

/* Older browsers: .banner renders immediately at full opacity.
   No polyfill needed. */

You can detect support with @supports if you need to adjust other styles: 

@supports (transition-behavior: allow-discrete) {
  .panel {
    transition-behavior: allow-discrete;
  }
}

Common Pitfalls

1. Forgetting transition-behavior: allow-discrete

If you're transitioning display or overlay (both discrete properties), you must set transition-behavior: allow-discrete. Without it, the browser can't animate the transition and falls back to instant display changes.

2. Not Including display in the Transition List

Even with allow-discrete, listing only opacity in your transition won't animate the display change. The browser needs display explicitly in the transition shorthand: 

/* Wrong: display changes instantly */
transition: opacity 0.3s;

/* Right: display flips after 0.3s */
transition: opacity 0.3s, display 0.3s;
transition-behavior: allow-discrete;

3. @starting-style in the Wrong Place

@starting-style must be nested inside the rule for the element's visible state, not its hidden state: 

/* Wrong: @starting-style does nothing here */
.element {
  display: none;
  @starting-style { opacity: 0; }
}

/* Right: @starting-style goes in the visible state */
.element[open],
.element.visible {
  display: block;
  opacity: 1;
  transition: opacity 0.3s, display 0.3s;
  transition-behavior: allow-discrete;

  @starting-style {
    opacity: 0;
  }
}

4. Too Many Properties in @starting-style

Only include the properties that are actually transitioning. Extra properties in @starting-style just create unnecessary style recalculation: 

/* Unnecessary: transform isn't transitioning */
.element {
  opacity: 1;
  transition: opacity 0.3s;
  @starting-style {
    opacity: 0;
    /* transform: translateY(20px); — wasted, no transition for this */
  }
}

Complete Real-World Component: Notification Toast

Putting it all together — a notification toast that slides in, auto-dismisses, and slides out: 

.toast {
  display: none;
  opacity: 1;
  transform: translateX(0);
  transition:
    opacity 0.3s,
    transform 0.3s cubic-bezier(0.34, 1.56, 0.64, 1),
    display 0.3s;
  transition-behavior: allow-discrete;

  position: fixed;
  bottom: 24px;
  right: 24px;
  padding: 16px 20px;
  border-radius: 12px;
  background: #1e293b;
  color: #f1f5f9;
  box-shadow: 0 8px 32px rgb(0 0 0 / 30%);
  max-width: 400px;
  z-index: 9999;
}

.toast.visible {
  display: block;

  @starting-style {
    opacity: 0;
    transform: translateX(100%);
  }
}

/* Exit state */
.toast.exiting {
  opacity: 0;
  transform: translateX(calc(100% + 24px));
}

The JavaScript is minimal — just toggling classes: 

function showToast(message) {
  const toast = document.querySelector('.toast');
  toast.textContent = message;
  toast.classList.add('visible');
  toast.classList.remove('exiting');

  setTimeout(() => {
    toast.classList.add('exiting');
    toast.classList.remove('visible');
  }, 4000);
}

That's it. No animation library. No animate() API. Just CSS. The toast slides in from the right with a spring easing, stays for 4 seconds, then slides out further right. The display transition handles the mount/unmount timing.
