<p class="post-p">
CSS custom properties (<code class="inline-code">--my-var</code>) have been Baseline since 2017. For years, we've used them for simple theming — define a few color tokens, swap them in a dark mode, done. But custom properties in 2026 are a completely different beast.
</p>

<p class="post-p">
With <code class="inline-code">@property</code> landing everywhere, custom properties now have <strong>types, default values, and animation support</strong>. Combined with style queries (part of Interop 2026), they unlock patterns that were previously impossible without JavaScript or preprocessors.
</p>

<p class="post-p">
Let's go beyond <code class="inline-code">--primary: blue</code> and see what custom properties can really do.
</p>

<h2 class="post-h2">The Foundation: What Custom Properties Actually Are</h2>

<p class="post-p">
Custom properties aren't just "variables." They're <strong>live values that participate in the cascade, inherit, and can be read by JavaScript</strong>. This makes them fundamentally different from Sass variables (compile-time) or CSS preprocessor variables (static).
</p>

<pre class="code-block"><code class="language-css">:root {
<p class="post-p">
--brand: oklch(0.6 0.2 250);
--spacing: 1rem;
}
</p>

<p class="post-p">
.card {
/<em> These resolve at computed-value time, not parse time </em>/
background: var(--brand);
padding: var(--spacing);
}
</p>

<p class="post-p">
.card--compact {
/<em> Override inherits through the cascade </em>/
--spacing: 0.5rem;
}
</code></pre>
</p>

<p class="post-p">
Three properties that make custom properties unique:
</p>

<ul class="post-ul"><li class="post-li"><strong>They inherit</strong> — unlike most CSS properties, custom properties inherit by default. Set <code class="inline-code">--spacing</code> on a parent, and every child sees it.</li>
<li class="post-li"><strong>They're live</strong> — change <code class="inline-code">--brand</code> with JavaScript via <code class="inline-code">element.style.setProperty('--brand', 'red')</code>, and every element that references it updates instantly.</li>
<li class="post-li"><strong>They cascade</strong> — you can override them at any level of specificity. This is the superpower.</li>
</ul>
<h2 class="post-h2">@property: Typed Custom Properties</h2>

<p class="post-p">
The <code class="inline-code">@property</code> at-rule (part of CSS Houdini) lets you <strong>register a custom property with a type, default value, and inheritance behavior</strong>. This unlocks three things you can't do with unregistered properties:
</p>

<h3 class="post-h3">1. Animation and Transitions</h3>

<p class="post-p">
Unregistered custom properties can't animate — the browser treats them as strings. Registered properties with a syntax type can:
</p>

<pre class="code-block"><code class="language-css">@property --angle {
<p class="post-p">
syntax: '&amp;lt;angle&amp;gt;';
initial-value: 0deg;
inherits: false;
}
</p>

<p class="post-p">
.spinner {
--angle: 0deg;
animation: spin 1s linear infinite;
transform: rotate(var(--angle));
}
</p>

<p class="post-p">
@keyframes spin {
to { --angle: 360deg; }
}
</code></pre>
</p>

<p class="post-p">
This is huge: <strong>you can now animate any CSS value that accepts a typed custom property</strong>. Colors, lengths, percentages, angles, numbers, even <code class="inline-code">&lt;transform-function&gt;</code> — all animatable through custom properties.
</p>

<h3 class="post-h3">2. Default Values at Parse Time</h3>

<p class="post-p">
Without <code class="inline-code">@property</code>, if a custom property is undefined, <code class="inline-code">var()</code> falls back to whatever you specify inline. But with <code class="inline-code">@property</code>, the browser knows the type at parse time:
</p>

<pre class="code-block"><code class="language-css">@property --gradient-angle {
<p class="post-p">
syntax: '&amp;lt;angle&amp;gt;';
initial-value: 180deg;
inherits: false;
}
</p>

<p class="post-p">
.hero {
/<em> If --gradient-angle isn't set, defaults to 180deg </em>/
background: linear-gradient(
var(--gradient-angle),
var(--brand, oklch(0.6 0.2 250)),
var(--accent, oklch(0.7 0.15 180))
);
}
</code></pre>
</p>

<h3 class="post-h3">3. Validation and Error Recovery</h3>

<p class="post-p">
Registered properties reject invalid values and fall back to their initial-value. Unregistered properties accept anything — including typos:
</p>

<pre class="code-block"><code class="language-css">@property --columns {
<p class="post-p">
syntax: '&amp;lt;integer&amp;gt;';
initial-value: 3;
inherits: false;
}
</p>

<p class="post-p">
.grid {
--columns: 4;          /<em> valid integer </em>/
grid-template-columns: repeat(var(--columns), 1fr);
}
</p>

<p class="post-p">
.grid--broken {
--columns: auto;       /<em> invalid — falls back to 3 </em>/
/<em> Browser silently uses initial-value: 3 </em>/
}
</code></pre>
</p>

<h3 class="post-h3">Available Syntax Types</h3>

<p class="post-p">
<code class="inline-code">@property</code> supports these syntax strings:
</p>

<p class="post-p">
| Type | Example | Animateable |
|------|---------|-------------|
| <code class="inline-code">&lt;length&gt;</code> | <code class="inline-code">10px</code>, <code class="inline-code">2rem</code>, <code class="inline-code">5vw</code> | Yes |
| <code class="inline-code">&lt;percentage&gt;</code> | <code class="inline-code">50%</code>, <code class="inline-code">-10%</code> | Yes |
| <code class="inline-code">&lt;length-percentage&gt;</code> | <code class="inline-code">10px</code> or <code class="inline-code">50%</code> | Yes |
| <code class="inline-code">&lt;number&gt;</code> | <code class="inline-code">0</code>, <code class="inline-code">1.5</code>, <code class="inline-code">-3</code> | Yes |
| <code class="inline-code">&lt;integer&gt;</code> | <code class="inline-code">1</code>, <code class="inline-code">42</code> | No (discrete) |
| <code class="inline-code">&lt;angle&gt;</code> | <code class="inline-code">45deg</code>, <code class="inline-code">1turn</code> | Yes |
| <code class="inline-code">&lt;time&gt;</code> | <code class="inline-code">1s</code>, <code class="inline-code">500ms</code> | No |
| <code class="inline-code">&lt;color&gt;</code> | <code class="inline-code">red</code>, <code class="inline-code">#ff0000</code>, <code class="inline-code">oklch(...)</code> | Yes |
| <code class="inline-code">&lt;transform-function&gt;</code> | <code class="inline-code">rotate(45deg)</code> | Yes |
| <code class="inline-code">&lt;transform-list&gt;</code> | <code class="inline-code">rotate(45deg) scale(1.2)</code> | Yes |
| <code class="inline-code">&lt;url&gt;</code> | <code class="inline-code">url(...)</code> | No |
| <code class="inline-code">&lt;image&gt;</code> | <code class="inline-code">&lt;url&gt;</code>, <code class="inline-code">&lt;gradient&gt;</code> | No |
| <code class="inline-code">*</code> | Any value (no type checking) | No |
</p>

<h2 class="post-h2">Pattern 1: The Space Toggle</h2>

<p class="post-p">
The "space toggle" is one of the most elegant custom property patterns. It uses <code class="inline-code">--var: ;</code> (a space) vs <code class="inline-code">--var: initial</code> to toggle between two values:
</p>

<pre class="code-block"><code class="language-css">:root {
<p class="post-p">
--is-dark: ;  /<em> space = false </em>/
}
</p>

<p class="post-p">
@media (prefers-color-scheme: dark) {
:root {
--is-dark: initial;  /<em> initial = true </em>/
}
}
</p>

<p class="post-p">
.card {
/<em> When --is-dark is a space: background = white, color = black </em>/
/<em> When --is-dark is initial: background = var(--bg-dark) = #1a1a2e </em>/
--bg: var(--is-dark, #1a1a2e);
--fg: var(--is-dark, #e0e0e0);
</p>

<p class="post-p">
background: var(--bg, white);
color: var(--fg, black);
}
</code></pre>
</p>

<p class="post-p">
How it works: <code class="inline-code">var(--is-dark, #1a1a2e)</code> resolves to <code class="inline-code">#1a1a2e</code> when <code class="inline-code">--is-dark</code> is <code class="inline-code">initial</code> (any value), and falls back to nothing (empty) when <code class="inline-code">--is-dark</code> is a space (empty/whitespace custom property). Then the outer <code class="inline-code">var(--bg, white)</code> falls back to <code class="inline-code">white</code>.
</p>

<p class="post-p">
This lets you chain multiple toggles:
</p>

<pre class="code-block"><code class="language-css">.button {
<p class="post-p">
padding: var(--is-compact, 0.25rem 0.5rem) var(--spacing, 0.75rem 1.5rem);
font-size: var(--is-compact, 0.75rem) var(--font-size, 0.875rem);
border-radius: var(--is-pill, 9999px) var(--radius, 0.375rem);
}
</code></pre>
</p>

<h2 class="post-h2">Pattern 2: Staggered Animations Without nth-child</h2>

<p class="post-p">
Custom properties let you stagger animations using a single animation and cascaded custom properties:
</p>

<pre class="code-block"><code class="language-css">.list-item {
<p class="post-p">
--index: 0;
--delay: calc(var(--index) * 100ms);
animation: slide-in 0.4s ease-out var(--delay) both;
}
</p>

<p class="post-p">
.list-item:nth-child(1) { --index: 1; }
.list-item:nth-child(2) { --index: 2; }
.list-item:nth-child(3) { --index: 3; }
.list-item:nth-child(4) { --index: 4; }
.list-item:nth-child(5) { --index: 5; }
</p>

<p class="post-p">
@keyframes slide-in {
from {
opacity: 0;
transform: translateY(20px);
}
}
</code></pre>
</p>

<p class="post-p">
Better yet, with <code class="inline-code">@property</code> and a single <code class="inline-code">@keyframes</code>:
</p>

<pre class="code-block"><code class="language-css">@property --item-delay {
<p class="post-p">
syntax: '&amp;lt;time&amp;gt;';
initial-value: 0ms;
inherits: true;
}
</p>

<p class="post-p">
.list-item {
animation: slide-in 0.4s ease-out var(--item-delay) both;
}
</code></pre>
</p>

<h2 class="post-h2">Pattern 3: Computed Design Tokens</h2>

<p class="post-p">
Custom properties can compute values from other custom properties using <code class="inline-code">calc()</code>:
</p>

<pre class="code-block"><code class="language-css">:root {
<p class="post-p">
--base-size: 1rem;
--ratio: 1.25;
</p>

<p class="post-p">
/<em> Computed from base and ratio </em>/
--size-sm: calc(var(--base-size) / var(--ratio));
--size-md: var(--base-size);
--size-lg: calc(var(--base-size) * var(--ratio));
--size-xl: calc(var(--base-size) <em> var(--ratio) </em> var(--ratio));
--size-2xl: calc(var(--base-size) <em> var(--ratio) </em> var(--ratio) * var(--ratio));
</p>

<p class="post-p">
/<em> Derived color tokens </em>/
--surface-hue: 250;
--surface-lightness: 15%;
--surface-1: oklch(var(--surface-lightness) 0.02 var(--surface-hue));
--surface-2: oklch(calc(var(--surface-lightness) + 5%) 0.03 var(--surface-hue));
--surface-3: oklch(calc(var(--surface-lightness) + 10%) 0.04 var(--surface-hue));
}
</code></pre>
</p>

<p class="post-p">
Now changing <code class="inline-code">--base-size</code> or <code class="inline-code">--ratio</code> propagates through the entire design system. This is impossible with preprocessor variables — they're baked in at compile time.
</p>

<h2 class="post-h2">Pattern 4: Custom Properties + Style Queries</h2>

<p class="post-p">
Style queries (part of Interop 2026) let you query <strong>computed styles</strong> of a container. Combined with custom properties, you get truly context-aware components:
</p>

<pre class="code-block"><code class="language-css">.component-container {
<p class="post-p">
container-type: inline-size;
/<em> Set these as "props" for children to query </em>/
--theme: dark;
--density: compact;
}
</p>

<p class="post-p">
/<em> Child queries the container's custom property values </em>/
@container style(--theme: dark) {
.card {
background: oklch(0.15 0.02 250);
color: oklch(0.9 0.01 250);
}
}
</p>

<p class="post-p">
@container style(--density: compact) {
.card {
padding: 0.5rem;
font-size: 0.8125rem;
}
}
</code></pre>
</p>

<p class="post-p">
This is essentially <strong>component props in CSS</strong> — a component can change its entire appearance based on custom properties set on any ancestor container.
</p>

<h2 class="post-h2">Pattern 5: Dynamic Gradients and Effects</h2>

<p class="post-p">
With <code class="inline-code">@property</code>-typed <code class="inline-code">&lt;angle&gt;</code> and <code class="inline-code">&lt;color&gt;</code> properties, you can animate gradients and visual effects that were previously JavaScript territory:
</p>

<pre class="code-block"><code class="language-css">@property --gradient-1 {
<p class="post-p">
syntax: '&amp;lt;color&amp;gt;';
initial-value: oklch(0.6 0.2 300);
inherits: false;
}
</p>

<p class="post-p">
@property --gradient-2 {
syntax: '&amp;lt;color&amp;gt;';
initial-value: oklch(0.6 0.2 200);
inherits: false;
}
</p>

<p class="post-p">
@property --angle {
syntax: '&amp;lt;angle&amp;gt;';
initial-value: 0deg;
inherits: false;
}
</p>

<p class="post-p">
.animated-gradient {
--gradient-1: oklch(0.6 0.2 300);
--gradient-2: oklch(0.6 0.2 200);
--angle: 0deg;
</p>

<p class="post-p">
background: linear-gradient(
var(--angle),
var(--gradient-1),
var(--gradient-2)
);
</p>

<p class="post-p">
animation: gradient-shift 4s ease-in-out infinite;
}
</p>

<p class="post-p">
@keyframes gradient-shift {
0%, 100% {
--gradient-1: oklch(0.6 0.2 300);
--gradient-2: oklch(0.6 0.2 200);
--angle: 0deg;
}
50% {
--gradient-1: oklch(0.6 0.2 150);
--gradient-2: oklch(0.6 0.2 50);
--angle: 180deg;
}
}
</code></pre>
</p>

<h2 class="post-h2">Pattern 6: The "Defensive" var() Fallback Chain</h2>

<p class="post-p">
<code class="inline-code">var()</code> supports fallback chains — but there's a subtlety with how they resolve:
</p>

<pre class="code-block"><code class="language-css">/<em> BAD: only one fallback </em>/
<p class="post-p">
color: var(--text-color, black);
</p>

<p class="post-p">
/<em> GOOD: chain of custom properties, then a hard value </em>/
color: var(--text-color, var(--text-color-component, var(--text-color-global, black)));
</p>

<p class="post-p">
/<em> BEST: component-scoped with theme fallback </em>/
.component {
--_text: var(--text-color, var(--theme-text, CanvasText));
</p>

<p class="post-p">
color: var(--_text);
background: var(--surface-color, var(--theme-surface, Canvas));
}
</code></pre>
</p>

<p class="post-p">
The key insight: custom properties can fall back to <strong>other custom properties</strong>, which can fall back to hard values. This creates a hierarchy: component override → theme token → system default.
</p>

<h2 class="post-h2">When NOT to Use Custom Properties</h2>

<p class="post-p">
Custom properties are powerful but not always the right tool:
</p>

<ul class="post-ul"><li class="post-li"><strong>Static design tokens that never change</strong> — Preprocessor variables or just hardcoding values may be simpler. Custom properties have a small runtime cost from inheritance.</li>
<li class="post-li"><strong>Values used in media queries</strong> — You can't use <code class="inline-code">var()</code> in <code class="inline-code">@media</code> queries. Media queries resolve at parse time, custom properties at computed-value time.</li>
<li class="post-li"><strong>Selectors or property names</strong> — Custom properties store values, not property names or selectors. <code class="inline-code">var(--some-prop): value;</code> doesn't work.</li>
<li class="post-li"><strong>Extreme performance-critical rendering</strong> — Custom properties that change frequently (on scroll, every frame) trigger style recalculations on all inheriting descendants. Use <code class="inline-code">inherits: false</code> with <code class="inline-code">@property</code> to limit the blast radius.</li>
</ul>
<h2 class="post-h2">Key Takeaways</h2>

<ul class="post-ul"><li class="post-li"><strong>Register with <code class="inline-code">@property</code></strong> — Unlocks animation, type safety, and default values. Do this for every design token.</li>
<li class="post-li"><strong>Compute, don't duplicate</strong> — Design tokens that derive from a few base values are easier to maintain. Use <code class="inline-code">calc()</code>.</li>
<li class="post-li"><strong>The cascade is your component API</strong> — Set custom properties on containers and let children query them with <code class="inline-code">@container style()</code>.</li>
<li class="post-li"><strong>Chain your fallbacks</strong> — <code class="inline-code">var(--component, var(--theme, var(--global, hard-fallback)))</code> gives you a full override hierarchy.</li>
<li class="post-li"><strong>Use <code class="inline-code">inherits: false</code></strong> — Unless inheritance is explicitly needed, false prevents accidental style leakage.</li>
</ul>
<p class="post-p">
Custom properties are no longer just "CSS variables." They're the backbone of modern CSS architecture — typed, animatable, and context-aware. If you're still treating them as simple color swaps, you're missing 90% of what they can do.
