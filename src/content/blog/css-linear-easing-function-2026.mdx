Every animation you've ever written in CSS has been held hostage by `cubic-bezier()`. Four numbers. Two control points. If the easing you wanted didn't fit within those constraints, you reached for JavaScript — GSAP, Framer Motion, anime.js, your own requestAnimationFrame loop. Not anymore. CSS `linear()` is the easing function that gives you unlimited control points, letting you specify the exact progress at any point in time.

## What's Wrong with cubic-bezier()

`cubic-bezier()` has served us well for 15 years. But it's fundamentally limited:

```css
/* The only easing primitives we had */
transition-timing-function: ease;           /* cubic-bezier(0.25, 0.1, 0.25, 1) */
transition-timing-function: ease-in;        /* cubic-bezier(0.42, 0, 1, 1) */
transition-timing-function: ease-out;       /* cubic-bezier(0, 0, 0.58, 1) */
transition-timing-function: ease-in-out;    /* cubic-bezier(0.42, 0, 0.58, 1) */
transition-timing-function: cubic-bezier(0.34, 1.56, 0.64, 1); /* "bounce" — barely */
```

The problem: **a cubic Bézier curve can only have one inflection point**. That means no bounce. No spring oscillation. No elastic overshoot-and-settle. The `cubic-bezier(0.34, 1.56, 0.64, 1)` "bounce" is a single overshoot — not the multi-bounce you get from a real physics simulation.

If you've ever built anything that needed genuine bounce, spring, or a custom motion profile, you've felt this limitation.

## Enter `linear()`

The `linear()` easing function accepts a comma-separated list of **stops** — each one says "at this percentage of time, progress should be at this percentage." You can have as many stops as you want.

```css
/* Basic syntax */
transition-timing-function: linear(0, 0.25, 0.5, 0.75, 1);
/*                               ↑  ↑      ↑     ↑      ↑
                               stops at 0%, 25%, 50%, 75%, 100% of duration */

/* With explicit input percentages */
transition-timing-function: linear(
  0 0%,       /* at 0% of time, progress is 0% */
  0.5 10%,    /* at 10% of time, progress is 50% */
  1 80%,      /* at 80% of time, progress is 100% — then stay at 100% */
  0.8 85%,    /* at 85% of time, progress drops to 80% — overshoot! */
  1 100%      /* finally settle at 100% */
);
```

Each stop is: `<output> <input>?` — where input is the percentage of duration and output is the progress at that point. If you omit the input percentage, stops are spaced evenly across the duration.

The browser linearly interpolates between consecutive stops. Between stop A and stop B, progress changes at a constant rate.

## Visual Comparison: linear() vs cubic-bezier()

Consider a card that animates in from the bottom. Here's the same animation with three different easings:

```css
/* Standard cubic-bezier — smooth but generic */
.card {
  animation: slideUp 0.5s cubic-bezier(0.34, 1.56, 0.64, 1);
}

/* linear() spring — settles naturally */
.card {
  animation: slideUp 0.5s var(--ease-spring);
}

/* linear() bounce — playful, attention-grabbing */
.card {
  animation: slideUp 0.5s var(--ease-bounce);
}

@keyframes slideUp {
  from { transform: translateY(40px); opacity: 0; }
  to   { transform: translateY(0); opacity: 1; }
}
```

The cubic-bezier version overshoots once. The spring version oscillates 3 times before settling — like a real physical spring. The bounce version rebounds 4 times from the ground — like a real dropped ball. All three work in plain CSS with zero JavaScript.

## How linear() Works Under the Hood

Unlike `cubic-bezier()` which computes a parametric curve, `linear()` is a piecewise linear interpolation. The browser:

1. Sorts stops by their input percentage
2. For any given time `t` (0 to 1), finds the two stops that bracket it
3. Linearly interpolates between those two stops' output values

This means `linear()` is **guaranteed to be fast** — it's always O(log n) lookups and one lerp operation. Cubic-bezier requires solving a cubic equation. Linear is literally simpler arithmetic.

### Performance note

```css
/* 4 stops — negligible overhead, identical to cubic-bezier performance */
transition-timing-function: linear(0, 0.25, 0.75, 1);

/* 50+ stops — still fast, but don't go overboard */
transition-timing-function: linear(0, 0.01, 0.02, 0.03, /* ... 50 values */);

/* 200+ stops — technically valid, but wasteful. Smooth at ~30+ stops */
```

The sweet spot is 5–30 stops for bounce and spring curves. Above 30 stops the visual difference is imperceptible — the browser already interpolates linearly between stops, so a dense curve converges to the same result.

```css
.notification {
  animation: notificationEnter 0.6s var(--ease-spring) both;
```

```css
.refresh-indicator {
```

```css
.input-error {
  animation: shake 0.5s var(--ease-shake);

@keyframes shake {

  100% { transform: translateX(0); }
```


## Combining linear() with animation-composition

CSS `animation-composition` (also Baseline 2026) lets multiple animations combine on the same property. Pair it with `linear()` for compound effects:

```css
.floating-card {
  animation:
    float 3s linear(0, 0.5 50%, 1 100%) infinite,
    shadow 3s var(--ease-emphatic) infinite;
  animation-composition: accumulate; /* stack both animations */
}

@keyframes float {
  from, to { transform: translateY(0); }
  50%      { transform: translateY(-12px); }
}

@keyframes shadow {
  from, to { box-shadow: 0 2px 8px rgba(0,0,0,0.15); }
  50%      { box-shadow: 0 12px 24px rgba(0,0,0,0.2); }
}
```

## Progressive Enhancement Strategy

`linear()` is supported in all major browsers as of Chrome 127, Firefox 126, and Safari 17.2 — it reached Baseline in early 2025. But if you need to support older browsers:

```css
/* Fallback: regular ease for old browsers */
.my-element {
  animation: slideUp 0.5s ease-out;
}

/* Enhancement: spring for modern browsers */
@supports (animation-timing-function: linear(0, 1)) {
  .my-element {
    animation: slideUp 0.5s var(--ease-spring);
  }
}
```

The `@supports` check detects `linear()` support cleanly. In unsupported browsers, you fall back to `ease-out` — the animation still plays, just without the spring effect.

## When NOT to Use linear()

- **Default state transitions**: A simple fade or color change doesn't need a 50-stop easing curve. Use `ease`, `ease-out`, or a 3-stop `linear()`.
- **Continuous infinite animations**: If an animation runs forever without a start/end (like a rotating loader), the easing only matters at the start. Use `linear` (the keyword, not the function).
- **Performance-critical 60fps animations with hundreds of elements**: While `linear()` is fast, `cubic-bezier()` is still slightly faster due to fewer points. For 500+ simultaneous animated elements, consider simpler easings.
- **When you need physics-accurate simulation**: `linear()` approximates spring/bounce curves. If you need exact physics (e.g., a game), you're better off with a JavaScript physics engine and requestAnimationFrame.

For 15 years, CSS animations have been constrained by `cubic-bezier()` — four numbers, one inflection point, and a whole lot of JavaScript workarounds for anything more complex. `linear()` changes that.

You can now define bounce. Spring. Elastic. Shake. Squash-and-stretch. Smooth stepped progressions. Anticipated movements. All in CSS, all GPU-accelerated, all running at 60fps with no JavaScript.
