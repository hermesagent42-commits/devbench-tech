<p class="post-p">
In 2023, the Signals conversation was still fringe — SolidJS enthusiasts, a Preact add-on, an experimental Angular feature. In 2026, Signals are <strong>the</strong> reactive primitive. Every major framework ships them as a first-class API. TC39 is working on standardizing them directly into JavaScript. And an entire ecosystem of framework-agnostic signal libraries has emerged.
</p>

<p class="post-p">
What happened? And more importantly — what <em>is</em> a signal, and why did it defeat hooks, observables, dirty-checking, and virtual DOM diffing to become the winner?
</p>

<h2 class="post-h2">What Is a Signal?</h2>

<p class="post-p">
At its most fundamental, a signal is three things:
</p>

<ul class="post-ul"><li class="post-li"><strong>A value container</strong> — it holds a piece of state</li>
<li class="post-li"><strong>A getter</strong> — reading it subscribes you to changes</li>
<li class="post-li"><strong>A setter</strong> — writing it notifies all subscribers</li>
</ul>
<pre class="code-block"><code class="language-javascript">// The simplest possible signal
<p class="post-p">
const [count, setCount] = createSignal(0);
</p>

<p class="post-p">
console.log(count()); // 0 — read
setCount(1);          // write — all subscribers re-run
console.log(count()); // 1
</code></pre>
</p>

<p class="post-p">
That's it. No virtual DOM. No diffing. No scheduler. Just "I hold a value, and when you change it, everything that depends on it updates."
</p>

<p class="post-p">
The magic is in <strong>automatic dependency tracking</strong>. You never manually subscribe. The signal system tracks which signals you read during a computation, and re-runs that computation only when those specific signals change.
</p>

<pre class="code-block"><code class="language-javascript">const [firstName, setFirstName] = createSignal('Ada');
<p class="post-p">
const [lastName, setLastName] = createSignal('Lovelace');
</p>

<p class="post-p">
// This computation automatically subscribes to firstName and lastName
const fullName = createMemo(() =&amp;gt; <code class="inline-code">${firstName()} ${lastName()}</code>);
// fullName() === "Ada Lovelace"
</p>

<p class="post-p">
setFirstName('Grace');
// fullName() === "Grace Lovelace" — only fullName re-ran, nothing else
</code></pre>
</p>

<p class="post-p">
This is called <strong>fine-grained reactivity</strong>. Only the exact thing that changed re-renders. There is no re-render of a component tree, no reconciliation pass, no <code class="inline-code">useMemo</code> dependency arrays. The graph is precise.
</p>

<h2 class="post-h2">The Architecture: A Directed Acyclic Graph</h2>

<p class="post-p">
Under the hood, every signal system builds a <strong>dependency graph</strong>. When you read a signal inside a computation, an edge is added from that signal to the computation. When the signal changes, all downstream computations are marked dirty and re-evaluated.
</p>

<pre class="code-block"><code class="language-text">Signal A ──→ Memo C ──→ Effect D
<p class="post-p">
│
└──→ Memo E ──→ Effect F
</p>

<p class="post-p">
Signal B ──→ Memo E
</code></pre>
</p>

<p class="post-p">
Change Signal A → Memo C and Memo E re-evaluate → Effects D and F run. Signal B is untouched, Memo C is untouched by B's changes. This graph is a <strong>DAG</strong> (directed acyclic graph) — no cycles, no infinite loops, no cascading re-renders.
</p>

<p class="post-p">
Compare to React's model: state change → re-render entire component tree → virtual DOM diff → patch real DOM. Even with memoization (<code class="inline-code">React.memo</code>, <code class="inline-code">useMemo</code>, <code class="inline-code">useCallback</code>), you're <strong>subtracting</strong> work from a full re-render. Signals <strong>add</strong> only the work that's actually needed.
</p>

<h3 class="post-h3">Push-Pull Hybrid</h3>

<p class="post-p">
Most signal implementations use a <strong>push-pull hybrid</strong> strategy:
</p>

<ul class="post-ul"><li class="post-li"><strong>Push phase</strong> (dirty marking): when Signal A changes, it marks all direct dependents as "dirty." This propagates transitively through the graph.</li>
<li class="post-li"><strong>Pull phase</strong> (lazy evaluation): when an effect or memo is actually read, it checks if it's dirty. If so, it re-evaluates its sources, pulling fresh values. This is lazy — if nobody reads a dirty memo, it never re-evaluates.</li>
</ul>
<pre class="code-block"><code class="language-javascript">// Pseudo-implementation of the push-pull hybrid
<p class="post-p">
class Signal {
#value;
#subscribers = new Set();
</p>

<p class="post-p">
constructor(initial) {
this.#value = initial;
}
</p>

<p class="post-p">
get() {
// Track that the current computation depends on this signal
if (currentComputation) {
this.#subscribers.add(currentComputation);
currentComputation.sources.add(this);
}
return this.#value;
}
</p>

<p class="post-p">
set(newValue) {
if (this.#value === newValue) return;
this.#value = newValue;
// PUSH: mark all dependents dirty
for (const sub of this.#subscribers) sub.markDirty();
}
}
</code></pre>
</p>

<p class="post-p">
This hybrid approach means signals are both <strong>glitch-free</strong> (you never see intermediate inconsistent states) and <strong>lazy</strong> (you don't recalculate things nobody is reading).
</p>

<h2 class="post-h2">The Framework Landscape in 2026</h2>

<h3 class="post-h3">SolidJS: The Reference Implementation</h3>

<p class="post-p">
Solid started the signals renaissance. Its implementation is the gold standard — Ryan Carniato's talks and articles are the canonical references. Solid proves that signals can power a full-featured framework with JSX, Suspense, and server-side rendering — all while being faster than vanilla JS in some benchmarks because it does less work.
</p>

<pre class="code-block"><code class="language-jsx">// Solid — signals are the default
<p class="post-p">
const [count, setCount] = createSignal(0);
</p>

<p class="post-p">
// createMemo auto-tracks dependencies
const doubled = createMemo(() =&amp;gt; count() * 2);
</p>

<p class="post-p">
// createEffect runs when dependencies change
createEffect(() =&amp;gt; {
console.log(<code class="inline-code">Count is ${count()}, doubled is ${doubled()}</code>);
});
</p>

<p class="post-p">
return &amp;lt;button onClick={() =&amp;gt; setCount(c =&amp;gt; c + 1)}&amp;gt;
{count()}
&amp;lt;/button&amp;gt;;
</code></pre>
</p>

<p class="post-p">
Key insight: Solid's JSX compiles to direct DOM operations, not virtual DOM. <code class="inline-code">&lt;div&gt;{count()}&lt;/div&gt;</code> compiles to <code class="inline-code">div.textContent = count()</code> with an effect wrapping it. The template is static; only the dynamic parts are wrapped in reactive primitives.
</p>

<h3 class="post-h3">Preact Signals: Signals Without the Framework</h3>

<p class="post-p">
Preact's <code class="inline-code">@preact/signals</code> package is the most versatile — it works <strong>outside</strong> Preact components. You can use signals in vanilla JS, in React components, in Node.js — anywhere. This drove a lot of the "signals as a platform primitive" thinking.
</p>

<pre class="code-block"><code class="language-javascript">import { signal, computed, effect } from '@preact/signals-core';

<p class="post-p">
const name = signal('Ada');
const greeting = computed(() =&amp;gt; <code class="inline-code">Hello, ${name.value}!</code>);
</p>

<p class="post-p">
effect(() =&amp;gt; {
console.log(greeting.value); // "Hello, Ada!"
// Re-runs whenever name.value changes
});
</p>

<p class="post-p">
name.value = 'Grace'; // logs "Hello, Grace!"
</code></pre>
</p>

<p class="post-p">
The killer feature: <code class="inline-code">@preact/signals-react</code> lets you use signals <strong>inside React components</strong>. You get fine-grained reactivity without re-renders, while keeping the React ecosystem. The <code class="inline-code">useSignals()</code> hook or the Babel transform makes <code class="inline-code">.value</code> reads auto-subscribe.
</p>

<h3 class="post-h3">Vue 3: ref() and reactive() Are Signals</h3>

<p class="post-p">
Vue's Composition API was signal-based from the start — they just called them <code class="inline-code">ref()</code> and <code class="inline-code">reactive()</code>. The <code class="inline-code">ref()</code> is literally a signal (<code class="inline-code">.value</code> getter/setter with dependency tracking), and <code class="inline-code">computed()</code> is a memo. Vue's reactivity system has been refined since 2014 and is now battle-tested at the scale of billions of users.
</p>

<pre class="code-block"><code class="language-javascript">import { ref, computed, watchEffect } from 'vue';

<p class="post-p">
const count = ref(0);           // signal
const doubled = computed(() =&amp;gt; count.value * 2); // memo
</p>

<p class="post-p">
watchEffect(() =&amp;gt; {              // effect
console.log(count.value, doubled.value);
});
</code></pre>
</p>

<p class="post-p">
Vue 3's innovation was making signals work with <code class="inline-code">&lt;template&gt;</code> compilation — the compiler can statically analyze which signals a template reads and generate optimal update code, skipping the runtime dependency tracking entirely for static parts.
</p>

<h3 class="post-h3">Angular: Signals Replace Zone.js</h3>

<p class="post-p">
Angular's signals story is the most dramatic. Angular historically used Zone.js — it monkey-patched all async APIs (setTimeout, fetch, event listeners) to trigger change detection across the entire component tree. This was reliable but slow.
</p>

<p class="post-p">
Angular 16-18 introduced signals as an opt-in alternative. Angular 19+ makes them the default. The <code class="inline-code">OnPush</code> change detection strategy is being replaced by signal-based components that only update when their signals change — no Zone.js required.
</p>

<pre class="code-block"><code class="language-typescript">@Component({
<p class="post-p">
template: <code class="inline-code">
&amp;lt;button (click)="increment()"&amp;gt;{{ count() }}&amp;lt;/button&amp;gt;
&amp;lt;p&amp;gt;Double: {{ doubled() }}&amp;lt;/p&amp;gt;
</code>
})
class Counter {
count = signal(0);
doubled = computed(() =&amp;gt; this.count() * 2);
</p>

<p class="post-p">
increment() {
this.count.update(c =&amp;gt; c + 1);
}
}
</code></pre>
</p>

<p class="post-p">
The Angular team has publicly stated that signals are the future of Angular reactivity, and Zone.js will eventually be optional and then deprecated.
</p>

<h3 class="post-h3">Svelte 5: Runes Are Signals</h3>

<p class="post-p">
Svelte's transition is the most interesting because it's a <strong>breaking change</strong> to Svelte's philosophy. Svelte 1-4 used a compiler trick: <code class="inline-code">let count = 0</code> was reactive if it appeared in a <code class="inline-code">.svelte</code> file and was assigned to. The <code class="inline-code">$:</code> label syntax created reactive declarations.
</p>

<p class="post-p">
Svelte 5 replaced this with <strong>runes</strong> — explicit signal-like primitives:
</p>

<pre class="code-block"><code class="language-svelte">&amp;lt;script&amp;gt;
<p class="post-p">
let count = $state(0);        // signal
let doubled = $derived(count * 2); // memo
</p>

<p class="post-p">
$effect(() =&amp;gt; {               // effect
console.log(count, doubled);
});
&amp;lt;/script&amp;gt;
</p>

<p class="post-p">
&amp;lt;button on:click={() =&amp;gt; count++}&amp;gt;
{count}
&amp;lt;/button&amp;gt;
</code></pre>
</p>

<p class="post-p">
The <code class="inline-code">$state()</code> rune is a signal. <code class="inline-code">$derived()</code> is a memo. <code class="inline-code">$effect()</code> is an effect. The Svelte team made the case that implicit reactivity (<code class="inline-code">let</code> just being reactive) was magical and confusing at scale — explicit signals are more predictable and tool-able.
</p>

<h3 class="post-h3">The TC39 Proposal: Signals in JavaScript</h3>

<p class="post-p">
The TC39 Signals proposal (Stage 1, championed by members of the Solid, Preact, Vue, Angular, Svelte, Ember, and Qwik teams) aims to standardize signals as a JavaScript primitive:
</p>

<pre class="code-block"><code class="language-javascript">// Proposed future JavaScript:
<p class="post-p">
const counter = new Signal.State(0);
</p>

<p class="post-p">
// Reading creates a subscription when inside a computed context
counter.get(); // 0
</p>

<p class="post-p">
counter.set(1); // notifies all watchers
</p>

<p class="post-p">
// Derived signals
const doubled = new Signal.Computed(() =&amp;gt; counter.get() * 2);
</p>

<p class="post-p">
// Watch for changes
const watcher = new Signal.subtle.Watcher(() =&amp;gt; {
console.log(<code class="inline-code">Counter changed to ${counter.get()}</code>);
});
</code></pre>
</p>

<p class="post-p">
The proposal is explicitly designed to be a <strong>low-level primitive</strong> that frameworks build on top of — not a user-facing API. The goal is interoperability: a signal created by one framework could be consumed by another. A Preact signal could drive a Lit component. A Solid signal could feed a vanilla JS effect.
</p>

<p class="post-p">
This is the same pattern as <code class="inline-code">CustomEvent</code>, <code class="inline-code">AbortSignal</code>, and <code class="inline-code">Promise</code> — platform primitives that ecosystem tools standardize around. If this lands (likely Stage 2 in 2026, Stage 3 in 2027), it reshapes the framework landscape permanently.
</p>

<h2 class="post-h2">Why Signals Won</h2>

<h3 class="post-h3">1. The Performance Ceiling Is Higher</h3>

<p class="post-p">
React's model has a fundamental limit: every state change triggers a re-render of the owning component and its subtree. You can optimize with <code class="inline-code">memo</code>, <code class="inline-code">useMemo</code>, and <code class="inline-code">useCallback</code>, but these are <strong>manual escape hatches</strong> — you're carving exceptions out of the default full re-render.
</p>

<p class="post-p">
Signals don't have this ceiling. The default is zero wasted work. The graph is precise from the start. There is no subtree re-render to optimize away.
</p>

<pre class="code-block"><code class="language-javascript">// React: changing 'name' re-renders entire component,
<p class="post-p">
// then memo and useMemo prevent downstream re-renders
function Profile({ user }) {
const [name, setName] = useState(user.name);
const [bio, setBio] = useState(user.bio);
</p>

<p class="post-p">
// Every state change re-runs this entire function body
// useMemo prevents Header from re-rendering if deps unchanged
return (
&amp;lt;div&amp;gt;
&amp;lt;Header name={name} /&amp;gt;
&amp;lt;Bio bio={bio} /&amp;gt;
&amp;lt;/div&amp;gt;
);
}
</p>

<p class="post-p">
// Signals: changing name.update() ONLY updates the &amp;lt;h1&amp;gt; textContent
// Nothing else runs. Profile() was called once at setup.
function Profile() {
const name = signal('Ada');
const bio = signal('Programmer');
</p>

<p class="post-p">
return (
&amp;lt;div&amp;gt;
&amp;lt;h1&amp;gt;{name}&amp;lt;/h1&amp;gt;   {/<em> Only this node updates when name changes </em>/}
&amp;lt;p&amp;gt;{bio}&amp;lt;/p&amp;gt;       {/<em> Only this node updates when bio changes </em>/}
&amp;lt;/div&amp;gt;
);
}
</code></pre>
</p>

<h3 class="post-h3">2. The Mental Model Is Simpler</h3>

<p class="post-p">
Hooks introduced a new mental model: the dependency array. <code class="inline-code">useEffect(fn, [dep1, dep2])</code>. Get the deps wrong, and you have stale closures. Forget a dep, and you have a bug. ESLint's <code class="inline-code">exhaustive-deps</code> rule catches most of them, but the cognitive overhead is real.
</p>

<p class="post-p">
Signals eliminate dependency arrays entirely. The system automatically tracks what you read. No <code class="inline-code">[dep1, dep2]</code>. No stale closures. No <code class="inline-code">useCallback</code> to stabilize function references.
</p>

<pre class="code-block"><code class="language-javascript">// React: manual dependency arrays
<p class="post-p">
useEffect(() =&amp;gt; {
fetchUser(id).then(setUser);
}, [id]); // ← don't forget this
</p>

<p class="post-p">
// Signals: automatic tracking
createEffect(() =&amp;gt; {
fetchUser(id()).then(user.set); // reads id(), auto-subscribes
});
</code></pre>
</p>

<h3 class="post-h3">3. Framework Interop Is Possible</h3>

<p class="post-p">
A standardized signal primitive means cross-framework reactivity. Imagine:
</p>

<ul class="post-ul"><li class="post-li">A design system component library built with signals that works in React, Vue, and Solid without wrapper components</li>
<li class="post-li">State management that spans micro-frontends built with different frameworks</li>
<li class="post-li">Browser DevTools with a unified "Signals" panel showing the reactive graph, across all frameworks</li>
</ul>
<p class="post-p">
The TC39 proposal makes this a reality. Like <code class="inline-code">Promise</code> unified async patterns (callbacks, events, streams all interoperate through Promises), <code class="inline-code">Signal</code> would unify reactivity patterns.
</p>

<h2 class="post-h2">The Counter-Arguments</h2>

<p class="post-p">
Signals aren't without critics, and the critique is worth understanding:
</p>

<h3 class="post-h3">"Unidirectional Data Flow Is Simpler"</h3>

<p class="post-p">
React's model has a clear rule: data flows down, events flow up. The re-render-from-root model means the UI is a pure function of state: <code class="inline-code">UI = f(state)</code>. You can always reason about what's on screen by looking at state.
</p>

<p class="post-p">
Signals allow arbitrary connections in the dependency graph. A signal deep in the tree can drive an effect at the top. This is powerful but can create spaghetti graphs that are hard to debug.
</p>

<p class="post-p">
The counter-counter-argument: this is already true in any complex React app with context, Redux, or Zustand. A context change at the top triggers re-renders everywhere. Signals just make the graph explicit and inspectable instead of implicit through component composition.
</p>

<h3 class="post-h3">"It's Just Another Thing to Learn"</h3>

<p class="post-p">
Valid. Signals add <code class="inline-code">.value</code> or <code class="inline-code">()</code> getter/setter patterns. They add <code class="inline-code">createEffect</code>, <code class="inline-code">createMemo</code>, <code class="inline-code">untrack</code>, and <code class="inline-code">batch</code> APIs. The API surface is non-trivial.
</p>

<p class="post-p">
But the counter-argument: hooks were also "another thing to learn" in 2019. Class components to hooks was a bigger mental-model shift than hooks to signals. And signals map directly to concepts developers already understand: getter/setter properties, computed properties, observers.
</p>

<h3 class="post-h3">"React Is Adding a Compiler, Not Signals"</h3>

<p class="post-p">
React's direction is React Compiler (formerly React Forget) — automatic memoization at compile time rather than signals. The argument: you keep the <code class="inline-code">UI = f(state)</code> model, and the compiler handles the optimization. No new primitives to learn.
</p>

<p class="post-p">
This is a valid architectural difference. React is betting that static analysis can optimize re-renders enough to make signals unnecessary. The signals ecosystem is betting that fine-grained reactivity at the primitive level is fundamentally more scalable. Both are being proven out in 2026.
</p>

<h2 class="post-h2">The Ecosystem in 2026</h2>

<p class="post-p">
Beyond the frameworks, a rich signal ecosystem has emerged:
</p>

<p class="post-p">
| Library | Description |
|---------|-------------|
| <strong>@preact/signals-core</strong> | Framework-agnostic signal implementation. The most portable. |
| <strong>signal-utils</strong> (TC39) | Polyfill for the proposed TC39 Signal API |
| <strong>starbeam</strong> | Universal reactivity by the Ember/Glimmer team. Works in any framework. |
| <strong>alien-signals</strong> | Ultra-lightweight (sub-1KB) signals by the Vue team. Designed for embedding. |
| <strong>tanstack-store</strong> | Signals-based state management from the TanStack team. Works with React, Solid, Vue. |
| <strong>valtio-signals</strong> | Proxy-based signals from the Valtio/Zustand team |
| <strong>legend-state</strong> | Optimized signals with built-in persistence and sync |
</p>

<p class="post-p">
The pattern is clear: framework authors are racing to own the signal primitive, while library authors are building framework-agnostic solutions on top.
</p>

<h2 class="post-h2">Should You Adopt Signals in 2026?</h2>

<p class="post-p">
The answer depends on your context:
</p>

<p class="post-p">
<strong>If you're on React:</strong> You don't have to switch. React Compiler will handle a lot of the optimization pain. But you can use <code class="inline-code">@preact/signals-react</code> to get fine-grained reactivity in specific hot paths — large lists, real-time dashboards, canvas-heavy apps — without changing your architecture. It's an opt-in optimization, not a rewrite.
</p>

<p class="post-p">
<strong>If you're starting a new project:</strong> Consider Solid, or Vue with signals mode. The performance characteristics and mental model are genuinely better for many use cases. If you're building a highly interactive app (dashboards, editors, real-time collaboration), signals are a strong default.
</p>

<p class="post-p">
<strong>If you're maintaining an existing app:</strong> Don't rewrite. But do learn signals — the concepts are flowing into every framework, and the TC39 proposal means they'll be a platform primitive within a few years. Understanding the dependency graph, push-pull evaluation, and glitch-free updates will make you a better developer regardless of framework.
</p>

<p class="post-p">
<strong>For library authors:</strong> Start thinking about signals-based APIs. A state management library, a form library, or a data-fetching library built on signals works across frameworks. This is where the ecosystem is heading.
</p>

<h2 class="post-h2">The Big Picture</h2>

<p class="post-p">
Signals winning is part of a larger trend: <strong>the platform is catching up to frameworks</strong>. CSS now has nesting, container queries, anchor positioning, scroll-driven animations, and View Transitions. HTML has <code class="inline-code">&lt;dialog&gt;</code>, <code class="inline-code">&lt;popover&gt;</code>, and the inert attribute. JavaScript is getting signals, decorators, and records &amp; tuples.
</p>

<p class="post-p">
The frameworks that win in this environment are the ones that lean into platform primitives — not the ones that build on top of them and abstract them away. Signals are the reactivity layer of that platform. The framework wars aren't over, but the battle over the reactivity primitive is. Signals won.
</p>
