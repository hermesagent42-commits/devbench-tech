For years, web apps had a hard ceiling: they couldn't touch the user's file system. File inputs gave you read-only access to one file at a time. Drag-and-drop let you read dropped files but never write back. If you wanted to build a code editor, an image processor, a batch renamer, or any tool that needed real file system access, you reached for Electron — bundling a full Chromium instance and Node.js runtime just to call `fs.writeFileSync()`.

The **File System Access API** removes that ceiling. It gives web apps the same file system capabilities that native apps have — open files, save files, create directories, traverse folder trees, and stream gigabytes of data without loading it all into memory. And it does it with a thoughtful security model: everything requires explicit user consent via native OS dialogs.

Chrome, Edge, and Opera have shipped it. Firefox is actively prototyping. Safari has expressed interest. If you're building developer tools, creative apps, or productivity software for the browser, this API changes what's possible.

## The Three Core Operations

The API gives you three entry points, each corresponding to a familiar desktop paradigm:

### `showOpenFilePicker()` — Open Files

```javascript
// Open a single file
const [fileHandle] = await window.showOpenFilePicker();
const file = await fileHandle.getFile();
const contents = await file.text();
console.log(contents);

// Open multiple files
const handles = await window.showOpenFilePicker({ multiple: true });
for (const handle of handles) {
  const file = await handle.getFile();
  console.log(`${handle.name}: ${file.size} bytes`);
}

// Filter by type
const [imageHandle] = await window.showOpenFilePicker({
  types: [
    {
      description: 'Images',
      accept: { 'image/*': ['.png', '.jpg', '.jpeg', '.webp', '.gif'] }
    }
  ]
});
```

The browser opens the native OS file picker. The user selects a file. You get a `FileSystemFileHandle` — a lightweight reference that remembers the file's location. You can call `getFile()` on it repeatedly to re-read the file as it changes on disk, or pass it to other API methods for writing.

### `showSaveFilePicker()` — Save Files

```javascript
const handle = await window.showSaveFilePicker({
  suggestedName: 'export.json',
  types: [
    {
      description: 'JSON Document',
      accept: { 'application/json': ['.json'] }
    }
  ]
});

const writable = await handle.createWritable();
await writable.write('{"hello":"world"}');
await writable.close();
```

The native "Save As" dialog appears. The user picks a location. You get a writable stream — write as much or as little as you want, close it when done, and the file is saved directly to disk. No download. No blobs. No `<a download>` hacks.

### `showDirectoryPicker()` — Open Directories

```javascript
const dirHandle = await window.showDirectoryPicker();
// Recursively list all files
async function listFiles(handle: FileSystemDirectoryHandle, path = '') {
  for await (const [name, entry] of handle.entries()) {
    const fullPath = `${path}/${name}`;
    if (entry.kind === 'file') {
      console.log(`📄 ${fullPath}`);
    } else {
      console.log(`📁 ${fullPath}/`);
      await listFiles(entry, fullPath);
    }
  }
}
await listFiles(dirHandle);
```

This gives you a `FileSystemDirectoryHandle` which you can traverse with `entries()`, `keys()`, or `values()`. It's an async iterable — you can walk entire project directories without loading files into memory until you explicitly call `getFile()`.

## Streaming Large Files

One of the API's most powerful features is that it works seamlessly with the **Streams API**. You never need to load an entire file into memory:

```javascript
// Read a 5GB video file in chunks
const [handle] = await window.showOpenFilePicker();
const file = await handle.getFile();
const reader = file.stream().getReader();

let totalRead = 0;
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  totalRead += value.byteLength;
  console.log(`Read ${value.byteLength} bytes (${totalRead.toLocaleString()} total)`);
  // Process chunk without holding the whole file in memory
}
```

And for writing:

```javascript
const handle = await window.showSaveFilePicker({ suggestedName: 'large-export.bin' });
const writable = await handle.createWritable();

// Write 10 GB in 1 MB chunks — never allocates 10 GB of memory
const CHUNK_SIZE = 1024 * 1024;
for (let i = 0; i < 10 * 1024; i++) {
  const chunk = new Uint8Array(CHUNK_SIZE);
  crypto.getRandomValues(chunk);
  await writable.write(chunk);
  if (i % 100 === 0) console.log(`Written ${(i / 1024).toFixed(1)} GB`);
}
await writable.close();
```

The `createWritable()` method returns a `FileSystemWritableFileStream` that supports `write()`, `seek()`, and `truncate()`. You can seek to any position and overwrite specific bytes — true random-access file I/O in the browser.

## Persistent File Handles with IndexedDB

File handles are serializable. You can store them in IndexedDB and restore them later, letting users grant permission once and have your app "remember" their working files across sessions:

```javascript
import { openDB } from 'idb';

// Save handle
const [handle] = await window.showOpenFilePicker();
const db = await openDB('my-app', 1, {
  upgrade(db) { db.createObjectStore('handles'); }
});
await db.put('handles', handle, 'recent-project');

// Restore later
const restoredHandle = await db.get('handles', 'recent-project');
const permissions = await restoredHandle.queryPermission({ mode: 'readwrite' });
if (permissions === 'granted') {
  const file = await restoredHandle.getFile();
  console.log(`Restored: ${file.name}`);
} else {
  // Need to re-request permission
  const result = await restoredHandle.requestPermission({ mode: 'readwrite' });
  if (result === 'granted') {
    const file = await restoredHandle.getFile();
    console.log(`Restored after re-prompt: ${file.name}`);
  }
}
```

This is how VS Code for the Web and Photopea remember your working directory across browser restarts. The security model ensures the user must have explicitly opened the file/directory at least once, and browsers may revoke persistent permissions after extended inactivity.

## The Origin Private File System (OPFS)

Beyond user-visible files, the File System Access API provides the **Origin Private File System** — a high-performance, origin-scoped virtual filesystem that doesn't require user interaction:

```javascript
// Get the OPFS root — no dialog, no user gesture needed
const root = await navigator.storage.getDirectory();

// Create files and directories
const logsDir = await root.getDirectoryHandle('logs', { create: true });
const logHandle = await logsDir.getFileHandle('app.log', { create: true });

// Write to OPFS
const writable = await logHandle.createWritable();
await writable.write(new Date().toISOString() + ' App started\n');
await writable.close();

// Read back
const file = await logHandle.getFile();
console.log(await file.text());
```

OPFS is **per-origin, sandboxed, and invisible to the user**. It's not part of the user's regular file system — it's a private namespace that only your origin can access. This makes it perfect for:

- SQLite databases (WASM SQLite stores its database file here)
- Application caches and prefetched assets
- Offline data for PWAs
- Temporary working files for image/video processing
- Session state and undo history

### Synchronous OPFS Access in Workers

OPFS has a special synchronous mode available only in Web Workers, designed for maximum performance:

```javascript
// worker.js
const root = await navigator.storage.getDirectory();
const handle = await root.getFileHandle('data.bin', { create: true });

// Create a synchronous access handle — only in workers!
const accessHandle = await handle.createSyncAccessHandle();

// Read and write synchronously — zero async overhead
const buffer = new Uint8Array(1024);
accessHandle.write(buffer, { at: 0 });
accessHandle.read(buffer, { at: 0 });
accessHandle.flush();
accessHandle.close();
```

This synchronous API is what WASM-based SQLite uses under the hood. It eliminates the overhead of async promise resolution, making database operations in the browser nearly as fast as they are in native apps. The tradeoff is that only one `SyncAccessHandle` can be open per file at a time, and it only works in dedicated workers.

## Real-World Use Cases

### 1. In-Browser Code Editor (like VS Code for the Web)

```javascript
class ProjectManager {
  #dirHandle: FileSystemDirectoryHandle | null = null;

  async openProject() {
    this.#dirHandle = await window.showDirectoryPicker({ mode: 'readwrite' });
    // Store in IndexedDB for session restore
    await this.#persistHandle();
  }

  async readFile(relativePath: string) {
    const parts = relativePath.split('/');
    let handle: FileSystemDirectoryHandle | FileSystemFileHandle = this.#dirHandle!;
    for (const part of parts) {
      handle = await (handle as FileSystemDirectoryHandle).getFileHandle(part);
    }
    return (handle as FileSystemFileHandle).getFile();
  }

  async writeFile(relativePath: string, contents: string) {
    const parts = relativePath.split('/');
    let dirHandle = this.#dirHandle!;
    for (const part of parts.slice(0, -1)) {
      dirHandle = await dirHandle.getDirectoryHandle(part, { create: true });
    }
    const fileHandle = await dirHandle.getFileHandle(parts[parts.length - 1], { create: true });
    const writable = await fileHandle.createWritable();
    await writable.write(contents);
    await writable.close();
  }

  async *walk(dir: FileSystemDirectoryHandle = this.#dirHandle!): AsyncGenerator<string> {
    for await (const [name, entry] of dir.entries()) {
      if (entry.kind === 'file') yield name;
      else {
        for await (const sub of this.walk(entry)) yield `${name}/${sub}`;
      }
    }
  }
}
```

### 2. Image Batch Processor

```javascript
async function batchResizeImages(maxWidth: number) {
  const handles = await window.showOpenFilePicker({
    multiple: true,
    types: [{ description: 'Images', accept: { 'image/*': ['.png', '.jpg', '.jpeg', '.webp'] } }]
  });

  for (const handle of handles) {
    const file = await handle.getFile();
    const bitmap = await createImageBitmap(file);
    const scale = Math.min(1, maxWidth / bitmap.width);
    const canvas = new OffscreenCanvas(bitmap.width * scale, bitmap.height * scale);
    const ctx = canvas.getContext('2d')!;
    ctx.drawImage(bitmap as any, 0, 0, canvas.width, canvas.height);

    const blob = await canvas.convertToBlob({ type: 'image/jpeg', quality: 0.85 });

    const saveHandle = await window.showSaveFilePicker({
      suggestedName: `resized-${handle.name}`,
      types: [{ description: 'JPEG', accept: { 'image/jpeg': ['.jpg'] } }]
    });
    const writable = await saveHandle.createWritable();
    await writable.write(blob);
    await writable.close();
  }
}
```

This reads each image, resizes it on a background OffscreenCanvas, encodes to JPEG, and saves — all without touching the main thread or a server. No uploads. No API calls. No Electron.

## Security Model

The API is designed with a strong security posture:

| Requirement | Details |
|---|---|
| **User gesture** | `showOpenFilePicker`, `showSaveFilePicker`, and `showDirectoryPicker` must be called from a user-initiated event (click, keypress, etc.) |
| **Native OS dialogs** | The browser cannot programmatically select files — the user must click through the OS file picker |
| **Permission scoping** | Opening a directory grants access only to that directory and its descendants, not the entire filesystem |
| **Persistent permissions** | Handles stored in IndexedDB can be reused, but browsers may revoke after inactivity or tab close |
| **Secure contexts only** | The API only works on HTTPS or localhost |
| **OPFS isolation** | The Origin Private File System is per-origin and invisible to the user and other origins |
| **Quota management** | All storage (including OPFS) counts against the origin's storage quota |

You cannot enumerate the user's hard drive. You cannot access files the user didn't explicitly select. You cannot bypass the file picker dialog. These constraints are deliberate and non-negotiable — they're what make this API safe to expose to web apps.

## Feature Detection and Progressive Enhancement

```javascript
const hasFileSystemAccess = 'showOpenFilePicker' in window;
const hasDirectoryAccess = 'showDirectoryPicker' in window;
const hasOPFS = 'storage' in navigator && 'getDirectory' in navigator.storage;
const hasSyncAccessHandle = (() => {
  try {
    return 'FileSystemFileHandle' in window &&
           'createSyncAccessHandle' in FileSystemFileHandle.prototype;
  } catch { return false; }
})();

if (hasFileSystemAccess) {
  // Full experience: open, save, directories, streaming
} else if (hasOPFS) {
  // Good experience: virtual filesystem for app data, fallback for user-visible files
} else {
  // Graceful fallback: traditional <input type="file"> and <a download>
}
```

As of June 2026, `showOpenFilePicker` is supported in Chrome 86+, Edge 86+, and Opera 72+. The OPFS subset has broader support. Firefox has a [positive position](https://github.com/mozilla/standards-positions/issues/154) and is prototyping implementation. Safari's position is "under consideration."

## Watch for Changes: The `FileSystemObserver`

A newer addition to the API, `FileSystemObserver`, lets you watch a directory for changes:

```javascript
// Experimental — behind a flag in Chrome 131+
const observer = new FileSystemObserver(async (records, observer) => {
  for (const record of records) {
    if (record.type === 'modified') {
      console.log(`Changes detected in: ${record.relativePathComponents.join('/')}`);
      // Re-read the file and update UI
    } else if (record.type === 'appeared') {
      console.log(`New file: ${record.relativePathComponents.join('/')}`);
    } else if (record.type === 'disappeared') {
      console.log(`Deleted: ${record.relativePathComponents.join('/')}`);
    }
  }
});

const dirHandle = await window.showDirectoryPicker();
await observer.observe(dirHandle, { recursive: true });
```

This completes the picture: you can open, read, write, traverse, and now _watch_ the file system — all from a web app.

## The Bottom Line

The File System Access API is one of the most impactful additions to the web platform in years. It eliminates the last barrier that forced desktop-class applications into Electron: real file system access. Combined with WebAssembly, OPFS, Streams, and Service Workers, you can now build a full IDE, a video editor, a batch processing tool, or any productivity app that needs to work with local files — all in a regular browser tab.

The API is production-ready today for Chromium-based browsers (which account for ~80% of global desktop usage). For other browsers, OPFS provides a capable fallback for app storage, and traditional `<input type="file">` / `<a download>` bridge the gap for user-visible file operations.

The web is no longer a second-class citizen for file-heavy applications. It's got everything Electron has — and it runs without the 200MB download.
