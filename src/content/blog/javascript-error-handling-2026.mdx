## Why Error Handling Still Matters in 2026

Error handling is one of those topics that every developer knows is important but few invest real time in mastering. The result? Logs full of `[Object object]`, swallowed promise rejections, and production incidents that take hours to debug because the error message is `"something went wrong"`.

JavaScript has evolved enormously in this area. ECMAScript 2022 gave us `Error.cause`. ES2021 shipped `AggregateError` and `Promise.any()`. Custom error subclasses with `instanceof` checks have been viable since ES2015, but patterns have matured. In 2026, every major runtime — Node.js 24, Deno 2, Bun 1.3, and all evergreen browsers — supports these features.

This post covers production-grade error handling patterns that go beyond `try/catch` and `console.error`. Every pattern is tested and runs in your browser right now.

## Error.cause: Chaining Errors Without Losing Context

The most common error handling mistake is catching an error and throwing a new one without preserving the original:

```javascript
try {
  await fetchUserData(userId);
} catch (err) {
  throw new Error('Failed to load user');
}
```

The original error — network failure, 404, auth expiry — is gone forever. `Error.cause` fixes this:

```javascript
try {
  await fetchUserData(userId);
} catch (err) {
  throw new Error('Failed to load user', { cause: err });
}
```

The `cause` is preserved on the error object through the entire chain. Your error reporting tool can now unwrap it:

```javascript
function unwrapError(err) {
  const chain = [];
  let current = err;
  while (current) {
    chain.push({
      message: current.message,
      name: current.name,
      stack: current.stack,
    });
    current = current.cause;
  }
  return chain;
}
```

### Real Pattern: API Layer Error Wrapping

Here's a production pattern for wrapping errors at each architectural layer while preserving the full causal chain:

```javascript
class NetworkError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = 'NetworkError';
  }
}

class APIError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = 'APIError';
  }
}

async function apiClient(endpoint) {
  try {
    const response = await fetch(endpoint);
    if (!response.ok) {
      throw new APIError(`HTTP ${response.status}: ${endpoint}`, {
        cause: new Error(await response.text()),
      });
    }
    return response.json();
  } catch (err) {
    if (err instanceof APIError) throw err;
    throw new NetworkError(`Network failure: ${endpoint}`, { cause: err });
  }
}
```

Now when something breaks at 3 AM, your error log shows the full chain: `NetworkError → TypeError → DNS resolution failure`, not just `"Failed to load user"`.

### Gotcha: Error.cause and JSON.stringify

`Error.cause` is not serialized by `JSON.stringify`. If you're sending errors to a logging service:

```javascript
function serializeError(err) {
  return JSON.stringify({
    name: err.name,
    message: err.message,
    stack: err.stack,
    cause: err.cause ? serializeError(err.cause) : null,
  });
}
```

## AggregateError: When Multiple Things Fail at Once

`Promise.all` fails fast — the first rejection throws, and you lose all other results. `Promise.allSettled` gives you all results but no automatic error coalescing. `AggregateError` gives you both:

```javascript
const results = await Promise.allSettled([
  fetchConfig(),
  fetchUser(userId),
  fetchPermissions(userId),
]);

const errors = results
  .filter(r => r.status === 'rejected')
  .map(r => r.reason);

if (errors.length > 0) {
  throw new AggregateError(errors, 'Failed to initialize application');
}
```

The `AggregateError` contains an `errors` property — an array of every individual error. Your error monitoring tool can now report "3 of 4 services failed" instead of just the first one.

### Pattern: Graceful Degradation with AggregateError

A more sophisticated pattern: collect errors but still return partial data:

```javascript
async function loadDashboard(userId) {
  const [config, user, permissions, analytics] = await Promise.allSettled([
    fetchConfig(),
    fetchUser(userId),
    fetchPermissions(userId),
    fetchAnalytics(userId),
  ]);

  const errors = [];
  const data = {};

  if (config.status === 'fulfilled') data.config = config.value;
  else errors.push(config.reason);

  if (user.status === 'fulfilled') data.user = user.value;
  else errors.push(user.reason);

  if (permissions.status === 'fulfilled') data.permissions = permissions.value;
  else errors.push(permissions.reason);

  if (analytics.status === 'fulfilled') data.analytics = analytics.value;
  else errors.push(analytics.reason);

  if (errors.length === 4) {
    throw new AggregateError(errors, 'Dashboard completely failed to load');
  }

  return {
    data,
    warnings: errors.length > 0
      ? new AggregateError(errors, `${errors.length} dashboard modules degraded`)
      : null,
  };
}
```

Your UI can now render whatever data it received and show a warning banner for the degraded modules — instead of a blank white screen.

## Custom Error Classes: instanceof Is Your Friend

Generic `Error` objects force you to parse message strings to understand what happened. Custom error subclasses let you use `instanceof` for clean control flow:

```javascript
class ValidationError extends Error {
  constructor(message, fields, options) {
    super(message, options);
    this.name = 'ValidationError';
    this.fields = fields; // { email: 'Invalid format', password: 'Too short' }
  }
}

class AuthError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = 'AuthError';
  }
}

class RateLimitError extends Error {
  constructor(message, retryAfterMs, options) {
    super(message, options);
    this.name = 'RateLimitError';
    this.retryAfterMs = retryAfterMs;
  }
}

// Usage — clean control flow
try {
  await submitForm(data);
} catch (err) {
  if (err instanceof ValidationError) {
    showFieldErrors(err.fields);
  } else if (err instanceof RateLimitError) {
    scheduleRetry(err.retryAfterMs);
  } else if (err instanceof AuthError) {
    redirectToLogin();
  } else {
    showGenericError();
    reportToSentry(err);
  }
}
```

### The Symbolic Approach for Serializable Errors

If your errors cross process boundaries (worker threads, server to client), use a discriminator property since `instanceof` doesn't survive serialization:

```javascript
const ErrorKind = {
  Validation: 'VALIDATION',
  Auth: 'AUTH',
  RateLimit: 'RATE_LIMIT',
  Network: 'NETWORK',
  Unknown: 'UNKNOWN',
};

class AppError extends Error {
  constructor(kind, message, options) {
    super(message, options);
    this.name = 'AppError';
    this.kind = kind;
  }
}

// On the client
if (err.kind === ErrorKind.Validation) {
  showFieldErrors(err.fields);
}
```

This pattern works across HTTP, WebSocket, postMessage, and even persisted error logs.

## Async Error Propagation: The Silent Killers

### Unhandled Promise Rejections

Node.js 16+ terminates the process on unhandled rejections. Browsers log them to console. Either way, they shouldn't happen. The fix is structural:

```javascript
// BAD — fire and forget
fetchUser(userId); // rejection swallowed

// GOOD — always handle or propagate
fetchUser(userId).catch(reportError);

// BEST — structured async wrapper
async function safeAsync(fn, context) {
  try {
    return await fn();
  } catch (err) {
    reportError(err, context);
    throw err; // re-throw so callers can decide
  }
}

const user = await safeAsync(() => fetchUser(userId), { userId });
```

### Error Boundaries in Event Listeners

Event listeners are another source of swallowed errors:

```javascript
// BAD — uncaught error in listener
button.addEventListener('click', async () => {
  const data = await fetchData(); // rejection unhandled if you don't try/catch
  updateUI(data);
});

// GOOD — wrap the handler
function withErrorBoundary(fn, context) {
  return async (...args) => {
    try {
      return await fn(...args);
    } catch (err) {
      reportError(err, context);
      showUserFriendlyError();
    }
  };
}

button.addEventListener('click', withErrorBoundary(async () => {
  const data = await fetchData();
  updateUI(data);
}, { component: 'DashboardButton' }));
```

## Structured Error Logging: Making Debugging Fast

The quality of your error logs determines how fast you can fix production issues. A good error log entry answers five questions without further investigation:

- **What** happened? (error message + kind)
- **Where** did it happen? (stack trace + component/module)  
- **Why** did it happen? (cause chain)
- **What was the context**? (user ID, route, request payload)
- **When** and **how often**? (timestamp, deduplication key)

```javascript
function createErrorReport(err, context = {}) {
  return {
    timestamp: new Date().toISOString(),
    error: {
      name: err.name,
      message: err.message,
      stack: err.stack,
      kind: err.kind || 'UNKNOWN',
      cause: err.cause ? createErrorReport(err.cause).error : null,
      errors: err instanceof AggregateError
        ? err.errors.map(e => createErrorReport(e).error)
        : undefined,
    },
    context: {
      url: typeof window !== 'undefined' ? window.location.href : undefined,
      userAgent: typeof navigator !== 'undefined' ? navigator.userAgent : undefined,
      ...context,
    },
    fingerprint: hashError(err),
  };
}

function hashError(err) {
  // Simple fingerprint for deduplication — combine name + first stack frame
  const frame = err.stack?.split('\n')[1]?.trim() || '';
  return `${err.name}:${frame}`;
}
```

## Putting It All Together: A Production Error Architecture

Here's a complete error handling layer you can drop into any project:

```javascript
// error-kinds.js
export const ErrorKind = Object.freeze({
  Validation: 'VALIDATION',
  Network: 'NETWORK',
  Auth: 'AUTH',
  RateLimit: 'RATE_LIMIT',
  NotFound: 'NOT_FOUND',
  Server: 'SERVER',
  Unknown: 'UNKNOWN',
});

// app-error.js
export class AppError extends Error {
  constructor(kind, message, { cause, context, ...extra } = {}) {
    super(message, { cause });
    this.name = 'AppError';
    this.kind = kind;
    this.context = context || {};
    Object.assign(this, extra);
  }
}

// async-wrapper.js
export async function attempt(fn, { context, onError } = {}) {
  try {
    return { ok: true, data: await fn() };
  } catch (err) {
    const wrapped = err instanceof AppError
      ? err
      : new AppError(ErrorKind.Unknown, err.message || 'Unknown error', {
          cause: err,
          context,
        });
    
    onError?.(wrapped);
    return { ok: false, error: wrapped };
  }
}

// Usage
const { ok, data, error } = await attempt(
  () => apiClient.fetchUser(userId),
  {
    context: { userId, component: 'UserProfile' },
    onError: (err) => {
      console.error('[UserProfile]', createErrorReport(err));
      analytics.track('error', { kind: err.kind });
    },
  }
);

if (!ok) {
  if (error.kind === ErrorKind.Auth) redirectToLogin();
  if (error.kind === ErrorKind.NotFound) show404();
  else showFallbackError(error);
}
```

## The One Thing to Remember

If you take one thing from this post: **every error should carry its cause, its kind, and its context**. That means using `Error.cause` to chain, custom error subclasses (or a `kind` property) for classification, and a context object with the runtime state that led to the error.

The difference between `"Something went wrong"` and `"ValidationError (kind=VALIDATION): Invalid email format — caused by TypeError: Cannot read properties of undefined — context: { userId: 'abc123', formStep: 2 }"` is the difference between a 4-hour debugging session and a 4-minute fix.

Start with `Error.cause` and a custom error class. Add `AggregateError` when you have parallel operations. Add structured context logging when you hit production. Your future self — waking up to a pager at 3 AM — will thank you.
