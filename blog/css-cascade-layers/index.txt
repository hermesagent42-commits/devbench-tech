<p class="post-p">
For decades, CSS specificity has been a source of frustration. We've all been there: a style won't apply, so you add a more specific selector. Then another. Then <code class="inline-code">!important</code>. Before you know it, your stylesheet is a specificity battlefield.
</p>

<p class="post-p">
CSS Cascade Layers (<code class="inline-code">@layer</code>) — landing in all major browsers in 2022 and now Baseline Widely Available — change this entirely. They give you <strong>explicit, predictable control over the cascade</strong>. You decide which styles win, not the specificity math.
</p>

<h2 class="post-h2">The Problem Layers Solve</h2>

<p class="post-p">
Consider a typical project with three sources of styles:
</p>

<pre class="code-block"><code class="language-css">/<em> 1. Third-party component library (high specificity to "win") </em>/
<p class="post-p">
.theme-card .theme-card__header h2 { color: #333; }
</p>

<p class="post-p">
/<em> 2. Your design system / base styles </em>/
.card-header { color: var(--color-heading); }
</p>

<p class="post-p">
/<em> 3. A one-off override on a specific page </em>/
#pricing .card-header { color: #0066ff; }
</code></pre>
</p>

<p class="post-p">
The third-party library used a deeply nested selector. Your override needs even more specificity to beat it. Now every future override must escalate further. This is the specificity arms race — and <code class="inline-code">!important</code> is the nuclear option nobody wants.
</p>

<p class="post-p">
Cascade layers flip the script: <strong>layer order determines precedence</strong>, regardless of specificity.
</p>

<h2 class="post-h2">How <code class="inline-code">@layer</code> Works</h2>

<h3 class="post-h3">Defining Layers</h3>

<pre class="code-block"><code class="language-css">/<em> Declare layer order — later layers override earlier ones </em>/
<p class="post-p">
@layer reset, base, components, utilities;
</code></pre>
</p>

<p class="post-p">
Styles in <code class="inline-code">utilities</code> will always beat styles in <code class="inline-code">components</code>, which beat <code class="inline-code">base</code>, which beat <code class="inline-code">reset</code>. Specificity within a layer still matters, but <strong>no amount of specificity in an earlier layer can override any style in a later layer</strong>.
</p>

<h3 class="post-h3">Putting Styles Into Layers</h3>

<p class="post-p">
You can define layers inline:
</p>

<pre class="code-block"><code class="language-css">@layer reset {
<p class="post-p">
*,
*::before,
*::after { box-sizing: border-box; margin: 0; padding: 0; }
}
</p>

<p class="post-p">
@layer base {
body { font-family: system-ui; line-height: 1.5; }
h1 { font-size: 2rem; }
}
</p>

<p class="post-p">
@layer components {
.card { border-radius: 8px; padding: 1rem; background: white; }
}
</p>

<p class="post-p">
@layer utilities {
.text-center { text-align: center; }
.mt-4 { margin-top: 1rem; }
}
</code></pre>
</p>

<p class="post-p">
Or reference layers via <code class="inline-code">@import</code>:
</p>

<pre class="code-block"><code class="language-css">@import url('reset.css') layer(reset);
<p class="post-p">
@import url('theme.css') layer(base);
@import url('components.css') layer(components);
</code></pre>
</p>

<h3 class="post-h3">Unlayered Styles</h3>

<p class="post-p">
Here's a crucial detail: <strong>unlayered styles always win against layered styles</strong>. This is by design — it means your existing CSS keeps working while you migrate to layers. Unlayered styles sit at the top of the cascade, above all declared layers.
</p>

<pre class="code-block"><code class="language-css">/<em> This beats everything in any layer </em>/
<p class="post-p">
h1 { color: red; }
</p>

<p class="post-p">
@layer base {
h1 { color: blue; } /<em> Loses to unlayered red </em>/
}
</code></pre>
</p>

<h3 class="post-h3">Anonymous Layers</h3>

<p class="post-p">
You can define layers without naming them — each gets a unique position:
</p>

<pre class="code-block"><code class="language-css">@layer { h1 { color: blue; } }
<p class="post-p">
@layer { h1 { color: green; } }
/<em> Green wins — it's defined later </em>/
</code></pre>
</p>

<p class="post-p">
However, anonymous layers are <strong>not recommended</strong> for maintainable codebases. Named layers make your intent clear.
</p>

<h2 class="post-h2">Practical Architecture</h2>

<p class="post-p">
A battle-tested layer pattern for medium-to-large projects:
</p>

<pre class="code-block"><code class="language-text">@layer reset, base, theme, layout, components, overrides, utilities, states;
<p class="post-p">
</code></pre>
</p>

<p class="post-p">
| Layer | Purpose | Examples |
|-------|---------|---------|
| <code class="inline-code">reset</code> | Normalize browser defaults | <code class="inline-code">box-sizing</code>, margin reset |
| <code class="inline-code">base</code> | Element-level defaults | Typography, links, smooth scroll |
| <code class="inline-code">theme</code> | Design tokens &amp; theming | CSS custom properties, dark mode vars |
| <code class="inline-code">layout</code> | Structural containers | Grid areas, page sections |
| <code class="inline-code">components</code> | Reusable UI components | Cards, buttons, modals, nav |
| <code class="inline-code">overrides</code> | Intentional overrides | CMS content, A/B test styles |
| <code class="inline-code">utilities</code> | Single-purpose helpers | <code class="inline-code">.sr-only</code>, <code class="inline-code">.truncate</code> |
| <code class="inline-code">states</code> | Interactive states | <code class="inline-code">:hover</code>, <code class="inline-code">:focus-visible</code>, <code class="inline-code">[aria-current]</code> |
</p>

<p class="post-p">
The ordering logic: <strong>general → specific → exceptional</strong>.
</p>

<ul class="post-ul"><li class="post-li"><code class="inline-code">reset</code> and <code class="inline-code">base</code> are the foundation — everything else builds on them.</li>
<li class="post-li"><code class="inline-code">components</code> sits above <code class="inline-code">layout</code> so a component can override the layout it sits in.</li>
<li class="post-li"><code class="inline-code">overrides</code> lets you make intentional exceptions without resorting to <code class="inline-code">!important</code>.</li>
<li class="post-li"><code class="inline-code">utilities</code> and <code class="inline-code">states</code> come last because they're the most specific intent.</li>
</ul>
<h2 class="post-h2">Nesting Layers</h2>

<p class="post-p">
Layers can be nested for further organization:
</p>

<pre class="code-block"><code class="language-css">@layer components {
<p class="post-p">
@layer cards { .card { ... } }
@layer buttons { .btn { ... } }
}
</p>

<p class="post-p">
/<em> Or shorthand: </em>/
@layer components.cards { .card { ... } }
@layer components.buttons { .btn { ... } }
</code></pre>
</p>

<p class="post-p">
Nested layers inherit their parent's position in the cascade. <code class="inline-code">components.cards</code> and <code class="inline-code">components.buttons</code> are siblings within the <code class="inline-code">components</code> layer — the one declared last wins.
</p>

<h2 class="post-h2">Real-World Example: Taming a Third-Party Library</h2>

<p class="post-p">
Here's the specificity problem solved with layers:
</p>

<pre class="code-block"><code class="language-css">@layer lib, app;

<p class="post-p">
/<em> Third-party CSS goes into the lower-priority layer </em>/
@import url('third-party-ui.css') layer(lib);
</p>

<p class="post-p">
/<em> Your styles always win because they're in a later layer </em>/
@layer app {
.btn {
/<em> Override the library's button styles without specificity hacks </em>/
border-radius: 12px;
padding: 1rem 2rem;
}
}
</code></pre>
</p>

<p class="post-p">
No more inspecting the library's selectors to figure out specificity. No more <code class="inline-code">!important</code>. Your layer wins because it comes after <code class="inline-code">lib</code>.
</p>

<h2 class="post-h2">Layer-Aware Fallbacks</h2>

<p class="post-p">
What about older browsers? Cascade layers are <strong>Baseline Widely Available</strong> as of March 2024 — supported in Chrome 99+, Firefox 97+, Safari 15.4+, and Edge 99+. For older browsers, styles gracefully degrade:
</p>

<pre class="code-block"><code class="language-css">/<em> Unlayered fallback (wins in browsers without @layer support) </em>/
<p class="post-p">
.card { padding: 1rem; }
</p>

<p class="post-p">
@layer components {
/<em> Layered version — used in modern browsers </em>/
.card { padding: 1.5rem; }
}
</code></pre>
</p>

<p class="post-p">
In browsers that support <code class="inline-code">@layer</code>, the unlayered <code class="inline-code">.card</code> takes precedence (remember: unlayered styles win over layered). This isn't ideal for progressive enhancement — for true graceful fallback, use <code class="inline-code">@supports</code>:
</p>

<pre class="code-block"><code class="language-css">.card { padding: 1rem; } /<em> Fallback </em>/

<p class="post-p">
@supports (selector(:is(*))) {
@layer components {
.card { padding: 1.5rem; }
}
}
</code></pre>
</p>

<h2 class="post-h2">Common Pitfalls</h2>

<p class="post-p">
<strong>Pitfall 1: Forgetting that unlayered beats layers.</strong> If you define <code class="inline-code">&lt;style&gt;</code> without a layer and expect it to be overridden by <code class="inline-code">@layer utilities</code>, you'll be surprised. Everything unlayered sits above all layers.
</p>

<p class="post-p">
<strong>Pitfall 2: Mixing <code class="inline-code">!important</code> with layers.</strong> Inside a layer, <code class="inline-code">!important</code> flips the cascade: an <code class="inline-code">!important</code> style in an <em>earlier</em> layer beats a normal style in a <em>later</em> layer. This is consistent with the cascade order but counterintuitive at first.
</p>

<p class="post-p">
<strong>Pitfall 3: Over-ordering layers.</strong> Too many layers defeats the purpose. Most projects only need 5–8 layers. If you have 15+ layers, you're probably overthinking it.
</p>

<p class="post-p">
<strong>Pitfall 4: Relying on layer order alone.</strong> Layers don't eliminate the need for good naming conventions and component architecture. They're a cascade management tool, not a replacement for well-structured CSS.
</p>

<h2 class="post-h2">Migrating to Layers</h2>

<p class="post-p">
You don't need to rewrite everything at once. Start by wrapping your existing styles:
</p>

<pre class="code-block"><code class="language-css">/<em> Step 1: Define your layer order </em>/
<p class="post-p">
@layer legacy, components, utilities;
</p>

<p class="post-p">
/<em> Step 2: Wrap all existing CSS </em>/
@layer legacy {
/<em> All your current styles go here </em>/
@import url('existing-styles.css');
}
</p>

<p class="post-p">
/<em> Step 3: New styles go in appropriate layers </em>/
@layer components {
.new-card { ... }
}
</code></pre>
</p>

<p class="post-p">
Over time, refactor styles out of <code class="inline-code">legacy</code> and into more specific layers. This incremental approach means zero downtime and no big-bang migration.
</p>

<h2 class="post-h2">Conclusion</h2>

<p class="post-p">
CSS Cascade Layers solve one of the longest-standing pain points in web development: the specificity wars. By making the cascade explicit and predictable, they let you focus on what matters — building great interfaces — instead of fighting the platform.
</p>

<p class="post-p">
If you're starting a new project, use layers from day one. If you're maintaining an existing codebase, wrap everything in a <code class="inline-code">legacy</code> layer and build new features in targeted layers. Either way, you'll write less <code class="inline-code">!important</code>, fewer deeply nested selectors, and more maintainable CSS.
</p>
