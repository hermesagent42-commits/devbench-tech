## The Rendering Problem

Every web page has a render budget. The browser must compute layout, paint pixels, and composite layers for every visible DOM node. The more nodes you have, the more work the browser does — even for content the user can't see yet.

Traditional solutions all have tradeoffs:

1. **Virtual scrolling (react-window, etc.)** — complex, breaks Ctrl+F, hurts SEO
2. **Intersection Observer + lazy loading** — JavaScript-driven, adds latency
3. **Pagination** — hurts UX, breaks user flow
4. **Server-side rendering limits** — reduces what you can build

`content-visibility: auto` is a CSS property that tells the browser: "You can skip rendering this element until it's near the viewport." The browser *natively* skips layout and paint for off-screen content — no JavaScript, no framework, no overhead.

## How content-visibility Works

```css
.off-screen-card {
  content-visibility: auto;
  contain-intrinsic-size: 300px;
}
```

That's it. Two properties.

### The Three Values

| Value | Behavior |
|-------|----------|
| `visible` (default) | Render everything normally — no skipping |
| `auto` | Browser skips rendering for off-screen elements, renders them as they approach the viewport |
| `hidden` | Skip rendering entirely. Like `display: none` but preserves the element's intrinsic size (no layout shift when toggled) |

### contain-intrinsic-size

When an element's rendering is skipped, the browser still needs to reserve space for it (otherwise you get layout shifts when it renders). `contain-intrinsic-size` tells the browser the placeholder dimensions:

```css
.off-screen-card {
  content-visibility: auto;
  contain-intrinsic-size: 300px 200px; /* width height */
}
```

You can also use the `auto` keyword with the `contain-intrinsic-size` shorthand:

```css
.off-screen-card {
  content-visibility: auto;
  contain-intrinsic-size: auto 300px;
}
```

The `auto` keyword remembers the last rendered size, so as cards render and scroll away, the browser uses their actual dimensions instead of a guess.

|----------|---------|--------------------------------|-------------|
| 1,000 cards (100 rendered, 900 skipped) | 1,200ms LCP | 180ms LCP | **85% faster** |

The key insight: the browser only renders what the user can see. On pages with hundreds or thousands of repeated content blocks, this is transformative.

## Production-Ready Patterns

### Pattern 1: Infinite Scroll Feed

```css
.feed-item {
  content-visibility: auto;
  contain-intrinsic-size: auto 280px;
  min-height: 280px;
}
```

Each feed item gets its own `content-visibility`. As the user scrolls, items enter the render zone and the browser paints them. Items that scroll far off-screen get their rendering skipped again. All native, zero JavaScript for the rendering behavior.

### Pattern 2: Tabbed Content

```css
.tab-panel {
  content-visibility: hidden;
}

.tab-panel.active {
  content-visibility: visible;
}
```

Hidden tab panels skip rendering entirely. When activated, they render instantly — no JavaScript needed to measure or animate.

### Pattern 3: Accordion / Disclosure

```html
<style>
  .accordion-body {
    content-visibility: hidden;
    contain-intrinsic-size: auto 200px;
  }
  .accordion-body.open {
    content-visibility: visible;
  }
</style>

<details>
  <summary>Show More</summary>
  <div class="accordion-body">
    <!-- Large amount of content — skipped until opened -->
  </div>
</details>
```

### Pattern 4: Search Results

```css
.result-card {
  content-visibility: auto;
  contain-intrinsic-size: auto 120px;
}
```

Search result pages often render 50+ result cards. With `content-visibility: auto`, only the first 3-5 get initial layout and paint. The rest render as the user scrolls.

### Pattern 5: E-Commerce Product Grid

```css
.product-grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(280px, 1fr));
}

.product-card {
  content-visibility: auto;
  contain-intrinsic-size: 400px;
}
```

A typical product listing page has 50-200 product cards. Without `content-visibility`, the browser computes layout for all 200 cards on page load. With it, only the first row or two render.

## When NOT to Use content-visibility

### ❌ Small Pages

If your page has fewer than 20-30 content blocks, `content-visibility` adds overhead with no benefit. The optimization cost (checking visibility) outweighs the savings.

### ❌ Critical Above-the-Fold Content

Never apply `content-visibility: auto` to hero sections, headers, navigation, or anything in the initial viewport. The browser will skip rendering it, then immediately realize it's visible and render it — a net loss.

### ❌ Interactive Elements

Avoid on elements with:
- Form inputs or textareas
- Focusable controls that need immediate interaction
- Iframes
- Canvas elements with active JavaScript
- WebGL content

### ❌ Elements with JavaScript-Dependent Layout

If your JavaScript measures the element's dimensions or position before the user scrolls to it, `content-visibility` will break those measurements (the element hasn't been laid out yet).

## content-visibility vs. Alternative Approaches

| Approach | Setup Complexity | Ctrl+F Works | SEO | Scrollbar Accuracy |
|----------|-----------------|--------------|-----|-------------------|
| content-visibility: auto | 2 CSS lines | ✅ | ✅ | ✅ |
| Virtual scrolling | 200+ JS lines | ❌ | ❌ | ❌ |
| IntersectionObserver + lazy load | 50+ JS lines | ✅ | ✅ (SSR) | ⚠️ |

`content-visibility` is the simplest approach with the best user experience — it preserves all native browser behaviors (find-in-page, accessibility tree, scroll position).

## Measuring the Impact

Use Chrome DevTools Performance panel to measure before/after:

1. Open DevTools → Performance tab
2. Record a page load without `content-visibility`
3. Apply `content-visibility: auto` to off-screen elements
4. Record again
5. Compare **Layout** and **Paint** times

You should see dramatic reductions in layout work. The "Rendering" flame chart section will be significantly shorter.

Also monitor real-user metrics:
- **LCP** (Largest Contentful Paint) — should improve because the browser has less rendering work
- **TBT** (Total Blocking Time) — should improve because fewer layout calculations block the main thread
- **INP** (Interaction to Next Paint) — should improve because layout is deferred

## The Bottom Line

`content-visibility: auto` is the closest thing CSS has to a free performance button. Two lines of CSS, no JavaScript, no library, no framework dependency. It works with every rendering approach — SSR, CSR, static, hybrid — because it operates at the browser level.

For pages with more than 30 repeating content blocks, `content-visibility` should be the default. It preserves all native browser features (find-in-page, accessibility, scroll position) while dramatically reducing rendering work.
