<p class="post-p">
JavaScript error handling has quietly gotten <strong>much</strong> better. <code class="inline-code">Error.cause</code> (Baseline 2023), <code class="inline-code">AggregateError</code> (ES2021), and a rich ecosystem of patterns mean you can now build error systems that are traceable, composable, and debuggable — without third-party libraries. Yet most codebases still throw raw strings or use <code class="inline-code">console.error</code> and call it a day.
</p>

<p class="post-p">
Let's fix that. Here's everything you need to know about structured error handling in 2026, from the language primitives to production patterns.
</p>

<h2 class="post-h2">Error.cause: Chaining Errors with Context</h2>

<p class="post-p">
The <code class="inline-code">cause</code> property on the <code class="inline-code">Error</code> constructor lets you chain errors while preserving the original stack trace and context. If you've ever caught an error, wrapped it, and lost the original — this is for you.
</p>

<pre class="code-block"><code class="language-javascript">async function fetchUser(id) {
<p class="post-p">
try {
const response = await fetch(<code class="inline-code">/api/users/${id}</code>);
if (!response.ok) {
throw new Error(<code class="inline-code">User fetch failed: ${response.status}</code>, {
cause: { status: response.status, id, endpoint: <code class="inline-code">/api/users/${id}</code> }
});
}
return response.json();
} catch (err) {
if (err instanceof TypeError) {
throw new Error('Network error fetching user', { cause: err });
}
throw err;
}
}
</p>

<p class="post-p">
try {
await fetchUser('usr_123');
} catch (err) {
console.log(err.message);        // "Network error fetching user"
console.log(err.cause.message);  // "Failed to fetch" (original TypeError)
// Full chain is preserved in err.stack
}
</code></pre>
</p>

<p class="post-p">
The <code class="inline-code">cause</code> value can be <strong>any JavaScript value</strong> — another error, an object, a string. The browser/Node.js will include it in the stack trace automatically when it's an <code class="inline-code">Error</code> instance:
</p>

<pre class="code-block"><code class="language-text">Error: Network error fetching user
<p class="post-p">
at fetchUser (api.js:12:13)
Caused by: TypeError: Failed to fetch
at fetchUser (api.js:9:17)
</code></pre>
</p>

<p class="post-p">

<p class="post-p">
Now every layer in your call stack can inspect the full causal chain without parsing error messages.

<h2 class="post-h2">AggregateError: Handling Multiple Failures</h2>

<p class="post-p">
<code class="inline-code">AggregateError</code> collects multiple errors into one. Essential for batch operations, <code class="inline-code">Promise.allSettled()</code>, and validation.
</p>

<pre class="code-block"><code class="language-javascript">// Promise.allSettled() naturally pairs with AggregateError
<p class="post-p">
async function loadMultipleResources(urls) {
const results = await Promise.allSettled(urls.map(u =&amp;gt; fetch(u)));
</p>

<p class="post-p">
const failures = results
.filter(r =&amp;gt; r.status === 'rejected')
.map((r, i) =&amp;gt; new Error(<code class="inline-code">Failed to load ${urls[i]}: ${r.reason.message}</code>, {
cause: r.reason
}));
</p>

<p class="post-p">
if (failures.length &amp;gt; 0) {
throw new AggregateError(failures, <code class="inline-code">${failures.length} of ${urls.length} resources failed to load</code>);
}
</p>

<p class="post-p">
return results.map(r =&amp;gt; r.value);
}
</p>

<p class="post-p">
try {
await loadMultipleResources(['/a.json', '/b.json', '/c.json']);
} catch (err) {
if (err instanceof AggregateError) {
console.log(err.message);          // "2 of 3 resources failed to load"
for (const e of err.errors) {      // err.errors is the array of sub-errors
console.log(' -', e.message);
}
}
}
</code></pre>
</p>

<h2 class="post-h2">Custom Error Classes: instanceof Actually Works</h2>

<p class="post-p">
JavaScript errors have a class hierarchy waiting to be used. Stop throwing raw strings.
</p>

<pre class="code-block"><code class="language-javascript">class AppError extends Error {
<p class="post-p">
constructor(message, options = {}) {
super(message, options);
this.name = this.constructor.name;
this.timestamp = new Date().toISOString();
this.code = options.code ?? 'UNKNOWN_ERROR';
this.severity = options.severity ?? 'error';   // 'warn' | 'error' | 'fatal'
}
</p>

<p class="post-p">
toJSON() {
return {
name: this.name,
message: this.message,
code: this.code,
severity: this.severity,
timestamp: this.timestamp,
cause: this.cause instanceof Error ? this.cause.message : this.cause,
};
}
}
</p>

<p class="post-p">
class ValidationError extends AppError {
constructor(message, { fields, ...rest } = {}) {
super(message, { code: 'VALIDATION_ERROR', severity: 'warn', ...rest });
this.fields = fields ?? {};
}
}
</p>

<p class="post-p">
class DatabaseError extends AppError {
constructor(message, { query, params, ...rest } = {}) {
super(message, { code: 'DB_ERROR', severity: 'error', ...rest });
this.query = query;
this.params = params;
}
}
</p>

<p class="post-p">
class AuthError extends AppError {
constructor(message, options = {}) {
super(message, { code: 'AUTH_ERROR', severity: 'warn', ...options });
}
}
</code></pre>
</p>

<p class="post-p">
Now you can discriminate errors cleanly:
</p>

<pre class="code-block"><code class="language-javascript">try {
<p class="post-p">

}
</code></pre>
</p>

<h2 class="post-h2">The Error Hierarchy Pattern</h2>

<p class="post-p">
Structure your errors in a tree. This makes catch clauses precise and logging consistent:
</p>

<pre class="code-block"><code class="language-text">Error
<p class="post-p">
└── AppError (base class for your app)
├── ValidationError (400)
├── AuthError (401)
├── ForbiddenError (403)
├── NotFoundError (404)
├── ConflictError (409)
├── RateLimitError (429)
├── DatabaseError (500)
└── ExternalServiceError (502/504)
</code></pre>
</p>

<pre class="code-block"><code class="language-javascript">class NotFoundError extends AppError {
<p class="post-p">
constructor(resource, id) {
super(<code class="inline-code">${resource} not found: ${id}</code>, {
code: 'NOT_FOUND',
severity: 'warn',
cause: { resource, id },
});
}
}
</p>

<p class="post-p">
class RateLimitError extends AppError {
constructor({ retryAfter, limit, remaining }) {
super('Rate limit exceeded', {
code: 'RATE_LIMITED',
severity: 'warn',
cause: { retryAfter, limit, remaining },
});
this.retryAfter = retryAfter;
}
}
</code></pre>
</p>

<p class="post-p">
Now your HTTP layer becomes a straightforward map:
</p>

<pre class="code-block"><code class="language-javascript">const ERROR_STATUS_MAP = new Map([
<p class="post-p">
[ValidationError, 400],
[AuthError, 401],

</p>

<p class="post-p">

}

}
</code></pre>

<h2 class="post-h2">The One Thing Most Teams Get Wrong</h2>

<p class="post-p">
The most common anti-pattern: <strong>catching too broadly and swallowing errors</strong>.
</p>

<pre class="code-block"><code class="language-javascript">// ❌ BAD: swallows all errors, loses context
<p class="post-p">
try {
await processOrder(order);
} catch (err) {
console.log('Order failed');
// Order is silently dropped. No retry. No alert.
}
</p>

<p class="post-p">
// ✅ GOOD: specific handling with escalation
try {
await processOrder(order);
} catch (err) {
if (err instanceof ValidationError) {
notifyCustomer(order.userId, 'Please correct your order', err.fields);
return;
}
if (err instanceof PaymentError) {
await retryPayment(order, err.cause);
return;
}
// Unknown errors: escalate loudly
logError(err, { orderId: order.id, severity: 'fatal' });
await alertOnCall(<code class="inline-code">Order ${order.id} failed with unknown error</code>, err);
}
</code></pre>
</p>

<p class="post-p">
The rule: <strong>only catch errors you can handle</strong>. If you can't meaningfully recover, let them propagate to a top-level boundary.
</p>

<h2 class="post-h2">Quick Reference: Error API Cheatsheet</h2>

<p class="post-p">
| API | When to Use | Example |
|-----|------------|---------|
| <code class="inline-code">new Error(msg, { cause })</code> | Wrapping errors with context | <code class="inline-code">throw new Error('API fail', { cause: fetchErr })</code> |
| <code class="inline-code">AggregateError(errors, msg)</code> | Multiple failures at once | <code class="inline-code">Promise.allSettled()</code> results, batch validation |
| <code class="inline-code">err.cause</code> | Inspecting the origin error | <code class="inline-code">err.cause.message</code> or <code class="inline-code">err.cause.status</code> |
| <code class="inline-code">err.stack</code> | Debugging — contains <code class="inline-code">Caused by:</code> chain | Log in development, strip in production |
| <code class="inline-code">instanceof</code> | Discriminating error types | <code class="inline-code">err instanceof ValidationError</code> |
| Custom <code class="inline-code">Error</code> subclasses | Domain-specific errors | <code class="inline-code">class PaymentError extends AppError</code> |
| <code class="inline-code">err.toJSON()</code> | Structured serialization | API responses, payload logging |
| <code class="inline-code">AbortController.signal.reason</code> | Cancellation reason | <code class="inline-code">err.cause === signal.reason</code> |
</p>

<h2 class="post-h2">Conclusion</h2>

<p class="post-p">
JavaScript's error handling primitives have matured. <code class="inline-code">Error.cause</code> gives you causal chains without losing context. <code class="inline-code">AggregateError</code> handles batch failures cleanly. Custom error classes with <code class="inline-code">instanceof</code> eliminate fragile string matching. And a consistent error hierarchy makes your entire stack debuggable.
</p>

<p class="post-p">
The key shift: <strong>treat errors as data, not strings</strong>. Structure them, type them, chain them. Your future self debugging a production incident at 3 AM will thank you.
</p>
