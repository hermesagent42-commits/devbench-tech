<p class="post-p">
For 30 years, the web has had a glaring UX deficiency: <strong>hard page cuts</strong>.
</p>

<p class="post-p">
Click a link in a multi-page app (the majority of the web) and the screen flashes white for 200-800ms before the next page paints. Single-page apps solved this with JavaScript routing and animation libraries like Framer Motion, GSAP, or <code class="inline-code">react-transition-group</code> — at the cost of bundle size, complexity, and accessibility regressions.
</p>

<p class="post-p">
The View Transitions API solves this natively. The browser captures snapshots of the old and new DOM states, cross-fades between them, and handles the entire transition on the compositor thread — <strong>hardware-accelerated, jank-free, zero JavaScript</strong>.
</p>

<p class="post-p">
As of mid-2026, it's <strong>Baseline across all browsers</strong>: Chrome 111+, Safari 18.2+, Firefox 144+, Edge 111+, Opera 97+, and Samsung Internet 23+. Firefox was the last holdout and shipped it in April 2026. If you target modern browsers, you can use it today.
</p>

<p class="post-p">
Let's build real transitions.
</p>

<hr class="post-hr" />

<h2 class="post-h2">How View Transitions Work Under the Hood</h2>

<p class="post-p">
The browser takes a <strong>snapshot</strong> of the page at two moments — the "old" state and the "new" state — and plays a cross-fade animation between them. This happens on the compositor thread, so the main thread stays free for JavaScript and layout work.
</p>

<pre class="code-block"><code class="language-text">Old DOM Snapshot ──[ cross-fade ]──&amp;gt; New DOM Snapshot
<p class="post-p">
↑                                  ↑
before swap                      after swap
</code></pre>
</p>

<p class="post-p">
There are two modes:
</p>

<ul class="post-ul"><li class="post-li"><strong>Same-document transitions</strong> — Animate DOM changes within a single page (SPA). Triggered via <code class="inline-code">document.startViewTransition()</code>.</li>
<li class="post-li"><strong>Cross-document transitions</strong> — Animate full page navigations between different URLs (MPA). Triggered with a single CSS at-rule: <code class="inline-code">@view-transition</code>.</li>
</ul>
<hr class="post-hr" />

<h2 class="post-h2">Same-Document Transitions: SPA State Changes</h2>

<p class="post-p">
The classic use case: you have a list of items, the user clicks one, and the content area updates. With View Transitions, the old content <em>cross-fades</em> into the new content — no jarring replacement.
</p>

<pre class="code-block"><code class="language-js">function navigateToDetail(id) {
<p class="post-p">
// Wrap your DOM update in startViewTransition()
document.startViewTransition(() =&amp;gt; {
// This callback runs synchronously — update the DOM here
document.getElementById('content').innerHTML = renderDetail(id);
});
}
</code></pre>
</p>

<p class="post-p">
That's it. The browser:
</p>
<ul class="post-ul"><li class="post-li">Captures a snapshot of the current <code class="inline-code">#content</code></li>
<li class="post-li">Runs your callback to update the DOM</li>
<li class="post-li">Captures a snapshot of the new <code class="inline-code">#content</code></li>
<li class="post-li">Cross-fades between them over ~300ms (configurable)</li>
</ul>
<p class="post-p">
<strong>No animation library. No CSS keyframes to write. Just one function call.</strong>
</p>

<p class="post-p">
Here it is in React:
</p>

<pre class="code-block"><code class="language-jsx">function ProductDetail({ productId }) {
<p class="post-p">
const navigate = (id) =&amp;gt; {
if (document.startViewTransition) {
document.startViewTransition(() =&amp;gt; setActiveId(id));
} else {
setActiveId(id); // fallback
}
};
// ...
}
</code></pre>
</p>

<p class="post-p">
And in vanilla JS with <code class="inline-code">fetch</code>:
</p>

<pre class="code-block"><code class="language-js">async function loadPage(url) {
<p class="post-p">
const res = await fetch(url);
const html = await res.text();
</p>

<p class="post-p">
document.startViewTransition(() =&amp;gt; {
document.getElementById('app').innerHTML = html;
});
}
</code></pre>
</p>

<hr class="post-hr" />

<h2 class="post-h2">Cross-Document Transitions: MPA Navigation</h2>

<p class="post-p">
This is the bigger deal. <strong>MPA cross-document transitions require zero JavaScript.</strong> You add one line of CSS to both pages, and the browser handles everything.
</p>

<p class="post-p">
Add this to your global CSS:
</p>

<pre class="code-block"><code class="language-css">@view-transition {
<p class="post-p">
navigation: auto;
}
</code></pre>
</p>

<p class="post-p">
Now every same-origin navigation (clicking a link to a page on your site) gets a smooth cross-fade. No JS. No SPA framework. No build step.
</p>

<p class="post-p">
The <code class="inline-code">@view-transition</code> at-rule has two values:
</p>
<ul class="post-ul"><li class="post-li"><code class="inline-code">navigation: auto</code> — enable transitions for all same-origin navigations</li>
<li class="post-li"><code class="inline-code">navigation: none</code> — disable transitions (the default)</li>
</ul>
<p class="post-p">
You can scope it:
</p>

<pre class="code-block"><code class="language-css">/<em> Only transition between blog pages </em>/
<p class="post-p">
@view-transition {
navigation: auto;
}
</p>

<p class="post-p">
/<em> But NOT on the search page (too heavy) </em>/
.search-page {
view-transition-name: none;
}
</code></pre>
</p>

<p class="post-p">
This is what makes View Transitions a <strong>web platform feature, not a JavaScript feature</strong>. It works with:
</p>
<ul class="post-ul"><li class="post-li">Plain HTML files served by any backend</li>
<li class="post-li">Static site generators (Next.js export, Astro, Hugo, 11ty)</li>
<li class="post-li">Server-rendered frameworks with traditional anchor tags</li>
<li class="post-li">Any <code class="inline-code">&lt;a href="..."&gt;</code> click on the same origin</li>
</ul>
<hr class="post-hr" />

<h2 class="post-h2">Named View Transitions: Shared-Element Morphing</h2>

<p class="post-p">
The default cross-fade is nice. But the real power is <strong>named view transitions</strong> — morphing a specific element from the old page into the new page.
</p>

<p class="post-p">
Give an element a <code class="inline-code">view-transition-name</code>:
</p>

<pre class="code-block"><code class="language-css">/<em> On the list page </em>/
<p class="post-p">
.product-card-42 {
view-transition-name: product-42;
}
</p>

<p class="post-p">
/<em> On the detail page </em>/
.product-hero {
view-transition-name: product-42;
}
</code></pre>
</p>

<p class="post-p">
The browser sees the same <code class="inline-code">view-transition-name</code> on both pages and <strong>morphs</strong> the element — animating position, size, and shape — while the rest of the page cross-fades normally.
</p>

<p class="post-p">
This is the "shared element transition" pattern that Material Design made famous. No JavaScript tweening. No layout math. The browser handles it natively.
</p>

<pre class="code-block"><code class="language-html">&amp;lt;!-- List page --&amp;gt;
<p class="post-p">
&amp;lt;a href="/product/42" class="product-card" style="view-transition-name: product-42"&amp;gt;
&amp;lt;img src="thumb-42.jpg" alt="Widget" /&amp;gt;
&amp;lt;h3&amp;gt;Widget Pro&amp;lt;/h3&amp;gt;
&amp;lt;/a&amp;gt;
</p>

<p class="post-p">
&amp;lt;!-- Detail page --&amp;gt;
&amp;lt;div class="product-hero" style="view-transition-name: product-42"&amp;gt;
&amp;lt;img src="hero-42.jpg" alt="Widget" /&amp;gt;
&amp;lt;/div&amp;gt;
</code></pre>
</p>

<p class="post-p">
&gt; <strong>Critical rule</strong>: A <code class="inline-code">view-transition-name</code> must be unique on the page at any given moment. If two elements share the same name during a transition, the transition aborts with a warning. Use unique names like <code class="inline-code">product-${id}</code> or <code class="inline-code">card-${index}</code>.
</p>

<hr class="post-hr" />

<h2 class="post-h2">Customizing the Transition Animation</h2>

<p class="post-p">
The default cross-fade is 300ms with an <code class="inline-code">ease</code> timing function. You can customize it via the <code class="inline-code">::view-transition</code> pseudo-element tree:
</p>

<pre class="code-block"><code class="language-css">/<em> Customize the root cross-fade </em>/
<p class="post-p">
::view-transition-old(root) {
animation: fade-out 0.4s cubic-bezier(0.4, 0, 0.2, 1);
}
</p>

<p class="post-p">
::view-transition-new(root) {
animation: fade-in 0.4s cubic-bezier(0.4, 0, 0.2, 1);
}
</p>

<p class="post-p">
@keyframes fade-out {
to { opacity: 0; }
}
</p>

<p class="post-p">
@keyframes fade-in {
from { opacity: 0; }
}
</code></pre>
</p>

<p class="post-p">
The full pseudo-element tree:
</p>

<pre class="code-block"><code class="language-text">::view-transition
<p class="post-p">
├── ::view-transition-group(root)
│   ├── ::view-transition-image-pair(root)
│   │   ├── ::view-transition-old(root)
│   │   └── ::view-transition-new(root)
</code></pre>
</p>

<p class="post-p">
For named transitions, replace <code class="inline-code">root</code> with the name:
</p>

<pre class="code-block"><code class="language-css">::view-transition-old(product-42) {
<p class="post-p">
animation: slide-out 0.4s ease;
}
</p>

<p class="post-p">
::view-transition-new(product-42) {
animation: slide-in 0.4s ease;
}
</p>

<p class="post-p">
@keyframes slide-out {
to {
transform: translateX(-30px);
opacity: 0;
}
}
</p>

<p class="post-p">
@keyframes slide-in {
from {
transform: translateX(30px);
opacity: 0;
}
}
</code></pre>
</p>

<h3 class="post-h3">Directional Navigation</h3>

<p class="post-p">
This is where View Transitions shines. Detect navigation direction and animate accordingly:
</p>

<pre class="code-block"><code class="language-css">/<em> Forward navigation: slide left </em>/
<p class="post-p">
html:active-view-transition-type(forward) ::view-transition-old(root) {
animation: slide-to-left 0.3s ease both;
}
html:active-view-transition-type(forward) ::view-transition-new(root) {
animation: slide-from-right 0.3s ease both;
}
</p>

<p class="post-p">
/<em> Back navigation: slide right </em>/
html:active-view-transition-type(back) ::view-transition-old(root) {
animation: slide-to-right 0.3s ease both;
}
html:active-view-transition-type(back) ::view-transition-new(root) {
animation: slide-from-left 0.3s ease both;
}
</p>

<p class="post-p">
@keyframes slide-to-left {
to { transform: translateX(-100%); }
}
@keyframes slide-to-right {
to { transform: translateX(100%); }
}
@keyframes slide-from-right {
from { transform: translateX(100%); }
}
@keyframes slide-from-left {
from { transform: translateX(-100%); }
}
</code></pre>
</p>

<p class="post-p">
Set the transition type in JavaScript when navigating:
</p>

<pre class="code-block"><code class="language-js">// Forward navigation
<p class="post-p">
document.startViewTransition({
update: () =&amp;gt; navigateForward(),
types: ['forward']
});
</p>

<p class="post-p">
// For cross-document, set via the pageswap event
window.addEventListener('pageswap', (e) =&amp;gt; {
if (e.viewTransition) {
const direction = getNavigationDirection();
e.viewTransition.types.add(direction);
}
});
</code></pre>
</p>

<h2 class="post-h2">Practical Patterns</h2>

<h3 class="post-h3">Pattern 1: List to Detail with Image Morph</h3>

<p class="post-p">
The most impactful MPA pattern. Product listings, blog post cards, photo galleries — anything where a thumbnail expands into a hero.
</p>

<pre class="code-block"><code class="language-css">/<em> Both pages need this </em>/
<p class="post-p">
@view-transition {
navigation: auto;
}
</p>

<p class="post-p">
/<em> List page — each card </em>/
.product-card {
view-transition-name: product-card;
contain: layout;
}
</p>

<p class="post-p">
/<em> Detail page — the hero </em>/
.product-hero-image {
view-transition-name: product-card;
contain: layout;
}
</code></pre>
</p>

<p class="post-p">
The <code class="inline-code">contain: layout</code> is important — it tells the browser to treat this element as an isolated layout root, preventing the snapshot from capturing layout shifts in ancestor elements.
</p>

<h3 class="post-h3">Pattern 2: Stack Navigator (Push/Pop)</h3>

<p class="post-p">
For apps with a drill-down flow (Settings &gt; Account &gt; Security), animate pages like a stack:
</p>

<pre class="code-block"><code class="language-css">@view-transition {
<p class="post-p">
navigation: auto;
}
</p>

<p class="post-p">
/<em> Push: new page slides in from right </em>/
::view-transition-new(root) {
animation: slide-in-right 0.3s ease both;
}
::view-transition-old(root) {
animation: slide-out-left 0.3s ease both;
}
</code></pre>
</p>

<p class="post-p">
When the user clicks "Back," the browser automatically reverses the animation — the old page slides in from the left. No code needed.
</p>

<h3 class="post-h3">Pattern 3: Filtering with View Transitions</h3>

<p class="post-p">
Animate a product grid when filters change:
</p>

<pre class="code-block"><code class="language-js">function applyFilter(category) {
<p class="post-p">
document.startViewTransition(() =&amp;gt; {
// Re-render the grid with filtered results
renderProducts(filterByCategory(category));
});
}
</code></pre>
</p>

<p class="post-p">
Each product card could have a <code class="inline-code">view-transition-name</code>, so cards that exist in both old and new grids morph to their new positions rather than fading out and back in. This is the "layout animation" pattern that used to require FLIP technique calculations.
</p>

<h3 class="post-h3">Pattern 4: Dark Mode Toggle</h3>

<p class="post-p">
The simplest SPA transition:
</p>

<pre class="code-block"><code class="language-js">function toggleDarkMode() {
<p class="post-p">
document.startViewTransition(() =&amp;gt; {
document.documentElement.classList.toggle('dark');
});
}
</code></pre>
</p>

<p class="post-p">
Gives a smooth cross-fade between light and dark themes. Add this CSS for a radial reveal effect:
</p>

<pre class="code-block"><code class="language-css">::view-transition-old(root),
<p class="post-p">
::view-transition-new(root) {
animation: none;
mix-blend-mode: normal;
}
</p>

<p class="post-p">
.dark::view-transition-old(root) {
z-index: 1;
}
.dark::view-transition-new(root) {
z-index: 9999;
}
</p>

<p class="post-p">
::view-transition-new(root) {
animation: reveal 0.5s ease;
}
</p>

<p class="post-p">
@keyframes reveal {
from {
clip-path: circle(0% at 100% 0%);
}
to {
clip-path: circle(150% at 100% 0%);
}
}
</code></pre>
</p>

<h2 class="post-h2">Performance and Best Practices</h2>

<h3 class="post-h3">The <code class="inline-code">contain</code> Property</h3>

<p class="post-p">
Every element with <code class="inline-code">view-transition-name</code> should have <code class="inline-code">contain: layout</code> (or <code class="inline-code">contain: paint</code> at minimum). This isolates the element from layout changes in ancestors, ensuring clean snapshots.
</p>

<pre class="code-block"><code class="language-css">.card {
<p class="post-p">
view-transition-name: card;
contain: layout;      /<em> isolate from ancestor layout shifts </em>/
}
</code></pre>
</p>

<h3 class="post-h3">Snapshot Size</h3>

<p class="post-p">
The browser captures the element as a bitmap. Large snapshots (full-width hero images) are fine — the compositor handles them. But avoid naming dozens of elements on a page; each name creates a separate snapshot and animation group. Stick to 2-5 named elements per transition.
</p>

<h3 class="post-h3">Accessibility: <code class="inline-code">prefers-reduced-motion</code></h3>

<p class="post-p">
Always respect the user's motion preference:
</p>

<pre class="code-block"><code class="language-css">@media (prefers-reduced-motion: reduce) {
<p class="post-p">
::view-transition-old(root),
::view-transition-new(root) {
animation: none;
}
</p>

<p class="post-p">
::view-transition-group(*),
::view-transition-old(*),
::view-transition-new(*) {
animation-duration: 0s !important;
}
}
</code></pre>
</p>

<p class="post-p">
This disables all view transition animations when the user has requested reduced motion.
</p>

<h3 class="post-h3">Skip Heavy Pages</h3>

<p class="post-p">
Don't enable cross-document transitions on pages with heavy initial paint (large data tables, WebGL canvases, maps). Use <code class="inline-code">view-transition-name: none</code> on those pages or scope <code class="inline-code">@view-transition</code> to specific routes:
</p>

<pre class="code-block"><code class="language-css">/<em> Enable only on article pages </em>/
<p class="post-p">
.article-page {
view-transition-name: article-content;
}
</p>

<p class="post-p">
/<em> Disable globally, enable selectively </em>/
@view-transition {
navigation: auto;
}
</p>

<p class="post-p">
.search-results-page {
view-transition-name: none;
}
</code></pre>
</p>

<h3 class="post-h3">The <code class="inline-code">pageswap</code> and <code class="inline-code">pagereveal</code> Events</h3>

<p class="post-p">
For cross-document transitions, these new events let you run code before/after the browser captures snapshots:
</p>

<pre class="code-block"><code class="language-js">// On the OLD page, before the snapshot
<p class="post-p">
window.addEventListener('pageswap', (e) =&amp;gt; {
if (e.viewTransition) {
// Save scroll position, close menus, etc.
sessionStorage.setItem('scrollPos', window.scrollY);
closeAllPopovers();
}
});
</p>

<p class="post-p">
// On the NEW page, after the snapshot
window.addEventListener('pagereveal', (e) =&amp;gt; {
if (e.viewTransition) {
// Restore scroll position, animate entrance
const scrollPos = sessionStorage.getItem('scrollPos');
if (scrollPos) window.scrollTo(0, parseInt(scrollPos));
}
});
</code></pre>
</p>

<h2 class="post-h2">Browser Support &amp; Progressive Enhancement</h2>

<p class="post-p">
Browser support as of May 2026:
</p>

<p class="post-p">
| Browser | Same-Document | Cross-Document |
|---------|:---:|:---:|
| Chrome 111+ | ✅ | ✅ |
| Safari 18.2+ | ✅ | ✅ |
| Firefox 144+ | ✅ | ✅ |
| Edge 111+ | ✅ | ✅ |
| Opera 97+ | ✅ | ✅ |
| Samsung Internet 23+ | ✅ | ✅ |
</p>

<p class="post-p">
<strong>Global coverage: ~94% of users.</strong> Cross-document transitions work in all modern browsers. Firefox was the last to ship (April 2026).
</p>

<h3 class="post-h3">Feature Detection</h3>

<pre class="code-block"><code class="language-js">// Same-document
<p class="post-p">
const supportsSPA = 'startViewTransition' in document;
</p>

<p class="post-p">
// Cross-document (CSS-only, no JS detection needed — browsers ignore unknown at-rules)
</code></pre>
</p>

<p class="post-p">
For same-document transitions, always wrap in a feature check:
</p>

<pre class="code-block"><code class="language-js">function navigate(url) {
<p class="post-p">
if (document.startViewTransition) {
document.startViewTransition(() =&amp;gt; updateDOM(url));
} else {
updateDOM(url); // fallback: instant update
}
}
</code></pre>
</p>

<p class="post-p">
For cross-document: browsers that don't support <code class="inline-code">@view-transition</code> simply ignore it. No polyfill needed. No JS required. This is the beauty of CSS at-rules as progressive enhancement.
</p>

<h2 class="post-h2">The Big Picture: What This Replaces</h2>

<p class="post-p">
| What You Used Before | What You Use Now |
|---|---|
| Framer Motion <code class="inline-code">AnimatePresence</code> | <code class="inline-code">document.startViewTransition()</code> |
| GSAP FLIP animations | <code class="inline-code">view-transition-name</code> + CSS |
| <code class="inline-code">react-transition-group</code> | <code class="inline-code">@view-transition { navigation: auto }</code> |
| <code class="inline-code">getBoundingClientRect()</code> math | Browser handles it natively |
| Manual z-index stacking | Pseudo-element tree |
| 20KB+ animation libraries | 0 bytes |
</p>

<p class="post-p">
The View Transitions API doesn't replace every animation need — complex sequenced animations, physics-based motion, and scroll-driven effects still benefit from libraries. But for the 90% case — page transitions, list-to-detail, toast notifications, modal enter/exit — the browser now does it better, faster, and with less code.
</p>
