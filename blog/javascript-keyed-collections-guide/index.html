JavaScript Map, Set, WeakMap, WeakSet in 2026 — A Complete Guide to Keyed Collections

2026-05-29
["JavaScript""Map""Set""WeakMap""WeakSet""Data Structures""Performance""2026"]

The Object-as-Dictionary Problem

Ask any JavaScript developer how to store key-value pairs, and 95% will reach for a plain object: 

const cache = {};


cache['user:1234'] = { name: 'Ada' };
cache['user:5678'] = { name: 'Grace' };

This works — until it doesn't. Plain objects come with a long list of footguns:

  • String-only keys. cache[obj] coerces the object to "[object Object]" — every key becomes identical.
  • Prototype pollution. cache['toString'] doesn't behave like a normal key.
  • No size tracking. You need Object.keys(cache).length — O(n) every time.
  • No iteration order guarantee. (Technically there is one now, but it's complex and fragile.)
  • No built-in clear(). You have to reassign or delete every key individually.
  • Keys collide with inherited properties. __proto__, constructor, and toString all have special behavior.

JavaScript has had first-class solutions for all of these problems since ES6 (2015). In 2026, every browser and runtime supports them natively, yet most developers still reach for {} by default.

Here's the definitive guide to all four keyed collections — with real-world patterns you can use today.

Map: The Real Hash Map

Map is the direct replacement for using objects as dictionaries. It supports any type as keys, preserves insertion order, and has a proper API.

Creating Maps

// Empty map


const map = new Map();





// From iterable of [key, value] pairs
const map = new Map([
['name', 'Ada'],
['role', 'engineer'],
[42, 'the answer'],
[{ id: 1 }, 'object key'],
]);





// From Object.entries()
const config = { theme: 'dark', fontSize: 14 };
const configMap = new Map(Object.entries(config));

Core API

const users = new Map();



// Set — returns the Map (chainable)
users.set('u1', { name: 'Ada', role: 'admin' });
users.set('u2', { name: 'Grace', role: 'editor' });





// Get
users.get('u1'); // { name: 'Ada', role: 'admin' }
users.get('u3'); // undefined





// Has (faster than checking undefined — keys CAN be undefined)
users.set('u3', undefined);
users.has('u3'); // true
users.get('u3'); // undefined — has() is the only reliable check





// Size — O(1)
users.size; // 3





// Delete
users.delete('u3'); // true
users.delete('u99'); // false (key doesn't exist)





// Clear
users.clear();
users.size; // 0

Iteration

Maps preserve insertion order and are directly iterable: 

const scores = new Map([


['Alice', 95],
['Bob', 82],
['Charlie', 88],
]);





// forEach
scores.forEach((value, key) =&gt; {
console.log(${key}: ${value});
});





// for...of — iterates [key, value] pairs by default
for (const [name, score] of scores) {
console.log(${name} scored ${score});
}





// keys(), values(), entries()
[...scores.keys()];     // ['Alice', 'Bob', 'Charlie']
[...scores.values()];   // [95, 82, 88]
[...scores.entries()];  // [['Alice', 95], ['Bob', 82], ['Charlie', 88]]

Any-Type Keys

This is the killer feature — keys can be anything, not just strings: 

const metadata = new Map();


const user = { id: 1 };
const role = Symbol('admin');





metadata.set(user, { lastLogin: Date.now() });
metadata.set(role, ['write', 'delete']);
metadata.set(NaN, 'NaN key');   // NaN === NaN is false, but Map uses SameValueZero
metadata.set(0, 'zero');
metadata.set(-0, 'negative zero'); // 0 and -0 ARE the same key in Map (SameValueZero)





metadata.get(user); // { lastLogin: ... }
metadata.get(NaN);  // 'NaN key'
metadata.get(0);    // 'negative zero' — overwritten
metadata.get(-0);   // 'negative zero'

Real-World Use Case: LRU Cache

class LRUCache {


#capacity;
#map = new Map();





constructor(capacity) {
this.#capacity = capacity;
}





get(key) {
if (!this.#map.has(key)) return -1;
const value = this.#map.get(key);
// Move to end (most recently used) by re-inserting
this.#map.delete(key);
this.#map.set(key, value);
return value;
}





put(key, value) {
if (this.#map.has(key)) {
this.#map.delete(key);
} else if (this.#map.size &gt;= this.#capacity) {
// Map.keys() returns in insertion order — first key is LRU
const lru = this.#map.keys().next().value;
this.#map.delete(lru);
}
this.#map.set(key, value);
}
}

This is cleaner and faster than any object-based LRU implementation. Map.keys().next() gives us O(1) access to the least recently used key.

Real-World Use Case: Event Delegation Metadata

const listeners = new Map();



function addDelegateListener(container, selector, event, handler) {
const wrapper = (e) =&gt; {
const target = e.target.closest(selector);
if (target &amp;&amp; container.contains(target)) {
handler.call(target, e);
}
};
container.addEventListener(event, wrapper);





// Store handler→wrapper mapping for cleanup
if (!listeners.has(handler)) {
listeners.set(handler, new Map());
}
listeners.get(handler).set(container, { event, wrapper });
}





function removeDelegateListener(handler) {
const containers = listeners.get(handler);
if (!containers) return;
for (const [container, { event, wrapper }] of containers) {
container.removeEventListener(event, wrapper);
}
listeners.delete(handler);
}

Map vs Object: When to Use Which

| Feature | Map | Object | |---------|-----|--------| | Key types | Any value | String or Symbol only | | Size | .size — O(1) | Object.keys().length — O(n) | | Iteration | Directly iterable | Object.entries() | | Insertion order | Guaranteed | Mostly guaranteed (complex) | | Default keys | None | Prototype chain | | JSON serializable | No | Yes | | Performance (frequent adds/deletes) | Better | Worse | | Performance (static, string-keyed lookup) | Comparable | Slightly faster in some engines |

Rule of thumb: Use Map when keys are dynamic, unknown, or non-string. Use plain objects for static, known, string-keyed data that needs JSON serialization (e.g., config objects, API payloads, React state).

Set: The Deduped Collection

Set stores unique values of any type. Think of it as an array that automatically deduplicates.

Core API

const tags = new Set();



tags.add('javascript');
tags.add('typescript');
tags.add('javascript'); // No-op — already exists
tags.add('css');





tags.has('javascript'); // true
tags.size;              // 3
tags.delete('css');     // true
tags.clear();

Iteration

const ids = new Set(['a', 'b', 'c']);



for (const id of ids) {
console.log(id);
}





ids.forEach(id =&gt; console.log(id));





// values() and keys() are identical for Set
[...ids.values()]; // ['a', 'b', 'c']
[...ids.keys()];   // ['a', 'b', 'c']
[...ids.entries()]; // [['a', 'a'], ['b', 'b'], ['c', 'c']] — [value, value] pairs

Creating Sets from Arrays

// Deduplicate an array


const arr = [1, 2, 2, 3, 3, 3, 4];
const unique = [...new Set(arr)]; // [1, 2, 3, 4]

Set Operations (Union, Intersection, Difference)

ES2025 added native set operations — but there's a zero-dependency approach that works everywhere: 

const a = new Set([1, 2, 3, 4]);


const b = new Set([3, 4, 5, 6]);





// Union: all unique elements from both
const union = new Set([...a, ...b]);        // {1, 2, 3, 4, 5, 6}





// Intersection: elements in both
const intersection = new Set([...a].filter(x =&gt; b.has(x))); // {3, 4}





// Difference: elements in a but not in b
const difference = new Set([...a].filter(x =&gt; !b.has(x)));  // {1, 2}





// Symmetric difference: elements in either but not both
const symDiff = new Set(
[...a].filter(x =&gt; !b.has(x)).concat([...b].filter(x =&gt; !a.has(x)))
); // {1, 2, 5, 6}





// Subset: is a a subset of b?
const isSubset = [...a].every(x =&gt; b.has(x)); // false





// Superset: is a a superset of b?
const isSuperset = [...b].every(x =&gt; a.has(x)); // false

Real-World Use Case: Tracking Active Connections

class ConnectionPool {


#connections = new Set();





connect(socket) {
this.#connections.add(socket);
console.log(Active connections: ${this.#connections.size});
}





disconnect(socket) {
this.#connections.delete(socket);
console.log(Active connections: ${this.#connections.size});
}





broadcast(data) {
for (const socket of this.#connections) {
socket.send(data);
}
}





get activeCount() {
return this.#connections.size;
}
}

Real-World Use Case: Visited State Tracker

const visitedNodes = new Set();



function traverse(node) {
if (visitedNodes.has(node)) return;
visitedNodes.add(node);





// Process node...
for (const child of node.children) {
traverse(child);
}
}

For graph traversal (DFS/BFS), Set is dramatically clearer than array-based visited tracking and avoids the O(n) includes() check.

WeakMap: Garbage-Collectable Key-Value Store

WeakMap is like Map but with one crucial difference: keys are weakly referenced. If nothing else references a key object, it can be garbage collected, and its entry is automatically removed from the WeakMap.

Constraints

  • Keys MUST be objects (not primitives)
  • WeakMaps are NOT iterable (no forEach, no keys(), no size)
  • No clear() method (entries clear automatically via GC)

Why Would You Want That?

The canonical use case is private data associated with DOM nodes: 

const elementData = new WeakMap();



function setupTooltip(el, content) {
elementData.set(el, { content, shown: false });





el.addEventListener('mouseenter', () =&gt; {
const data = elementData.get(el);
if (!data.shown) {
showTooltip(el, data.content);
data.shown = true;
}
});
}





// When the element is removed from the DOM and no longer referenced,
// both the element and its associated data are garbage collected.
// No cleanup code needed. No memory leak.

With a Map, you'd have to manually delete entries when elements are removed — or leak memory. With WeakMap, the garbage collector handles it automatically.

Real-World Use Case: True Private Instance Data

Before private class fields (#field), WeakMap was the standard way to achieve truly private instance data: 

const _private = new WeakMap();



class BankAccount {
constructor(owner, balance) {
_private.set(this, { owner, balance });
}





get balance() {
return _private.get(this).balance;
}





deposit(amount) {
const data = _private.get(this);
data.balance += amount;
return data.balance;
}





withdraw(amount) {
const data = _private.get(this);
if (amount &gt; data.balance) throw new Error('Insufficient funds');
data.balance -= amount;
return data.balance;
}





// owner is truly inaccessible from outside
}

In 2026, #privateFields are preferred for this (they're syntactic sugar and slightly faster), but WeakMap-based privacy is still valuable when you need to share private state across multiple classes or between a class and its mixins.

Real-World Use Case: Caching Computed Values

const computedCache = new WeakMap();



function getExpensiveComputation(obj) {
if (computedCache.has(obj)) {
return computedCache.get(obj);
}
const result = / expensive computation using obj /;
computedCache.set(obj, result);
return result;
}





// When obj is garbage collected, its cached result is automatically freed.
// No manual cache eviction needed.

This pattern is used by libraries like Zod, Valibot, and React's internal hooks system. It's the most memory-efficient caching pattern in JavaScript.

WeakMap vs Private Fields: 2026 Guidance

| Feature | WeakMap | #private | |---------|---------|------------| | Syntax | Verbose setup | this.#field | | Performance | Slightly slower | Faster (engine-optimized) | | Cross-class sharing | ✅ Easy | ❌ Per-class | | Dynamic key objects | ✅ Any object | Only this | | Debugging | Harder to inspect | Visible in DevTools | | Garbage collection | Automatic | Tied to instance lifecycle |

Use #private for class-specific private state. Use WeakMap when you need shared, cross-cutting private state, caching, or DOM metadata.

WeakSet: Garbage-Collectable Membership Tracker

WeakSet stores objects and, like WeakMap, holds them weakly. If nothing else references an object in a WeakSet, it gets garbage collected.

Constraints

  • Values MUST be objects
  • Not iterable (no forEach, no size)
  • No clear()

Real-World Use Case: Branding / Tagging Objects

const processedItems = new WeakSet();



function processItem(item) {
if (processedItems.has(item)) {
console.log('Already processed, skipping');
return;
}
processedItems.add(item);
// ... expensive processing ...
}

Real-World Use Case: Circular Reference Detection

const visiting = new WeakSet();



function deepClone(obj) {
if (typeof obj !== 'object' || obj === null) return obj;
if (visiting.has(obj)) throw new Error('Circular reference detected');





visiting.add(obj);
const clone = Array.isArray(obj) ? [] : {};





for (const [key, value] of Object.entries(obj)) {
clone[key] = deepClone(value);
}





visiting.delete(obj); // Allow object to appear multiple times in different branches
return clone;
}

Real-World Use Case: Preventing Double-Invocation of Callbacks

const invoked = new WeakSet();



function once(fn) {
return function (...args) {
if (invoked.has(fn)) return;
invoked.add(fn);
return fn.apply(this, args);
};
}





const init = once(() =&gt; console.log('Initialized'));
init(); // 'Initialized'
init(); // (silent no-op)

Performance: The Numbers

Here's a rough performance comparison of common operations (relative, not absolute — exact numbers depend on the engine):

| Operation | Performance | |-----------|-------------| | Map.set() vs Object assignment | Map is ~20% faster for frequent adds/deletes | | Map.get() vs Object access | Comparable for string keys; Map wins for non-string keys | | Set.has() vs Array.includes() | O(1) vs O(n) — Set wins massively for large collections | | Set iteration | Comparable to array iteration | | WeakMap memory | Zero leak-by-design; Map requires manual cleanup |

The 100-element rule: For collections under ~100 elements, the difference is negligible. For anything larger, or any code that runs in a hot loop, Map and Set should be your defaults.

Decision Flowchart

Do you need key-value pairs?


├── Keys are strings AND data needs JSON serialization?
│   └── Use Object
├── Keys are objects AND entries should auto-cleanup when keys are GC'd?
│   └── Use WeakMap
└── Otherwise?
└── Use Map





Do you need a collection of unique values?
├── Values are objects AND membership should auto-cleanup when values are GC'd?
│   └── Use WeakSet
└── Otherwise?
└── Use Set

Common Mistakes

1. Using map.get(key) to check existence

// ❌ Wrong — breaks when value is undefined, 0, '', null, or false


if (map.get(key)) { ... }





// ✅ Correct
if (map.has(key)) { ... }

2. Expecting JSON.stringify to work

const map = new Map([['a', 1]]);


JSON.stringify(map); // '{}' — Map is not JSON-serializable





// ✅ Convert first
JSON.stringify([...map]); // '[["a",1]]'
// Or
JSON.stringify(Object.fromEntries(map)); // '{"a":1}'

3. Using WeakMap with primitive keys

const wm = new WeakMap();


wm.set('hello', 'world'); // TypeError: Invalid value used as weak map key

4. Forgetting that Set only checks reference equality for objects

const set = new Set();


set.add({ id: 1 });
set.add({ id: 1 });
set.size; // 2 — different object references!

5. Overusing WeakMap for everything

WeakMap is not a silver bullet. If you need iteration, size, or primitive keys, use Map. WeakMap is specifically for the "associate data with objects and auto-clean when they're GC'd" use case.

The Bottom Line

JavaScript's keyed collections aren't niche features — they're fundamental data structures that solve real problems:

  • Map replaces object-as-dictionary with better API, non-string keys, and O(1) size
  • Set replaces array-for-uniqueness with O(1) has() and automatic deduplication
  • WeakMap enables zero-leak private data and DOM metadata patterns
  • WeakSet enables zero-leak membership tracking and branding

In 2026, every JavaScript developer should reach for these before reaching for {} or [] for collection use cases. The APIs are ergonomic, the performance is better, and the intent is clearer.

Stop using objects for everything. Your future self (and your garbage collector) will thank you.
