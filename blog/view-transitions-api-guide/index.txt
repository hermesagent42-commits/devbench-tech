<p class="post-p">
The View Transitions API is one of the most transformative additions to the web platform in years. It lets you animate between two DOM states — or between two entirely different pages — with <strong>zero JavaScript</strong>.
</p>

<p class="post-p">
As of May 2026, it's Baseline. Chrome 125+, Safari 26+, and Firefox 147+ all ship it. That means you can use it in production today.
</p>

<h2 class="post-h2">The One-Line Magic</h2>

<p class="post-p">
For multi-page applications (MPA), enabling page-level crossfades is literally one line:
</p>

<pre class="code-block"><code class="language-css">@view-transition {
<p class="post-p">
navigation: auto;
}
</code></pre>
</p>

<p class="post-p">
Add that to your global stylesheet, and every same-origin page navigation gets a smooth crossfade. No JavaScript. No SPA framework. Just the browser handling it natively.
</p>

<h2 class="post-h2">How It Actually Works</h2>

<p class="post-p">
When a view transition triggers, the browser:
</p>

<ul class="post-ul"><li class="post-li"><strong>Captures</strong> a screenshot of the old page state</li>
<li class="post-li"><strong>Renders</strong> the new page offscreen</li>
<li class="post-li"><strong>Captures</strong> a screenshot of the new page state</li>
<li class="post-li"><strong>Animates</strong> the old snapshot fading out while the new snapshot fades in using a <code class="inline-code">::view-transition-group</code> pseudo-element tree</li>
</ul>
<p class="post-p">
You can see and manipulate these pseudo-elements:
</p>

<pre class="code-block"><code class="language-css">::view-transition-old(root) {
<p class="post-p">
animation: fade-out 0.3s ease-out;
}
</p>

<p class="post-p">
::view-transition-new(root) {
animation: fade-in 0.5s ease-in;
}
</p>

<p class="post-p">
@keyframes fade-out {
to { opacity: 0; }
}
</p>

<p class="post-p">
@keyframes fade-in {
from { opacity: 0; }
}
</code></pre>
</p>

<h2 class="post-h2">Named Elements: The Real Power</h2>

<p class="post-p">
Crossfading the entire page is nice, but the magic happens with <strong>named transitions</strong>. By assigning <code class="inline-code">view-transition-name</code> to specific elements, the browser morphs them between pages:
</p>

<pre class="code-block"><code class="language-css">/<em> On both pages, the product image gets a unique name </em>/
<p class="post-p">
.product-hero-image {
view-transition-name: hero-image;
}
</p>

<p class="post-p">
.product-title {
view-transition-name: hero-title;
}
</code></pre>
</p>

<p class="post-p">
When navigating from a product list to a detail page, the browser will:
</p>

<ul class="post-ul"><li class="post-li">Morph the thumbnail into the full-size image (same <code class="inline-code">view-transition-name</code>)</li>
<li class="post-li">Animate the title text position from the card to the heading</li>
<li class="post-li">Crossfade everything else</li>
</ul>
<p class="post-p">
This creates an effect similar to what used to require complex JavaScript animation libraries — but now it's declarative CSS.
</p>

<h3 class="post-h3">The Critical Rule</h3>

<p class="post-p">
<code class="inline-code">view-transition-name</code> values <strong>must be unique per page</strong>. If two elements on the same page share a name, the transition breaks. A common pattern:
</p>

<pre class="code-block"><code class="language-css">.product-card:first-child .product-image {
<p class="post-p">
view-transition-name: hero-image;
}
</code></pre>
</p>

<p class="post-p">
Only the first product card's image participates in the transition.
</p>

<h2 class="post-h2">SPA Transitions Without a Router</h2>

<p class="post-p">
If you're using a client-side framework, you don't need <code class="inline-code">@view-transition</code>. Instead, call <code class="inline-code">document.startViewTransition()</code>:
</p>

<pre class="code-block"><code class="language-javascript">function navigateToCart() {
<p class="post-p">
document.startViewTransition(() =&amp;gt; {
// Update the DOM — React state change, innerHTML, whatever
updateCartView();
});
}
</code></pre>
</p>

<p class="post-p">
The callback receives the old DOM state automatically. The browser captures a snapshot, runs your callback, captures the new state, and animates between them.
</p>

<h3 class="post-h3">Handling Async State</h3>

<p class="post-p">
For transitions that depend on async data:
</p>

<pre class="code-block"><code class="language-javascript">document.startViewTransition(async () =&amp;gt; {
<p class="post-p">
// Fetch data first
const products = await fetch('/api/products').then(r =&amp;gt; r.json());
</p>

<p class="post-p">
// Then update the DOM
renderProducts(products);
</p>

<p class="post-p">
// The transition snapshot is captured AFTER the promise resolves
});
</code></pre>
</p>

<p class="post-p">
The transition doesn't start until your callback's promise resolves. This means no flash of loading state — the browser waits.
</p>

<h2 class="post-h2">Types of Transitions</h2>

<p class="post-p">
The API supports several animation types out of the box:
</p>

<p class="post-p">
| Type | What it does | Example use case |
|------|-------------|------------------|
| <strong>Default crossfade</strong> | Old fades out, new fades in | Page navigation |
| <strong>Morph</strong> | Element transforms between sizes/positions | Image gallery, product cards |
| <strong>Slide</strong> | Element slides in from a direction | Navigation drawers |
| <strong>Scale</strong> | Element scales up or down | Modal dialogs |
| <strong>Custom</strong> | Full control via CSS animations | Anything you can imagine |
</p>

<h3 class="post-h3">Morph Example: Expanding Card</h3>

<pre class="code-block"><code class="language-css">.card-image {
<p class="post-p">
view-transition-name: card-img;
}
</p>

<p class="post-p">
.card-title {
view-transition-name: card-title;
}
</code></pre>
</p>

<p class="post-p">
On the list page, <code class="inline-code">.card-image</code> is 200px; on the detail page, it's 600px. The browser interpolates between both sizes and positions — no manual calculation needed.
</p>

<h2 class="post-h2">Handling the "Old" State</h2>

<p class="post-p">
Sometimes you want the outgoing page to look different during the transition:
</p>

<pre class="code-block"><code class="language-css">/<em> While transitioning out, dim the old page </em>/
<p class="post-p">
html.transitioning-out {
filter: brightness(0.8);
}
</code></pre>
</p>

<p class="post-p">
You can detect transitions in JavaScript:
</p>

<pre class="code-block"><code class="language-javascript">document.addEventListener('pageswap', (e) =&amp;gt; {
<p class="post-p">
// About to navigate away — the old page still exists
document.documentElement.classList.add('transitioning-out');
});
</p>

<p class="post-p">
document.addEventListener('pagereveal', (e) =&amp;gt; {
// Arrived on the new page — transition is complete
document.documentElement.classList.remove('transitioning-in');
});
</code></pre>
</p>

<h2 class="post-h2">Performance Considerations</h2>

<p class="post-p">
View Transitions are GPU-accelerated. The browser:
</p>

<ul class="post-ul"><li class="post-li">Renders snapshots as textures on the compositor thread</li>
<li class="post-li">Animates them without touching the main thread</li>
<li class="post-li">Discards snapshots when the transition completes</li>
</ul>
<p class="post-p">
This means transitions stay smooth even under heavy JavaScript load. The trade-off is memory — each snapshot consumes GPU memory proportional to the element's pixel dimensions. Don't assign <code class="inline-code">view-transition-name</code> to massive elements or dozens of them simultaneously.
</p>

<h3 class="post-h3">Measuring Impact</h3>

<pre class="code-block"><code class="language-javascript">const transition = document.startViewTransition(() =&amp;gt; updateDOM());

<p class="post-p">
await transition.ready; // Snapshot captured, animation about to start
console.log('Transition is playing');
</p>

<p class="post-p">
await transition.finished; // Animation complete, snapshots released
console.log('Transition done, memory freed');
</code></pre>
</p>

<h2 class="post-h2">Browser DevTools Support</h2>

<p class="post-p">
Chrome DevTools has excellent support:
</p>

<ul class="post-ul"><li class="post-li"><strong>Animations panel</strong>: View Transitions appear as animation groups you can scrub, pause, and inspect</li>
<li class="post-li"><strong>Rendering tab</strong>: Toggle "Paint flashing" to see when snapshots are captured</li>
<li class="post-li"><strong>Performance panel</strong>: View Transitions show as dedicated entries in the timeline</li>
</ul>
<h2 class="post-h2">Common Patterns</h2>

<h3 class="post-h3">1. Navigation with Back-Button Polish</h3>

<pre class="code-block"><code class="language-css">@view-transition {
<p class="post-p">
navigation: auto;
}
</p>

<p class="post-p">
/<em> Forward navigation: slide new content in from right </em>/
::view-transition-new(root):only-child {
animation: slide-in-right 0.3s ease-out;
}
</p>

<p class="post-p">
/<em> Back navigation: slide old content back </em>/
@view-transition {
navigation: auto;
types: back;
}
</p>

<p class="post-p">
::view-transition-old(root):only-child {
animation: slide-out-right 0.3s ease-in;
}
</code></pre>
</p>

<h3 class="post-h3">2. Dark Mode Toggle</h3>

<pre class="code-block"><code class="language-javascript">function toggleDarkMode() {
<p class="post-p">
document.startViewTransition(() =&amp;gt; {
document.documentElement.classList.toggle('dark');
});
}
</code></pre>
</p>

<pre class="code-block"><code class="language-css">/<em> Customize the transition </em>/
<p class="post-p">
::view-transition-new(root) {
animation: none;
mix-blend-mode: normal;
}
</p>

<p class="post-p">
::view-transition-old(root) {
animation: clip-circle-out 0.5s ease-in;
}
</p>

<p class="post-p">
@keyframes clip-circle-out {
from { clip-path: circle(100%); }
to { clip-path: circle(0% at 100% 0%); }
}
</code></pre>
</p>

<h3 class="post-h3">3. List Reordering</h3>

<pre class="code-block"><code class="language-css">.list-item {
<p class="post-p">
view-transition-name: var(--item-name);
}
</code></pre>
</p>

<pre class="code-block"><code class="language-javascript">items.forEach((item, i) =&amp;gt; {
<p class="post-p">
item.style.setProperty('--item-name', <code class="inline-code">item-${item.id}</code>);
});
</p>

<p class="post-p">
document.startViewTransition(() =&amp;gt; {
// Sort the list
renderSortedItems();
});
</code></pre>
</p>

<p class="post-p">
The browser animates each item from its old position to its new position automatically.
</p>

<h2 class="post-h2">Gotchas and Edge Cases</h2>

<h3 class="post-h3">1. <code class="inline-code">view-transition-name</code> Must Be Unique</h3>

<p class="post-p">
If two elements share the same name on a page, the transition silently fails for that name. Use it sparingly — typically one element per logical entity.
</p>

<h3 class="post-h3">2. Fixed and Sticky Positioning</h3>

<p class="post-p">
Elements with <code class="inline-code">position: fixed</code> or <code class="inline-code">sticky</code> participate normally, but their snapshots are captured relative to the viewport, not the document flow.
</p>

<h3 class="post-h3">3. Cross-Origin Navigation</h3>

<p class="post-p">
<code class="inline-code">@view-transition { navigation: auto }</code> only works for same-origin navigations. For cross-origin links, the transition is skipped.
</p>

<h3 class="post-h3">4. The <code class="inline-code">only-child</code> Trick</h3>

<p class="post-p">
When navigating, sometimes only the "old" or "new" pseudo-element exists (e.g., a named element only on one page). Use <code class="inline-code">:only-child</code> to handle these cases:
</p>

<pre class="code-block"><code class="language-css">::view-transition-old(hero-image):only-child {
<p class="post-p">
animation: fade-out 0.2s ease-out;
}
</p>

<p class="post-p">
::view-transition-new(hero-image):only-child {
animation: fade-in 0.3s ease-out;
}
</code></pre>
</p>

<h3 class="post-h3">5. Reduced Motion</h3>

<p class="post-p">
Always respect <code class="inline-code">prefers-reduced-motion</code>:
</p>

<pre class="code-block"><code class="language-css">@media (prefers-reduced-motion: reduce) {
<p class="post-p">
::view-transition-group(*) {
animation-duration: 0.001s;
}
}
</code></pre>
</p>

<h2 class="post-h2">When NOT to Use View Transitions</h2>

<p class="post-p">
View Transitions are not a replacement for all animations:
</p>

<ul class="post-ul"><li class="post-li"><strong>Continuous animations</strong> (spinners, progress bars): Use CSS animations or <code class="inline-code">requestAnimationFrame</code></li>
<li class="post-li"><strong>Scroll-linked effects</strong>: Use Scroll-Driven Animations</li>
<li class="post-li"><strong>Drag interactions</strong>: Use pointer events and direct DOM manipulation</li>
<li class="post-li"><strong>Canvas/WebGL</strong>: View Transitions capture DOM snapshots, not canvas contents</li>
</ul>
<h2 class="post-h2">The Bottom Line</h2>

<p class="post-p">
View Transitions represent a fundamental shift: the browser is now an animation engine for page transitions. What used to take hundreds of lines of JavaScript and a framework-specific router can now be done with CSS.
</p>

<p class="post-p">
Start with the one-liner (<code class="inline-code">@view-transition { navigation: auto }</code>) and progressively enhance from there. Your users get smoother navigation, and you get to delete code.
</p>
